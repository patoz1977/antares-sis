## Purpose

This document is the official historical record of the project.

It records completed work in chronological order.

It intentionally excludes:

- the current status of the project (see `02.CURRENT_STATUS.md`);
- future planning (see `03.ROADMAP.md`).

This document is immutable except for the addition of new historical entries.

# Logging Rules

Every completed milestone shall generate a new entry.

Each entry should record:

- date;
- completed milestone;
- summary of the work performed;
- important architectural decisions;
- documentation updated;
- repository status.

Entries shall never be modified to reflect the current state of the project.

### Temporary User Lockout Policy

**Date:** 2026-07-31

**Milestone:** E004.1 — Identity & Access Baseline

**Status:** Documentary decision completed

#### Ambiguity

ADR-0013 required failed-attempt tracking and a temporary lock represented by `locked_at`, but the official documentation did not define the threshold, duration, expiration behavior or institutional configuration.

#### Decision

ADR-0016 approved a default threshold of five consecutive failed attempts and a default duration of fifteen minutes. Both values are configurable per deployment through a typed authentication policy. Attempts during an active lock do not extend it; expiration and successful authentication reset `failed_login_attempts` and `locked_at`; `USER_STATUS = DISABLED` remains independent.

- Billing, Medical, Transport, leave-alone, AcademicPlacement and Acknowledgements remain outside the snapshot. The existing acknowledgement satisfaction boundary accepts zero active requirements or a historical Completion, and Reopening/Resubmission never forces recompletion.

- Representative Review is side-effect free and shows current authorized data, prospective snapshot resources, annual state, placement, acknowledgement state and one non-persisted authoritative validation result with safe actionable requirement codes/messages. POST Submit revalidates from scratch and is never autosave or an automatic transition.
- Reopen changes Submitted → Draft without reason, reset, copy or snapshot removal. Resubmission reruns all rules and atomically replaces the single snapshot on the same Enrollment. Complete changes Submitted → Completed with the server Clock and no unrelated side effect. Cancel changes Draft/Submitted → Cancelled without delete, reason or external status mutation. Secretaría review uses current annual state plus immutable snapshot; its list is operational, not E013 reporting. The temporary exact `admin` gate may be reused but is not definitive RBAC.

- No new Aggregate, Domain behavior or schema delta is expected. Migrations remain exactly 001–009; migration 010 is absent. Existing Enrollment Persistence needs no redesign, though Phase 2 may add only proven locking/read capabilities for a stable cross-Aggregate snapshot source.
