# DOMAIN MODEL

**Versión:** 2.0
**Estado:** Aprobado
**Última actualización:** Julio 2026

---

# 1. Propósito

Este documento define el modelo de dominio del Sistema de Información Escolar (SIS).

Su objetivo es establecer un lenguaje común entre el negocio, la arquitectura del sistema y las herramientas de desarrollo asistidas por IA (ChatGPT y GitHub Copilot).

Este documento constituye la fuente oficial para comprender:

- las entidades del negocio;
- las responsabilidades de cada entidad;
- las relaciones entre ellas;
- los límites del dominio;
- las reglas generales del negocio.

No describe la implementación física de la base de datos ni detalles específicos del framework. Esas decisiones se documentan en `DATABASE_DESIGN.md`.

---

# 2. Objetivos del modelo

El modelo de dominio debe cumplir los siguientes objetivos:

- representar fielmente la operación de una institución educativa;
- evitar duplicación de información;
- separar claramente identidad, autenticación y reglas del negocio;
- facilitar la evolución futura del producto;
- soportar múltiples instituciones mediante una única base de código;
- mantener independencia entre el dominio y la tecnología utilizada.

El dominio debe permanecer estable aunque cambien:

- la base de datos;
- el framework;
- el motor de autenticación;
- la interfaz de usuario.

---

# 3. Alcance

Este documento describe el dominio del MVP. Incluye autenticación, representantes, estudiantes, familias, matrícula anual en línea, BillingInformation de Enrollment, MedicalInformation anual, contactos de emergencia familiares, autorizados de retiro familiares, requerimiento institucional de transporte, documentos institucionales y revisión administrativa.

Fuera de alcance: emisión de facturas, cuentas por cobrar, contabilidad, pagos y procesamiento financiero; nómina, biblioteca, calificaciones, asistencia y recursos humanos. BillingInformation requerida dentro de Enrollment no implica facturación ni pagos.

# 4. Principios del modelo

## 4.1 White Label

El sistema es un producto comercial para múltiples instituciones educativas.

Todo el código debe ser reutilizable.

Nunca se deben incorporar nombres, configuraciones o reglas específicas de una institución dentro del dominio.

---

## 4.2 Una base de datos por institución

Cada institución utiliza:

- una base de datos propia;
- un archivo `.env` propio;
- una configuración independiente.

Por esta razón el dominio **no** incluye una entidad `Institution`.

Tampoco existirán campos como:

- institution_id
- school_id
- tenant_id

en las tablas del negocio.

---

## 4.3 Separación de responsabilidades

El dominio distingue claramente entre:

- identidad;
- autenticación;
- roles;
- relaciones.

Estas responsabilidades nunca deben mezclarse dentro de una misma entidad.

---

## 4.4 Person como fuente única de identidad

Person es la identidad institucional única de quien posee identidad o un rol institucional. Student y Representative siempre referencian Person. FamilyEmergencyContact y FamilyAuthorizedPickup son recursos de datos propiedad de Family: no son Person, no tienen User y pueden reutilizarse entre estudiantes de esa Family.

## 4.5 User no representa una persona

Una cuenta de usuario únicamente representa credenciales de acceso.

Las credenciales nunca contienen información personal.

Toda cuenta pertenece exactamente a una persona.

Una persona puede existir sin tener una cuenta de usuario.

---

## 4.6 Roles de negocio

Los roles representan responsabilidades dentro del sistema.

Un rol agrega comportamiento.

No representa identidad.

Los principales roles del MVP son:

- Representative
- Student

En futuras versiones podrán existir:

- Teacher
- Staff
- Administrator
- Applicant
- Alumni

---

## 4.7 Relaciones del dominio

Family gestiona membresías y recursos reutilizables. Las relaciones de representante y estudiante se modelan mediante FamilyRepresentative y FamilyStudent. Emergency contacts y authorized pickups no son relaciones entre Person: son datos familiares asignables a estudiantes de la misma Family.

# 5. Lenguaje Ubicuo (Ubiquitous Language)

Todos los desarrolladores, herramientas de IA y documentación utilizarán el mismo vocabulario.

| Concepto | Definición |
|----------|------------|
| User | Cuenta de acceso asociada a Person. |
| Person | Identidad física institucional. |
| Representative | Rol institucional que representa y gestiona estudiantes. |
| Student | Rol académico estable asociado a Person. |
| Family | Unidad administrativa de representantes, estudiantes y recursos familiares reutilizables. |
| Enrollment | Matrícula anual de un Student para un AcademicPeriod. |
| FamilyEmergencyContact | Dato familiar de contacto de emergencia; no es Person. |
| FamilyAuthorizedPickup | Dato familiar de autorización de retiro; no es Person. |
| MedicalInformation | Value Object anual de Enrollment. |
| TransportInformation | Value Object anual de Enrollment con el requerimiento institucional. |
| Catalog | Lista institucional configurable de valores. |

Todo el código, documentación y conversaciones técnicas deberán utilizar estos términos.

# 6. Bounded Contexts

## Identity & Access
Owns Person, ContactInformation, User, authentication and access state. Person is the single physical identity; User is optional and credentials never belong to Person.

## Family Management
Owns Representative, Family, memberships and reusable FamilyAddress, FamilyEmergencyContact and FamilyAuthorizedPickup resources with assignments.

## Academic Core
Owns the stable Student role only. It does not own grade, section, medical data, transport, emergency contacts, pickups or annual enrollment.

## Enrollment
Owns annual Enrollment lifecycle, AcademicPlacement, BillingInformation, MedicalInformation, TransportInformation, leave-alone authorization, DocumentAcceptance and submission snapshot.

## Catalogs
Owns institution-managed values, including the geographic hierarchy Province → Canton → Parish and academic catalogs.

## Institutional Documents
Owns InstitutionalDocument, InstitutionalDocumentVersion and DocumentRequirement; Enrollment owns acceptance only.

# 7. Actores del dominio

## Secretaría
Creates and maintains identities, roles and families; initiates annual enrollment; maintains restricted fields; reviews, reopens, completes and cancels enrollment.

## Representante
Uses an active User, selects one authorized Family context, updates permitted personal/contact/employment data and family resources, completes annual data, accepts documents and submits. May not create students/representatives, edit another representative, change grade/section or edit after Submitted unless reopened.

## Estudiante
Has no portal access in MVP. Is managed by Secretaría and authorized representatives, has one active Family and one Enrollment per AcademicPeriod.

# 8. Aggregates

| Aggregate Root | Entities / Value Objects | Responsabilidad |
|---|---|---|
| Person | User; PersonalName, Identification, ContactInformation | Identidad y contacto |
| Representative | EmploymentInformation | Rol institucional |
| Student | — | Rol académico estable |
| Family | FamilyRepresentative, FamilyStudent, dirección/contacto/pickup y asignaciones; Address, Geolocation | Recursos familiares reutilizables |
| Enrollment | DocumentAcceptance, EnrollmentSubmissionSnapshot; AcademicPlacement, BillingInformation, MedicalInformation, TransportInformation | Matrícula anual |

# 9. Aggregate: Person

## Entidades y Value Objects
`Person(PersonId, PersonalName, Identification, BirthDate, SexId, MaritalStatusId?, EducationLevelId?, ContactInformation?, Status)`. PersonalName contiene first/middle names y surnames; Identification contiene DocumentTypeId y DocumentNumber; ContactInformation contiene email, mobile y landline opcionales. `User(UserId, PersonId, UsernameOrEmail, PasswordCredential, Status, LastAccessAt?, LockedAt?)` es Entity.

## Reglas e invariantes
Identification es única por institución cuando existe. Person puede no tener ContactInformation ni User; User siempre pertenece a Person. Student no tiene User en MVP. Email y mobile de Representative son obligatorios al enviar matrícula, no para toda Person.

# 10. Aggregate: Representative

`Representative(RepresentativeId, PersonId, EmploymentInformation, Status)`. EmploymentInformation tiene Occupation?, Company?, Position?, WorkPhone? y WorkEmail?; todos opcionales y Occupation es texto libre. No duplica datos de Person; puede tener múltiples Family activas; desactivar no elimina Person.

# 11. Aggregate: Student

`Student(StudentId, PersonId, InstitutionalCode, AdmissionDate, Status)`. Grade/Section y los datos médicos, transporte, contactos y pickups no pertenecen a Student. Tiene una relación Family activa, puede conservar historia y no requiere ContactInformation.

# 12. Aggregate: Family

## Entidades
`Family(FamilyId, DisplayName, Status)`; `FamilyRepresentative(RepresentativeId, RelationshipTypeId, IsPrimary, Status)`; `FamilyStudent(StudentId, StartedAt, EndedAt?, Status)`; `FamilyAddress(Label, Address, Status)`; `FamilyEmergencyContact(Names, Relationship, MobilePhone, Phone?, Email?, Observations?, Status)`; `FamilyAuthorizedPickup(Names, Relationship, MobilePhone, Phone?, DocumentNumber, Observations?, Status)` y sus asignaciones.

## Address y asignaciones
Address contiene ProvinceId, CantonId, ParishId, MainStreet, StreetNumber?, SecondaryStreet?, Sector?, Reference? y Geolocation?. Label, jerarquía geográfica y MainStreet son requeridos. Cada Representative tiene a lo sumo una dirección activa por Family; Student una dirección activa. AddressAssignment es conceptual: en persistencia se divide por representante/estudiante. Cambiar asignación desactiva la anterior; recurso asignado no se elimina.

## Reglas e invariantes
Family tiene al menos un Representative activo, máximo un primary activo y recursos que no cruzan fronteras. Representative puede tener muchas Family; Student exactamente una activa. EmergencyContact y AuthorizedPickup no son Person, no tienen User, son reutilizables entre hermanos y no se eliminan asignados. Contact puede asignarse a muchos Students; se exige al menos uno activo antes de envío. Pickup puede ser cero únicamente con autorización de salir solo.

# 13. Aggregate: Enrollment

`Enrollment(EnrollmentId, StudentId, FamilyId, AcademicPeriodId, AcademicPlacement, BillingInformation, MedicalInformation, TransportInformation, IsAuthorizedToLeaveAlone, Status, timestamps, DocumentAcceptances, EnrollmentSubmissionSnapshot?)`. AcademicPlacement contiene GradeId y SectionId?; TransportInformation solo RequiresInstitutionalTransport obligatorio. Payment, rutas, proveedores, conductores y observaciones de transporte están fuera de alcance.

## Estados y transiciones
`Draft → Submitted → Completed`; `Submitted → Draft` solo por Secretaría; `Draft|Submitted → Cancelled`. Returned, Approved y Rejected son obsoletos. En Draft hay navegación libre; Submitted bloquea edición del representante.

## Snapshot
En el primer envío se crea un único EnrollmentSubmissionSnapshot con dirección, EmergencyContacts y AuthorizedPickups seleccionados; reenvío lo reemplaza. No copia billing, medical, transport, placement ni acceptances.

## Invariantes de envío
Student/period es único; Representative y Student deben estar activos en la Family seleccionada; dirección activa, contactos, regla pickup/leave-alone, campos anuales, grade y documentos requeridos deben ser válidos. Submission es atómica.

# 14. Servicios de dominio, eventos y repositorios

## Domain Services
`EnrollmentSubmissionService.Submit` valida acceso, membresía, identidad/periodo, datos obligatorios, recursos, documentos, construye/reemplaza snapshot y pasa a Submitted. `EnrollmentInitializationService.Start` asegura unicidad, propone siguiente grade, pre-carga datos anuales permitidos y crea Draft. `FamilyAccessService` resuelve familias accesibles y autorización server-side.

## Eventos
Esenciales: PersonCreated, UserCreated, UserActivated, UserDisabled, RepresentativeAssignedToFamily, RepresentativeRemovedFromFamily, StudentAssignedToFamily, StudentRemovedFromFamily, EnrollmentStarted, EnrollmentSubmitted, EnrollmentReopened, EnrollmentCompleted, EnrollmentCancelled. Eventos de recursos/datos se agregan solo con consumidor real. Autosave no emite eventos por campo.

## Repositories
Uno por Aggregate Root: PersonRepository, RepresentativeRepository, StudentRepository, FamilyRepository y EnrollmentRepository. EnrollmentRepository busca por Student/AcademicPeriod, drafts por Family y submitted para revisión; persiste el snapshot. No existen repositorios para recursos internos de Family.

# 15. Context Map y reglas de acceso

```text
Identity & Access (PersonId)
  → Family Management (RepresentativeId, StudentId, FamilyId)
  → Enrollment ← Academic Core (StudentId)
Catalogs → todos los contextos
Institutional Documents → Enrollment
```

Monolito modular con contratos explícitos, ids y eventos, sin acceso irrestricto a tablas ajenas. Toda solicitud valida `User → Person → Representative → FamilyRepresentative → selected Family`; la selección de cliente nunca autoriza.
