# MVP Validation and Closure Baseline

**Version:** 1.0
**Status:** Approved MVP-VALIDATION-001 baseline
**Last updated:** 2026-09-15

---

# 1. Purpose

This document defines the permanent protocol for integrated MVP validation, owner acceptance and formal closure after the approved deployment baseline has been completed.

It does not redefine architecture, business rules, Domain behavior, schema, catalogs, UI/UX or deployment. Those responsibilities remain respectively in `10.ARCHITECTURE.md`, the applicable functional/domain documents and ADRs, `12.DATABASE_DESIGN.md`, `14.CATALOGS.md`, `16.UI_UX_BASELINE.md`, `17.BULK_IMPORT_BASELINE.md` and `18.DEPLOYMENT_BASELINE.md`.

---

# 2. Scope

MVP-VALIDATION-001 covers:

- post-deployment documentation synchronization;
- one persistent local review installation;
- integrated technical acceptance;
- an owner-led functional and visual walkthrough;
- deterministic defect triage;
- conditional correction of qualifying defects;
- affected physical checks and integrated automated regression;
- explicit owner acceptance and formal MVP closure.

Formal closure is not implied by prior component or deployment validation. It occurs only when every gate in this document is satisfied.

---

# 3. Explicit Exclusions

This milestone does not authorize:

- new business capabilities or business rules;
- an installer wizard, provisioner or deployment automation;
- new generic administration screens;
- i18n, a language selector or multilingual content management;
- architectural redesign;
- schema changes unless a confirmed MVP blocker proves one unavoidable and receives explicit authorization;
- repair of the corrupted local XAMPP MariaDB `mysql.db` system database;
- committed production, review or demo data;
- committed credentials, SQL artifacts, institution-specific assets or PII;
- work belonging to a future milestone.

---

# 4. Approved Phase Sequence

1. **Phase 1 — Post-DEPLOY Synchronization & Validation Baseline:** synchronize the PR #83 post-merge state and establish this permanent protocol.
2. **Phase 2 — Persistent Local Installation & Technical Acceptance:** prepare and validate the persistent production-like local review installation.
3. **Phase 3 — Owner Functional & Visual Acceptance:** execute the owner walkthrough across the implemented capability and presentation boundaries.
4. **Phase 4 — Conditional Correction, Integrated Validation & Formal Closure:** correct only qualifying findings when present, repeat applicable validation and record the closure verdict.

Phase 4 contains correction work only when Phase 3 finds an A–C defect under Section 7. No unnecessary empty correction step is created when none exists; Phase 4 then performs integrated validation and formal closure directly.

Each phase requires its own authorization. Starting or completing this baseline does not authorize a later phase.

---

# 5. Persistent Review Installation Contract

Phase 2 uses one persistent local review environment that remains available throughout Phases 2–4:

- a clean MariaDB instance compatible with the approved `18.DEPLOYMENT_BASELINE.md` target;
- one dedicated empty database created manually by the owner through phpMyAdmin after the environment is ready;
- a fresh institution-specific `install.sql` kept external and untracked;
- a local untracked `.env`;
- local deployment-owned White Label assets;
- the application root outside the web root and its internal `public/` directory as DocumentRoot;
- no installer, provisioner, production CLI dependency or automatic database creation;
- no repair of the corrupted XAMPP `mysql.db` unless separately analyzed and authorized.

The installation is persistent review state, not a disposable harness database. Closure does not prescribe its deletion: the owner decides whether to retain or remove it after acceptance. Credentials, SQL and local assets remain outside Git regardless of that decision.

DEPLOY-001 physical evidence remains authoritative while its tested boundary is unchanged. Expensive physical validation is not repeated without cause; it is repeated when a qualifying correction affects schema, migrations, persistence, transactions, database configuration or another physically relevant boundary.

# 6. Review-data Taxonomy

## 6.1 Installation/master data

Installation/master data is the exact approved institutional baseline required to make a clean installation operable. It is governed by `14.CATALOGS.md` and the concrete installation contract in `18.DEPLOYMENT_BASELINE.md`.

`install.sql` contains only this approved installation/master data and the required schema and migration ledger. It contains no review Families, Representatives, Students, Family Resources, Institutional Acknowledgement completion data or Enrollments.

## 6.2 Owner-review test data

Owner-review data exists only to exercise the integrated product during Phases 2–4:

- it is fictional and contains no real PII;
- it is created preferably through real product flows or the approved Bulk Import boundary;
- it is not committed with credentials, populated workbooks, exports, uploads or database artifacts;
- it may be retained only inside the local persistent review installation while acceptance is active.

## 6.3 Product demo data

Product demo data is a reusable illustrative dataset shipped with the product. It is not part of the MVP installation baseline or MVP-VALIDATION-001. No demo data is added to `install.sql` or Git.

# 7. Defect Triage

| Category | Meaning | MVP-VALIDATION-001 handling |
|---|---|---|
| A | MVP blocker defect: installation, security, authorization, data integrity or required workflow cannot be accepted | Must be corrected before closure |
| B | Non-blocking MVP defect within an already approved requirement | Normally corrected before closure |
| C | UX or presentation defect, including Spanish, White Label, responsive or accessibility deviation | Normally corrected before closure |
| D | Future enhancement beyond the approved MVP behavior | Recorded outside this milestone |
| E | New business capability, workflow or rule | Requires separate discovery and authorization |

Only A–C normally qualify for correction during this milestone. D–E remain outside unless an already approved MVP requirement is otherwise impossible to satisfy. Validation and closure never invent a new business rule.

# 8. Owner Acceptance Areas

The owner walkthrough validates capabilities rather than duplicating a route inventory. Exact presentation behavior and current reachable screens belong to `16.UI_UX_BASELINE.md`; functional rules remain in their domain and application sources.

| Area | Acceptance focus |
|---|---|
| Authentication | Login, logout, assisted forgot-password guidance, safe feedback and session behavior |
| Dashboard and navigation | Role-appropriate destinations, active state and no exposure of unauthorized capabilities |
| Person | Existing creation, lookup, detail and allowed maintenance |
| Family | Representative/Family creation, Student association and Family context |
| Representative access | User provisioning, password replacement and authorized Portal entry |
| Family Resources | Approved addresses, emergency contacts, pickups, assignments and history |
| Institutional Acknowledgements | AcademicPeriod context, Requirements and Representative completion |
| Enrollment administration | Queue, review, reopen, complete and cancel; Secretaría does not initiate Enrollment |
| Enrollment reports | Approved HTML datasets, filters and CSV downloads |
| Bulk Import | Data-free template, Preview, Apply, bounded results/errors, idempotency and safe cleanup |
| Representative Portal | Family selection, authorized context and access to existing capabilities |
| Enrollment lifecycle | Draft/live-data ownership, annual editing, review, Submission and post-Submission behavior |
| Presentation states | Success, empty, validation, not-found, forbidden, read-only and safe failure states |
| Cross-cutting presentation | Spanish UI, White Label identity, narrow/responsive layouts, keyboard behavior, focus, contrast and no-JavaScript fundamentals |

No standalone Representative or Student administration screen is assumed. Their approved capabilities remain integrated through Person, Family and Representative Portal flows.

# 10. Closure Gates

Formal MVP closure requires all of the following:

1. official documentation is synchronized;
2. the persistent clean local installation is technically accepted;
3. the approved schema, migration ledger and installation baseline remain valid;
4. authentication and access boundaries are accepted;
5. implemented administrator flows are accepted;
6. implemented Representative flows are accepted;
7. Bulk Import is accepted;
8. Enrollment and its lifecycle are accepted;
9. the five approved reports and CSV boundaries are accepted;
10. security, authorization, Family-context revalidation, CSRF and safe-output checks are accepted;
11. Spanish, White Label, responsive and accessibility presentation is accepted;
12. the complete automated regression passes;
13. affected physical validation passes when a correction changes a physical boundary;
14. no Category A, B or C finding remains open;
15. no secret, PII, review workbook/export/upload, SQL artifact or local asset is committed;
16. the owner records explicit acceptance;
17. Current Status, Roadmap and Development Log record formal closure consistently.

Prior physical evidence is reused when unchanged; it must not be represented as a fresh execution. Any new execution records its actual environment and result without credentials.

---

# 11. Closure Authority

Automated PASS results support but do not replace owner acceptance. The owner supplies the final functional and visual verdict and decides whether the persistent review installation remains available after closure.

Until that verdict and every closure gate are recorded, the MVP remains implemented but not formally closed.
