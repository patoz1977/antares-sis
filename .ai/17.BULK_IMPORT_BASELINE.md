# BULK IMPORT BASELINE

**Version:** 1.0
**Status:** Approved functional baseline; implementation not started
**Last Updated:** 2026-08-30

## 1. Purpose

E015 avoids requiring Secretaría to create, one by one, the minimum new records needed at the start of each academic year. It prepares identity, Family membership and Representative access so that Representatives can later enter the Portal, maintain authorized live data and initiate their own Enrollment.

E015 is not a complete SIS migration. This document is the approved functional and design source for Bulk Import; the Domain Model, ADRs, Catalogs, Database Design, ERD and Security Guidelines retain authority over their respective concerns.

## 2. Scope

The baseline can create or recognize a Family, create minimum Representatives and their mandatory Users, associate Representatives with the Family, create minimum Students and associate them directly with the Family. It may add new Representatives or Students to an existing Family during recurrent annual use.

Imported new records use the valid initial statuses required by the existing lifecycles: operational identity, role, Family and Student records use the applicable active GENERAL_STATUS, and the User must be in an access-capable USER_STATUS. Exact spreadsheet representation and default-resolution rules remain Phase 2 design.

## 3. Conceptual XLSX Structure

One XLSX workbook contains exactly three conceptual sheets:

1. `Familias`
2. `Representantes`
3. `Estudiantes`

Final technical sheet and column names are not fixed in Phase 1. Secretaría-facing labels and instructions may be Spanish, while catalog references resolve through stable language-independent codes. Physical database IDs are never part of the Secretaría template.

The minimum baseline resolves Sex, DocumentType and RelationshipType through their existing stable codes and resolves initial GENERAL_STATUS/USER_STATUS through existing codes. Phase 2 determines the exact columns and which values are supplied or safely derived; it creates no new catalog.

## 4. Family Identity

Family has a persistent, institution-unique, stable functional identity named `FamilyCode`. It is independent of and never derived from `DisplayName`. Existing Families are referenced exclusively by FamilyCode; names, Representative or Student data and heuristic matching are not identities.

A new Family also requires its current DisplayName and valid initial Family status. DisplayName remains visible mutable data, not identity. FamilyCode must exist after the Family unit applies successfully, but Phase 1 does not decide whether Secretaría supplies it or the SIS generates it.

A new Family may use `family_ref` solely to correlate rows inside one workbook. This value is not persistent, is not a database column, never substitutes FamilyCode and is never used for persistent deduplication. A successfully created Family must receive a persistent FamilyCode.

The FamilyCode format, physical type and length, generation, migration, unique constraint and compatibility/backfill policy remain intentionally undecided for Phase 2.

## 5. Minimum Representative and User

Each new Representative requires the current minimum consistent state:

- Person: required FirstName and FirstSurname, BirthDate, Sex code, complete DocumentType/DocumentNumber identification, personal email and the valid initial Person status; MiddleName and SecondSurname remain optional and are not part of the minimum;
- Representative: reference to that Person and the valid initial Representative status;
- FamilyRepresentative: Family, RelationshipType code, `isPrimary` and required `startedAt` validity;
- User: the same Person, `LoginIdentifier` derived under the existing normalization from Person.DocumentNumber, the initial password supplied in `Representantes` and processed only by the existing credential policy, and the valid initial account status.

Every Representative created by the SIS must finish creation with an associated User. This restricts Representative creation, not Person generally: a Person may exist without User and Student does not receive User or Portal access. DocumentNumber/LoginIdentifier synchronization and administrative password replacement remain unchanged.

EmploymentInformation, optional phones, MaritalStatus, EducationLevel, addresses and other optional live data are excluded from the minimum and remain maintainable through their existing flows.

## 6. Minimum Student

Each new Student requires:

- Person: required FirstName and FirstSurname, BirthDate, Sex code and the valid initial Person status; MiddleName and SecondSurname remain optional, and Identification remains optional because the current Student Domain does not require it;
- Student: InstitutionalCode, AdmissionDate and the valid initial Student status;
- FamilyStudent: direct Family membership and required `startedAt` validity.

There is no Representative-to-Student relationship. InstitutionalCode is the Student identity used for import recognition; physical IDs are not exposed in the workbook.

## 7. Relationships and Primary Representative

A new Family must contain exactly one imported Representative marked Primary. All Person, Representative, User, Student, FamilyRepresentative and FamilyStudent records required for that Family must form one consistent result.

An existing Family retains its current Primary Representative. E015 may add Representatives and Students but does not replace the Primary or update existing memberships. Marking a new Representative as Primary when it conflicts with the current Primary is a validation conflict.

## 8. Idempotent Create, Not Upsert

E015 is idempotent create only:

- exact reimport does not create duplicates;
- an equivalent existing record may be recognized as already present;
- existing live data is never overwritten or automatically changed to match the workbook;
- an identity match with incompatible data is a conflict visible before apply.

Persistent recognition uses DocumentNumber for Person/Representative where required by current rules, the derived User LoginIdentifier, Student InstitutionalCode and Family FamilyCode. `family_ref` is file-local correlation only; DisplayName and physical IDs are never deduplication identities. Phase 1 does not define the technical comparison algorithm.

## 9. Atomicity

The full workbook is validated before any production write. Apply is atomic per Family, not globally across the workbook.

For a new Family, its Persons, Representatives, Users, Students and memberships either persist consistently or none of that Family unit persists. For an existing Family, the transaction covers only the new records and memberships E015 is attempting to add. Failure of one Family does not roll back independent Families already imported successfully.

## 10. Validation Before Apply

E015 separates three conceptual stages:

1. load;
2. validation and preview;
3. apply.

Before apply, the system must validate workbook structure, expected sheets, required fields, stable catalog codes, Family references, identities, duplicates, conflicts, Primary Representative rules and all current Domain invariants without writing production data. No UI wizard, endpoint, parser or coordinator is designed in Phase 1.

## 11. Exclusions

The baseline excludes EmploymentInformation; Family, Representative and Student addresses; EmergencyContacts; AuthorizedPickups; all other Family Resources and assignments; Enrollment; AcademicPlacement; BillingInformation; MedicalInformation; TransportInformation; IsAuthorizedToLeaveAlone; Institutional Acknowledgements and completions; academic history; payments; historical import; and any update/upsert of existing live information.

E015 does not create Enrollment and does not infer institutional acceptance. Representative continues to initiate Enrollment and complete acknowledgements through the existing Portal. Family Resources remain maintained through the E008/E011 flows.

## 12. Security Requirements

- Only an authorized administrative user may import; mutable operations require CSRF protection.
- The workbook is untrusted input. Its true format, structure and content must be validated with a bounded size before processing; Phase 1 defines no numeric limit.
- Preview, errors and any output must prevent XSS. Generated spreadsheet output, if later approved, must prevent formula injection.
- The initial password is consumed only for User creation through the existing hash and credential policy. It is never stored in plaintext, staging, logs, reports or errors.
- Temporary workbooks must be deleted after processing. The source workbook is sensitive, is not retained as historical evidence and exposes only the minimum personal data required by the baseline.
- Errors disclose no password, secret or unnecessary personal data.

Implementation must also comply with `31.SECURITY_GUIDELINES.md`; Phase 1 does not design upload or temporary-storage infrastructure.

## 13. Open Technical Design Items

Phase 2 must decide, with explicit review, the FamilyCode format, generator, SQL type, length, physical column, unique constraint, migration and existing-data backfill/compatibility policy. It must also evaluate the XLSX library, exact template, catalog columns, file-size limit, parser, temporary-file handling, preview representation, comparison algorithm, error-report format, transaction coordination and any required audit evidence.

Phase 1 authorizes no dependency, import-batch/staging persistence, audit table, endpoint, Controller, Application or Domain service, repository, migration, UI workflow or implementation class.

## 14. Implementation Phases and Status

1. **Phase 1 — Discovery & Scope Baseline:** documented and locally validated; pending review, PR and merge.
2. **Later E015 phases:** pending technical design and separate authorization after Phase 1 merges. Their exact decomposition is intentionally not invented here.

E015 remains in progress. Product implementation, FamilyCode persistence and Representative/User creation coordination have not started.
