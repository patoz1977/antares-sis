# BULK IMPORT BASELINE

**Version:** 2.2
**Status:** Completed and formally validated; Phases 1–7 merged and Phase 8 closure pending integration only
**Last Updated:** 2026-09-03

## 1. Purpose

E015 avoids requiring Secretaría to create, one by one, the minimum new records needed at the start of each academic year. It prepares identity, Family membership and Representative access so that Representatives can later enter the Portal, maintain authorized live data and initiate their own Enrollment.

E015 is not a complete SIS migration. This document is the approved functional and design source for Bulk Import; the Domain Model, ADRs, Catalogs, Database Design, ERD and Security Guidelines retain authority over their respective concerns.

## 2. Scope

The baseline can create or recognize a Family, create minimum Representatives and their mandatory Users, associate Representatives with the Family, create minimum Students and associate them directly with the Family. It may add new Representatives or Students to an existing Family during recurrent annual use.

Imported new records use the valid initial statuses required by the existing lifecycles: operational identity, role, Family and Student records use the applicable active GENERAL_STATUS, and the User must be in an access-capable USER_STATUS. The exact spreadsheet representation and default-resolution rules are defined in sections 15 and 15.4.

## 3. Conceptual XLSX Structure

One XLSX workbook contains exactly three conceptual sheets:

1. `Familias`
2. `Representantes`
3. `Estudiantes`

The exact sheet and column contracts are defined in section 15. Secretaría-facing labels and instructions are Spanish, while headers are lower-snake-case English identifiers and catalog references resolve through stable language-independent codes. Physical database IDs are never part of the Secretaría template.

The minimum baseline resolves Sex, DocumentType and RelationshipType through their existing stable codes. Initial statuses are derived server-side as `GENERAL_STATUS / ACTIVE` and `USER_STATUS / ACTIVE`; no status column or new catalog is introduced.

## 4. Family Identity

Family has a persistent, institution-unique, stable functional identity named `FamilyCode`. It is independent of and never derived from `DisplayName`. Existing Families are referenced exclusively by FamilyCode; names, Representative or Student data and heuristic matching are not identities.

A new Family also requires its current DisplayName and valid initial Family status. DisplayName remains visible mutable data, not identity. Secretaría supplies FamilyCode in E015; other manual channels use the approved SIS generator.

`family_code` is the sole Family reference in all three sheets. Secretaría supplies it for new and existing Families. A nonexistent valid code means NEW; an existing valid code means EXISTING. `family_ref` is not part of E015 and is never accepted or persisted. ADR-0030 replaces only the incompatible `family_ref` portions of ADR-0027 and ADR-0029.

FamilyCode is exactly uppercase `F` plus eight decimal digits, for example `F00000123`. Its Domain, generation, physical schema, migration 011 and backfill are final in section 16.

## 5. Minimum Representative and User

Each new Representative requires the current minimum consistent state:

- Person: required FirstName and FirstSurname, BirthDate, Sex code, complete DocumentType/DocumentNumber identification, personal email and the valid initial Person status; MiddleName and SecondSurname remain optional and are not part of the minimum;
- Representative: reference to that Person and the valid initial Representative status;
- FamilyRepresentative: Family, RelationshipType code, `isPrimary` and required `startedAt` validity;
- User: the same Person, `LoginIdentifier` derived under the existing normalization from Person.DocumentNumber, the initial password supplied in `Representantes` and processed only by the existing credential policy, and the valid initial account status.

Every Representative created by the SIS must finish creation with an associated User. This restricts Representative creation, not Person generally: a Person may exist without User and Student does not receive User or Portal access. DocumentNumber/LoginIdentifier synchronization and administrative password replacement remain unchanged.

EmploymentInformation, optional phones, MaritalStatus, EducationLevel, addresses and other optional live data are excluded from the minimum and remain maintainable through their existing flows.

## 6. Minimum Student

Each new Student requires:

- Person: required FirstName and FirstSurname, BirthDate, Sex code and the valid initial Person status; MiddleName and SecondSurname remain optional, and Identification remains optional because the current Student Domain does not require it;
- Student: InstitutionalCode, AdmissionDate and the valid initial Student status;
- FamilyStudent: direct Family membership and required `startedAt` validity.

There is no Representative-to-Student relationship. InstitutionalCode is the Student identity used for import recognition; physical IDs are not exposed in the workbook.

## 7. Relationships and Primary Representative

A new Family must contain exactly one imported Representative marked Primary. All Person, Representative, User, Student, FamilyRepresentative and FamilyStudent records required for that Family must form one consistent result.

An existing Family retains its current Primary Representative. E015 may add Representatives and Students but does not replace the Primary or update existing memberships. Marking a new Representative as Primary when it conflicts with the current Primary is a validation conflict.

## 8. Idempotent Create, Not Upsert

E015 is idempotent create only:

- exact reimport does not create duplicates;
- an equivalent existing record may be recognized as already present;
- existing live data is never overwritten or automatically changed to match the workbook;
- an identity match with incompatible data is a conflict visible before apply.

Persistent recognition uses DocumentType + normalized DocumentNumber for Person/Representative, the derived User LoginIdentifier, Student InstitutionalCode and FamilyCode. DisplayName and physical IDs are never deduplication identities. Exact matching and equivalence are defined in section 21.

## 9. Atomicity

The full workbook is validated before any production write. Apply is atomic per Family, not globally across the workbook.

For a new Family, its Persons, Representatives, Users, Students and memberships either persist consistently or none of that Family unit persists. For an existing Family, the transaction covers only the new records and memberships E015 is attempting to add. Failure of one Family does not roll back independent Families already imported successfully.

## 10. Validation Before Apply

E015 separates three conceptual stages:

1. load;
2. validation and preview;
3. apply.

Before apply, the system must validate workbook structure, expected sheets, required fields, stable catalog codes, Family references, identities, duplicates, conflicts, Primary Representative rules and all current Domain invariants without writing production data. No UI wizard, endpoint, parser or coordinator is designed in Phase 1.

## 11. Exclusions

The baseline excludes EmploymentInformation; Family, Representative and Student addresses; EmergencyContacts; AuthorizedPickups; all other Family Resources and assignments; Enrollment; AcademicPlacement; BillingInformation; MedicalInformation; TransportInformation; IsAuthorizedToLeaveAlone; Institutional Acknowledgements and completions; academic history; payments; historical import; and any update/upsert of existing live information.

E015 does not create Enrollment and does not infer institutional acceptance. Representative continues to initiate Enrollment and complete acknowledgements through the existing Portal. Family Resources remain maintained through the E008/E011 flows.

## 12. Security Requirements

- Only an authorized administrative user may import; mutable operations require CSRF protection.
- The workbook is untrusted input. Its true format, structure and content must be validated with a bounded size before processing; the concrete Phase 2 limits are defined in section 18.
- Preview, errors and any output must prevent XSS. Generated spreadsheet output, if later approved, must prevent formula injection.
- The initial password is consumed only for User creation through the existing hash and credential policy. It is never stored in plaintext, staging, logs, reports or errors.
- Temporary workbooks must be deleted after processing. The source workbook is sensitive, is not retained as historical evidence and exposes only the minimum personal data required by the baseline.
- Errors disclose no password, secret or unnecessary personal data.

Implementation must also comply with `31.SECURITY_GUIDELINES.md`; Phase 2 freezes the upload and temporary-storage design in sections 18–19 without implementing it.

## 13. Technical Design Closure

Phase 2 closes FamilyCode, XLSX contract/library, resource limits, temporary-file lifecycle, preview/apply integrity, comparison, duplicates, transaction coordination, architecture, errors, template distribution, audit evidence and exact implementation phases in sections 14–28. No implementation decision remains open.

Phase 1 authorizes no dependency, import-batch/staging persistence, audit table, endpoint, Controller, Application or Domain service, repository, migration, UI workflow or implementation class.

## 15. Exact XLSX Contract

The workbook is XLSX only and contains exactly `Familias`, `Representantes` and `Estudiantes`, in any order and with exact case. No extra, hidden or duplicate sheet is accepted. Row 1 is the exact header. Columns are lower-snake-case English identifiers in the exact documented order, with no missing, duplicate, hidden or extra column. There are no physical database IDs.

### 15.1 `Familias`

| Order | Column | Required | Type / limit | Semantics |
|---:|---|---|---|---|
| 1 | `family_code` | yes | text, exact FamilyCode | Sole Family reference. Nonexistent = new; existing = existing. |
| 2 | `display_name` | yes | text, 1–150 chars | New value; for existing Family it must equal the current normalized DisplayName. It is corroboration, never identity or update. |

There is exactly one Family row per FamilyCode. `family_ref` is not accepted anywhere.

### 15.2 `Representantes`

| Order | Column | Required | Type / limit | Semantics |
|---:|---|---|---|---|
| 1 | `family_code` | yes | text, exact FamilyCode | Must have one `Familias` row. |
| 2 | `first_name` | yes | text, 1–100 chars | Person minimum. |
| 3 | `middle_name` | no | text, max 100 chars | Blank becomes null. |
| 4 | `first_surname` | yes | text, 1–100 chars | Person minimum. |
| 5 | `second_surname` | no | text, max 100 chars | Blank becomes null. |
| 6 | `birth_date` | yes | text `YYYY-MM-DD` | Valid non-future UTC calendar date. |
| 7 | `sex_code` | yes | catalog code, max 50 chars | Active Sex code. |
| 8 | `document_type_code` | yes | catalog code, max 50 chars | Active DocumentType code. |
| 9 | `document_number` | yes | text, 1–50 chars | Preserve as text; identity uses DocumentType plus current normalized number. |
| 10 | `email` | yes | text, max 254 chars | Valid personal email required for Representative access. |
| 11 | `relationship_type_code` | yes | catalog code, max 50 chars | Active RelationshipType code. |
| 12 | `is_primary` | yes | `SI` or `NO` | Uppercase after trim. |

### 15.3 `Estudiantes`

| Order | Column | Required | Type / limit | Semantics |
|---:|---|---|---|---|

| 2 | `first_name` | yes | text, 1–100 chars | Person minimum. |
| 3 | `middle_name` | no | text, max 100 chars | Blank becomes null. |
| 4 | `first_surname` | yes | text, 1–100 chars | Person minimum. |
| 5 | `second_surname` | no | text, max 100 chars | Blank becomes null. |
| 6 | `birth_date` | yes | text `YYYY-MM-DD` | Valid non-future UTC calendar date. |
| 7 | `sex_code` | yes | catalog code, max 50 chars | Active Sex code. |
| 8 | `document_type_code` | conditional | catalog code, max 50 chars | Blank only with `document_number`; otherwise active DocumentType. |
| 9 | `document_number` | conditional | text, 1–50 chars | Blank only with `document_type_code`; preserve as text. |

| 11 | `admission_date` | yes | text `YYYY-MM-DD` | Valid non-future UTC calendar date. |
| 12 | `started_at` | yes | text `YYYY-MM-DD` | Membership start day, converted to `00:00:00 UTC`. |

### 15.4 Normalization, catalogs and statuses

- Outer whitespace is trimmed; internal whitespace and case remain unless stated. Required blank is an error; optional blank becomes null.
- Catalog codes receive trim + uppercase and resolve by stable `code`, never ID. Unknown, duplicated or inactive supplied codes fail validation.
- FamilyCode, catalog codes, document numbers, institutional codes and passwords must be string cells. Numeric or boolean cells are rejected to prevent leading-zero or identity corruption.
- Dates are exact ISO text. Numeric Excel serials and formula-produced values are rejected.
- Any formula cell is rejected; cached results are never trusted. Merged header/data cells are rejected.
- Completely blank data rows are ignored while retaining original row numbers. Partially populated rows validate normally. No duplicate row is collapsed.
- Supplied catalogs are Sex, DocumentType and RelationshipType. No catalog is added.
- Statuses are not columns. Application resolves `GENERAL_STATUS / ACTIVE` for new Family, Person, Representative and Student, and `USER_STATUS / ACTIVE` for new User, always by type + code and never hard-coded ID.

## 16. FamilyCode Technical Design

FamilyCode is uppercase `F` plus exactly eight decimal digits (`\AF[0-9]{8}\z`), for example `F00000123`: 9 ASCII characters, trimmed then compared exactly. It is immutable, non-PII, not an authorization secret, institution-unique and independent of DisplayName and technical FamilyId.

Secretaría supplies it in every E015 row. For manual Family creation, an Application `FamilyCodeGenerator` port obtains candidates from an Infrastructure generator using `random_int(0, 99_999_999)` and zero-padding. Delivery never generates a code. The generator attempts at most five candidates; the database UNIQUE is final authority. It uses no `MAX(id)`, sequence table or special lock. Supplied import codes are never regenerated: a concurrent create maps to `CONCURRENT_CHANGE` and requires fresh preview.

The next real migration is `011_add_family_code_to_families.php`. The target delta is:

```sql
`family_code` CHAR(9) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
UNIQUE KEY `uq_families_family_code` (`family_code`)
```

The column follows `id`, has no default and adds no table or FK. Format stays a Domain/Application invariant instead of a dialect-sensitive regex CHECK.

Migration 011 conceptually:

1. adds the column nullable;
2. fails closed if an existing positive FamilyId exceeds `99999999`;
3. backfills `CONCAT('F', LPAD(CAST(id AS CHAR), 8, '0'))`;
4. asserts zero null, malformed or duplicate values;
5. changes it to NOT NULL and adds the UNIQUE key.

The one-time legacy derivation is deterministic, collision-free in the supported range, reproducible on MariaDB 10.4/MySQL 8 and preserves all IDs, FKs and memberships without mutable data or operator mapping. The persisted code then has an independent lifecycle; new codes are not ID-derived. Rollback drops the UNIQUE and column only. Fresh installations run 001–011 and backfill zero rows.

Implementation adds immutable `FamilyCode`, requires it for Family creation/reconstitution, includes it in Family output, and extends `FamilyRepository` only with `findByCode()` and `findByCodeForUpdate()`. `PdoFamilyRepository` persists/selects it. Manual composite creation receives the generator through Application; import passes the validated supplied code. No Domain event is needed.

## 17. XLSX Library Decision

The implemented Phase 5 parser uses `openspout/openspout` with Composer constraint `~4.28.5` and only its XLSX reader. Installed version 4.28.5 supports PHP 8.2, is MIT licensed, streams rows with low memory usage, handles shared strings and typed cells, and requires standard PHP extensions (`dom`, `fileinfo`, `filter`, `libxml`, `xmlreader`, `zip`) without extra Composer packages. The 4.28 patch line is pinned because later 4.x minors dropped PHP 8.2; upgrades require compatibility and advisory review.

PhpSpreadsheet 5.x was evaluated as the mature broad alternative. It supports PHP 8.2 and rich workbook/date/formula behavior but creates an in-memory model, requires more extensions/transitive packages and exposes features E015 does not need. OpenSpout is proportionate to three bounded row-oriented sheets. Phase 5 adds the dependency and its advisory review; Phase 2 changed neither Composer file.

Infrastructure instantiates the XLSX reader directly against a verified local path. It does not auto-detect by extension, evaluate formulas, follow external links, open stream wrappers or parse CSV, ODS or XLS.

## 18. File Security and Resource Limits

These MVP technical constants live in code, not institutional `.env` settings:

- upload: at most 5 MiB;
- sheets: exactly 3;
- data rows: `Familias` 1,000, `Representantes` 2,000, `Estudiantes` 3,000;
- total data rows: at most 5,000;
- columns: exact contract, global maximum 14;
- cell text: at most 1,000 Unicode characters and 4,000 bytes before field validation;
- ZIP entries: at most 100;
- declared uncompressed ZIP total: at most 25 MiB;
- one ZIP entry: at most 10 MiB;
- compressed-to-uncompressed ratio: at most 100:1 per entry and overall.

Delivery verifies upload success and bytes. Infrastructure verifies a regular local file, ZIP signature/container, safe entry names, no traversal or encrypted entry, declared/observed limits, required OOXML content types/relationships/workbook parts and absence of macros, embedded objects, external links or executable content. `.xlsx` and MIME are supporting checks only. XML parsing disables network/entity expansion. Invalid ZIP metadata, parsing or limit overflow fails closed.

## 19. Temporary File and Preview/Apply Integrity

Uploads move to an application-owned temporary directory outside `public`, under a cryptographically random server name and process-only permissions. The user filename is display metadata only and never a path.

Preview and Apply are separate requests:

1. Preview keeps the upload only for the request, validates it, hashes the exact bytes with SHA-256, builds a password-free preview and deletes the file in `finally` before responding.
2. Session stores only a random one-use token bound to actor/User, digest, issue/expiry time and safe counts. It stores no workbook, row payload, PII, FamilyCode list or password. Lifetime is 15 minutes.
3. Apply requires the same bytes reuploaded, the opaque token and valid CSRF. It verifies the digest, reparses and completely revalidates current database state before writes.
4. Digest, actor/session, expiry, reuse or token failure requires a new preview.
5. Apply deletes its file in `finally`, consumes the token regardless of result and clears plaintext password references after each Family command.

This avoids browser authority and persistent plaintext while remaining server-rendered. It introduces no Redis, queue or object storage.

The plaintext password path is strictly `XLSX temp file → OpenSpout string → in-memory canonical command → current credential policy → PasswordHasher → User hash`. It is not trimmed silently, serialized, stored in session, preview, error, log, CSV or table, nor returned. Temporary files are deleted after success, validation failure and exception.

## 20. Classification

Every canonical row is NEW, ALREADY_EXISTS or CONFLICT. Preview never writes and no fuzzy matching exists.

## 21. Matching and Equivalence

### 21.1 Family

- Exact normalized FamilyCode is identity.
- Nonexistent code is NEW. Existing ACTIVE Family requires exact trimmed, case-sensitive DisplayName corroboration; equality is ALREADY_EXISTS and difference is `EXISTING_DATA_CONFLICT` without update.
- INACTIVE Family is a conflict because E015 cannot reactivate it.

### 21.2 Person, Representative and User

- Person identity is complete DocumentType + database-normalized DocumentNumber; number alone across types is insufficient.
- Existing Person identity is the document pair. Sex is the creation-critical corroborating fact retained by current Representative/Student self-service flows and must match. Names, BirthDate and personal email are mutable live data: differences neither update nor conflict, and preview states current SIS values are retained.
- Creating a missing Representative role requires ACTIVE Person with valid current personal email. INACTIVE Representative conflicts; E015 never activates it.
- A missing User for a valid Representative may be created. Existing User equivalence requires the same Person and current derived normalized LoginIdentifier. Login owned by another Person, divergent User identity or non-access-capable User status conflicts.
- `initial_password` is validated/used only for User creation. Existing hash is never compared or replaced.
- Existing active FamilyRepresentative is equivalent only when Family, RelationshipType, Primary marker and exact UTC `started_at` match. New membership may be created; no existing membership is edited or ended.

### 21.3 Student and Person

- Student identity is InstitutionalCode under current trim/case-preserving Domain rules; names never identify.
- Existing Student Person must match any complete supplied Identification and Sex. Names, BirthDate and AdmissionDate are mutable live data and remain untouched without conflict solely for differing workbook values.
- If Student is absent and complete Identification resolves Person, reuse is allowed only with matching Sex and absent/equivalent Student role. Without Identification, Person is never reused by name/birth date.
- INACTIVE Person or Student conflicts.
- Active membership in target Family is equivalent only with equal `started_at`; active membership elsewhere conflicts and is never transferred. Ended history permits a new valid membership.

### 21.4 Multi-role Person

Person may hold Representative and Student roles. Reuse requires complete approved Identification plus matching Sex and unique role-specific identity. No reuse is inferred for a Student with blank Identification.

## 22. Intra-workbook Duplicates and Primary

- Duplicate FamilyCode row always conflicts, even if textually equal.
- Representative identity may occur in different Families, but its Person/User creation payload must be identical and each Family membership pair unique. Same-Family repetition conflicts.
- Conflicting payload or password for one new Representative conflicts without echoing password details.
- Student InstitutionalCode occurs once only; repetition in same/another Family conflicts because Student has at most one active Family.
- Complete Identification reused for different intended Persons, or one derived login for different Persons, is an identity conflict.
- Every new Family has exactly one `SI` Primary. Existing Family accepts imported `SI` only as exact corroboration of its current active Primary membership; a new/replacement Primary conflicts.

## 23. Transactions and Concurrency

After complete validation, Family units apply sequentially by ascending FamilyCode. Each uses one outer `TransactionRunner` transaction; subordinate operations expose transaction-aware composition and never open nested transactions.

Within the transaction Application re-resolves statuses/catalogs, locks existing Family by code, then locks/revalidates Person identities in canonical DocumentType/normalized-number order, followed deterministically by Representative, User/login, Student institutional identities and memberships. It creates only missing records in dependency order: Family, Person, Representative, User, Student, then memberships, and reconstitutes the committed result.

Preview is advisory. Apply repeats all lookups/invariants under transaction. UNIQUE/FK/generated-key races map to safe `CONCURRENT_CHANGE` or the specific conflict without database text. Deadlock/lock timeout rolls back that Family, is not retried automatically and requires fresh preview. One Family failure does not roll back earlier independent successful Families.

`CreateRepresentativeAccess` is the implemented authority that coordinates Person + Representative + User for manual and future bulk creation. `CreateRepresentativeFamily` delegates to it within the single outer transaction; Bulk Import must reuse it and never duplicate Representative creation. Hashing remains delegated to `CreateRepresentativeUser` after the relevant validation and before User persistence.

## 24. Architecture and Persistence Boundaries

E015 is a transversal Application capability, not a new giant bounded context.

- **Delivery:** administrative authorization, upload/CSRF/PRG, safe Spanish rendering, reupload and response headers. No matching, XLSX parsing, SQL or Domain rule.
- **Application:** canonical commands, complete validation, preview classification, per-Family apply, Representative/User and Student reuse/create coordination, transaction boundary and safe errors.
- **Domain:** FamilyCode plus existing Aggregate/Value Object invariants.
- **Infrastructure:** OpenSpout adapter, ZIP guard, temporary-file adapter, CSPRNG FamilyCode generator, PDO repository extensions and operational logger.

The Application surface is intentionally small and explicit:

- `BulkImportWorkbookReader` port returns typed raw sheets/cells and parser diagnostics; its OpenSpout adapter contains no business rule.
- `PreviewBulkImport` performs normalization, catalogs, cross-sheet validation, database matching and password-free preview classification without writes.
- `ApplyBulkImport` verifies the approved digest context, rebuilds the same canonical model and coordinates one transaction per Family.
- `FamilyCodeGenerator` serves non-import Family creation only.
- implemented `CreateRepresentativeAccess` owns Person + Representative + User creation; the manual channel already reuses it and the future bulk channel must do the same;
- one Student reuse/create coordinator composes existing Person/Student/Family contracts without becoming a second Student Domain implementation.

Names may align mechanically with existing namespace conventions during implementation, but these responsibilities may not be collapsed into a Controller/parser God Service or duplicated across manual/import flows.

Required repository changes are limited to FamilyCode persistence/lookups and proven lock-aware gaps. Existing Person identification, Representative-by-Person, Student-by-InstitutionalCode, User-by-Person/login and membership contracts are reused. No Controller/parser ad hoc SQL or universal import repository is allowed.

There are no `import_batches`, `import_rows`, identity mappings, persistent staging or workbook history:

`No persistent import staging or import-history tables in E015 MVP.`

Only `families.family_code` and its UNIQUE key change schema.

## 25. Errors, Preview and Report

Stable conceptual categories are `FILE_INVALID`, `STRUCTURE_INVALID`, `REQUIRED_VALUE_MISSING`, `VALUE_INVALID`, `CATALOG_UNKNOWN`, `FAMILY_REFERENCE_INVALID`, `DUPLICATE_IN_WORKBOOK`, `IDENTITY_CONFLICT`, `FAMILY_MEMBERSHIP_CONFLICT`, `PRIMARY_REPRESENTATIVE_CONFLICT`, `EXISTING_DATA_CONFLICT`, `CONCURRENT_CHANGE` and `APPLY_FAILED`.

Each error has category, sheet, original one-based row, field when applicable and safe Spanish message. It never has exception/SQL/path/secret or unnecessary PII.

Preview shows safe counts and a bounded table with FamilyCode, DisplayName, person display name, masked DocumentNumber (last four only), InstitutionalCode when applicable, classification and safe message. It omits email, birth date, password, password metadata, hash, physical ID and browser authority; output is escaped.

MVP provides summary + bounded HTML table and optional downloadable UTF-8 CSV of the same safe errors, not error XLSX. CSV columns are `category,sheet,row,field,message`; values starting `=`, `+`, `-` or `@` are neutralized against formula injection. No password or original row payload is exported.

## 26. Delivery and Template

The implemented no-JavaScript server-rendered flow is: authorized import/template page; CSRF Preview upload; password-free preview; CSRF Apply with the same file reuploaded and opaque token; PRG result per Family. The exact 4 GET and 2 POST routes follow existing administrative conventions. AuthenticationMiddleware and the current exact admin gate remain mandatory; navigation never grants authority.

The template is the static, versioned, data-free XLSX at `resources/templates/bulk-import/e015-family-import-v1.xlsx`. It contains only the three exact contract sheets and header rows, with no data rows, formulas, hidden content, PII, password, institution identity, current catalog ID or secret. Phase 7 serves it through a safe application download response and presents adjacent Spanish instructions, including the accepted catalog codes; dynamic generation adds no MVP value.

## 27. PII and Audit Evidence

E015 adds no audit table. Existing operational logging may record actor/User ID, UTC timestamp, correlation ID, safe counts, result and affected FamilyCodes. It omits workbook filename/hash, names, documents, institutional codes, emails, dates and passwords. Full workbook history is prohibited.
