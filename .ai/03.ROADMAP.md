# ROADMAP

## Purpose

This document defines the official future planning of the project.

It contains only planned work and future milestones. Current state belongs to `02.CURRENT_STATUS.md`; completed history belongs to `04.DEVELOPMENT_LOG.md`.

---

# Planning Principles

The roadmap represents the agreed direction of the project. It organizes future work without using planning sections as a status report or historical log.

---

# Current Planning Baseline

The Enrollment Domain Discovery and its documentation reconstruction are complete. Technical approval remains the gate for future implementation.

No new business functionality is planned for execution until Architecture, Domain Model, Database Design, ERD, Catalogs and Decisions pass the final consistency review.

# Current Planned Milestone

## E003.4A — Enrollment Domain Documentation Review

### Objective

Approve the reconstructed Enrollment documentation as the stable basis for implementation.

### Remaining Scope

- Review the official Domain Model against the closed Discovery.
- Verify every physical table and constraint against the domain invariants.
- Verify the ERD against DATABASE_DESIGN.
- Resolve review observations without reintroducing obsolete concepts.
- Record explicit technical approval or any new blocking decision.

### Exit Criteria

- no unresolved business or physical-design contradiction;
- Database Design and ERD remain exactly aligned;
- permanent decisions are traceable through ADR;
- technical review is explicitly approved;
- the next implementation milestone is defined before code changes begin.

---

# Development Workflow

Every future milestone shall follow the same lifecycle:

1. Business analysis.
2. Domain validation.
3. Technical design.
4. Implementation.
5. Testing.
6. Technical review.
7. Documentation update.
8. Commit.
9. Repository synchronization.

No milestone is complete until implementation and documentation are synchronized.

---

# Scope Management

During a milestone:

- no future functionality is incorporated;
- architectural changes require documented justification;
- undefined rules are not implemented;
- permanent project knowledge is recorded in the repository;
- database execution requires explicit authorization.

---

# Architectural Governance

- GitHub is the single source of truth.
- `.ai` contains the official project documentation.
- Approved architecture and domain decisions precede implementation.
- Business rules drive technical design.
- Long-term maintainability has priority over short-term speed.
- Compatibility is preserved whenever reasonably possible.

# Quality Criteria

A planned milestone may be marked complete only when:

- its approved objective is achieved;
- required validation and tests pass;
- documentation is synchronized;
- architectural consistency is verified;
- repository changes are reviewed and confirmed.
