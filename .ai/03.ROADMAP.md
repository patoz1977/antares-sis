# Current Functional Milestone

## E006 — Representative & Student Baseline

**Status:** In progress — Phase 4 Persistence implemented; technical review, MariaDB validation and merge pending

### Objective

Implement the stable institutional Representative and Student roles over Person, including Domain, Persistence, Application and the minimal White Label web delivery required by the current administrator.

### Functional Scope

**Representative**

- references one existing Person;
- owns optional EmploymentInformation: occupation, company, position, work phone and work email;
- uses ACTIVE or INACTIVE;
- supports create, query and update operations.

**Student**

- references one existing Person;
- owns institutional code and admission date;
- uses ACTIVE or INACTIVE;
- supports create, query and update operations.

### Invariants

- One Person has at most one Representative and at most one Student independently.
- Neither role duplicates personal data owned by Person.
- Deactivating a role does not deactivate or delete Person.
- Student has no User in the MVP.
- Grade and Section belong to Enrollment, not Student.
- Neither role exists without an existing Person.

### General Exclusions

- Family, FamilyRepresentative and FamilyStudent.
- Association between Representative and Student.
- User creation for Representative.
- Bulk import and the Representative Portal.
- Enrollment, Grade or Section implementation.
- Addresses, emergency contacts and authorized pickups.
- Reports and definitive Secretaría, DECE or Enfermería roles.
- Physical deletion, new Catalogs and schema changes not required by the approved baseline.
- Institution-specific rules, generic administration infrastructure and TEST-001 work.

### Approved Phases

1. **Documentation alignment and milestone baseline — completed and merged** — E006 scope, exclusions and phases are established.
2. **Representative Domain — completed and merged** — Aggregate, identity, EmploymentInformation, GENERAL_STATUS lifecycle, invariants and unit tests are implemented.
3. **Student Domain — completed and merged** — Aggregate, identity, InstitutionalCode, AdmissionDate, GENERAL_STATUS lifecycle, invariants and unit tests are implemented.
4. **Persistence — implemented; review, MariaDB validation and merge pending** — minimal contracts and PDO repositories cover both roles with database-enforced uniqueness and local plus disposable MariaDB coverage.
5. **Application — planned** — add minimal create, query and update use cases, DTOs and errors for both roles without coordinating Family or User.
6. **Administrator delivery — planned** — add White Label routes, controller and forms, temporarily restricted to authenticated `admin`, with selection of an existing Person and no generic administration panel.
7. **Validation and closure — planned** — complete local and disposable MariaDB 10.4 validation, synchronize documentation and close E006.

### Immediate Action

Run the Phase 4 disposable XAMPP MariaDB validation, complete technical review and merge, then authorize Phase 5 — Application.

E006 is not complete until all seven phases pass their applicable analysis, implementation, validation and documentation gates.

# Development Workflow

Every future milestone shall follow the same lifecycle:

1. Business analysis.
2. Domain validation.
3. Technical design.
4. Implementation.
5. Testing.
6. Technical review.
7. Documentation update.
8. Commit.
9. Repository synchronization.

No milestone is complete until implementation and documentation are synchronized.

---

# Scope Management

During a milestone:

- no future functionality is incorporated;
- architectural changes require documented justification;
- undefined rules are not implemented;
- permanent project knowledge is recorded in the repository;
- database execution requires explicit authorization.

---

# Architectural Governance

- GitHub is the single source of truth.
- `.ai` contains the official project documentation.
- Approved architecture and domain decisions precede implementation.
- `DATABASE_DESIGN.md` governs the resulting physical schema.
- Business rules drive technical design.
- Long-term maintainability has priority over short-term speed.
- Compatibility is preserved whenever reasonably possible, subject to the pre-production boundary established by ADR-0018.
