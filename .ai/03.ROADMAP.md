# ROADMAP

## Purpose

This document defines the official future planning of the project.

It contains only planned work and future milestones.

It intentionally excludes:

- current implementation status (see `02.CURRENT_STATUS.md`);
- historical development information (see `04.DEVELOPMENT_LOG.md`).

---

# Planning Principles

The roadmap represents the agreed direction of the project.

Its purpose is to organize future work without documenting completed activities beyond the level necessary to establish dependencies between milestones.

The roadmap evolves as business priorities evolve.

---

# Current Planning Baseline

The current planning assumes that implementation will resume only after the Enrollment Domain has been formally consolidated.

Until that milestone is completed, no new business functionality should be implemented.

---

# Development Workflow

Every future milestone shall follow the same lifecycle:

1. Business analysis.
2. Domain validation.
3. Technical design.
4. Implementation.
5. Testing.
6. Technical review.
7. Documentation update.
8. Commit.
9. Repository synchronization.

No milestone is considered complete until both implementation and documentation are synchronized.

---

# Scope Management

During the execution of a milestone:

- no functionality from future milestones shall be incorporated;
- architectural changes shall only be introduced when technically justified;
- business rules shall not be implemented until formally defined;
- permanent project knowledge shall be incorporated into the repository documentation.

---

# Architectural Governance

The following principles govern the evolution of the project:

- GitHub is the single source of truth.
- The `.ai` directory contains the official project documentation.
- The documented architecture takes precedence over implementation.
- Business rules drive technical implementation.
- Long-term maintainability has priority over short-term speed.
- Backward compatibility should be preserved whenever reasonably possible.

---

# Documentation Synchronization

Whenever a milestone changes state, the following documents shall be reviewed for consistency:

- `02.CURRENT_STATUS.md`
- `03.ROADMAP.md`
- `04.DEVELOPMENT_LOG.md`

Additional documentation shall be updated whenever affected, including:

- ARCHITECTURE
- DOMAIN_MODEL
- DATABASE_DESIGN
- ERD
- CATALOGS
- DECISIONS
- SECURITY_GUIDELINES

Documentation is considered part of every deliverable.

---

# Quality Criteria

A planned milestone may be marked as completed only when:

- its business objective has been achieved;
- implementation has been technically validated;
- required tests have passed;
- documentation has been synchronized;
- architectural consistency has been verified;
- the corresponding commit has been completed.

---

# Roadmap Evolution

This roadmap shall only be modified when one of the following occurs:

- a milestone changes state;
- a new milestone is officially approved;
- an existing milestone is removed;
- project priorities change;
- architectural planning changes.

Normal implementation work shall not modify this roadmap.
