# Planning Principles

The roadmap represents the agreed direction of the project. It organizes future work without using planning sections as a status report or historical log.

E003.4A completed formal technical review. Architecture, Domain Model, Decisions, Catalogs, Database Design and ERD are the technically approved Enrollment baseline.

E004.1 — Identity & Access Baseline is completed and merged into `main` through PR #3.

# Current Functional Milestone

## E005 — Person Baseline

**Status:** In progress — Phase 1

### Objective

Establish Person as the coherent identity baseline for subsequent Enrollment implementation, align the executable system with the approved official documentation, and replace incompatible legacy structures through the pre-production rebaseline policy defined by ADR-0018.

### General Exclusions

- New Enrollment functionality beyond the Person baseline.
- Institution-specific business rules not present in the approved documentation.
- Destructive execution against production or any institutional database containing real data.
- Preservation, backup, backfill or migration of the current disposable pre-production data.
- TEST-001 infrastructure work.

### Approved Phases

1. **Documentation alignment and pre-production strategy** — synchronize status and planning and approve the rebaseline boundary.
2. **Technical cleanup and schema rebaseline** — preserve only compatible, reusable components; incompatible migrations may be removed from the active executable sequence under ADR-0018.
3. **Person Domain** — implement the approved Person domain model and invariants.
4. **Person Application** — implement Person use cases and orchestration.
5. **Person Persistence** — implement repositories and mappings for the approved schema.
6. **Person HTTP and previous-flow replacement** — expose the Person use cases and replace the superseded flow.
7. **Validation and closure** — validate the clean installation, behavior, documentation and milestone completion.

E005 is not complete until all seven phases pass their applicable analysis, implementation, validation and documentation gates.

# Independent Technical Milestone

## TEST-001 — MariaDB Integration Test Infrastructure

**Status:** Planned

### Objective

Provide an isolated, reproducible and disposable MariaDB 10.4 environment for safely exercising migrations, concurrency, UTC behavior, seeders, preflight checks, repeated execution and cleanup while preventing accidental use of institutional or production databases.

TEST-001 is technical test infrastructure. It remains independent from E005 and does not authorize migration execution against persistent databases.

# Development Workflow

Every future milestone shall follow the same lifecycle:

1. Business analysis.
2. Domain validation.
3. Technical design.
4. Implementation.
5. Testing.
6. Technical review.
7. Documentation update.
8. Commit.
9. Repository synchronization.

No milestone is complete until implementation and documentation are synchronized.

---

# Scope Management

During a milestone:

- no future functionality is incorporated;
- architectural changes require documented justification;
- undefined rules are not implemented;
- permanent project knowledge is recorded in the repository;
- database execution requires explicit authorization.

---

# Architectural Governance

- GitHub is the single source of truth.
- `.ai` contains the official project documentation.
- Approved architecture and domain decisions precede implementation.
- `DATABASE_DESIGN.md` governs the resulting physical schema.
- Business rules drive technical design.
- Long-term maintainability has priority over short-term speed.
- Compatibility is preserved whenever reasonably possible, subject to the pre-production boundary established by ADR-0018.

# Quality Criteria

A planned milestone may be marked complete only when:

- its approved objective is achieved;
- required validation and tests pass;
- documentation is synchronized;
- architectural consistency is verified;
- repository changes are reviewed and confirmed.
