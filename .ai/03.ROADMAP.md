# Completed Functional Milestone

## E006 — Representative & Student Baseline

**Status:** Completed

### Objective

Implement the stable institutional Representative and Student roles over Person, including Domain, Persistence, Application and the minimal White Label web delivery required by the current administrator.

### Functional Scope

**Representative**

- references one existing Person;
- owns optional EmploymentInformation: occupation, company, position, work phone and work email;
- uses ACTIVE or INACTIVE;
- supports create, query and update operations.

**Student**

- references one existing Person;
- owns institutional code and admission date;
- uses ACTIVE or INACTIVE;
- supports create, query and update operations.

### Invariants

- One Person has at most one Representative and at most one Student independently.
- Neither role duplicates personal data owned by Person.
- Deactivating a role does not deactivate or delete Person.
- Student has no User in the MVP.
- Grade and Section belong to Enrollment, not Student.
- Neither role exists without an existing Person.

### General Exclusions

- Family Membership implementation inside E006; its required baseline is governed separately by E006.5.
- Association between Representative and Student.
- User creation for Representative.
- Bulk import and the Representative Portal.
- Enrollment, Grade or Section implementation.
- Addresses, emergency contacts and authorized pickups.
- Reports and definitive Secretaría, DECE or Enfermería roles.
- Physical deletion, new Catalogs and schema changes not required by the approved baseline.
- Institution-specific rules, generic administration infrastructure and TEST-001 work.

### Approved Phases

1. **Documentation alignment and milestone baseline — completed and merged** — E006 scope, exclusions and phases are established.
2. **Representative Domain — completed and merged** — Aggregate, identity, EmploymentInformation, GENERAL_STATUS lifecycle, invariants and unit tests are implemented.
3. **Student Domain — completed and merged** — Aggregate, identity, InstitutionalCode, AdmissionDate, GENERAL_STATUS lifecycle, invariants and unit tests are implemented.
4. **Persistence — completed, MariaDB validated and merged** — minimal contracts and PDO repositories cover both roles with database-enforced uniqueness and local plus disposable MariaDB coverage.
5. **Application — completed and merged** — minimal create, query and update use cases, typed DTOs and specific errors cover both roles without coordinating Family or User.
6. **Administrator delivery — completed through E006.5** — the White Label routes, controller and composite forms are temporarily restricted to authenticated `admin`, reuse the approved Family Membership flow and add no generic administration panel. The implementation and its MariaDB 10.4 validation were merged through PR #20.
7. **Validation and closure — completed** — the final integrated audit approved Domain, Persistence, Application, orchestration, Delivery, wiring, security, White Label, schema parity, exclusions and the complete local suite.

### Immediate Action

E006 has no remaining functional phase in its approved scope. E007 — Representative Access Baseline follows as the current functional milestone.

# Completed Intermediate Technical-Functional Milestone

## E006.5 — Family Membership Baseline

**Status:** Completed

### Objective

Implement only the minimum Family Membership core required for the administrative flow to create one Family and associate Representative and Student correctly before E006 Administrator Delivery.

E006.5 was inserted after the merged E006 Phase 5 to establish the membership prerequisite and deliver the approved administrator flow through Phase 6. Its integrated validation and closure also completed the remaining E006 gates.

### Conceptual Correction

Representative and Student do not have a direct association. Family is the administrative grouping unit, and membership follows this approved model:

```text
Representative
→ FamilyRepresentative
→ Family
→ FamilyStudent
→ Student
```

Representative relates to Family through FamilyRepresentative. Student relates to Family through FamilyStudent. No direct RepresentativeStudent table, Aggregate or use case shall be created.

A new Family is valid only when created atomically with its first active primary FamilyRepresentative. No empty, draft or pending Family state is part of the approved model.

### Target Administrative Flow

**Create a new representative**

```text
Create representative
→ Create Person
→ Create Representative
→ Create Family
→ Create active primary FamilyRepresentative
```

The implemented administrator experience presents this coordination as one visible form, while Application coordinates the Aggregates internally.

**Add a student to the Family**

```text
Add student
→ Create Person
→ Create Student
→ Create active FamilyStudent
```

The Student becomes a member of Family, not directly associated with Representative. This flow starts from Family detail or the primary representative context.

**Add another representative later**

```text
Add representative
→ Create or select Person
→ Create or select Representative
→ Create FamilyRepresentative
```

This compatible future behavior is documented but is not implemented during Phase 1.

### Family Membership Invariants

**Family**

- has FamilyId, DisplayName and status;
- retains at least one active representative;
- groups one or more representatives and students;
- prevents members and resources from crossing Family boundaries.

**FamilyRepresentative**

- references Family and Representative;
- requires RelationshipTypeId from the existing approved catalog;
- contains IsPrimary;
- keeps an active Family and Representative relation unique;
- permits only one active primary representative per Family;
- can be ended without deleting Representative or Person;
- allows one Representative to belong to multiple active Family records.

**FamilyStudent**

- references Family and Student;
- permits one active Family for each Student;
- preserves previous membership history;
- treats a Family change as an administrative operation;
- can be ended without deleting Student or Person.

### Planned Phases

1. **Documentation alignment — completed and merged** — scope, flow, invariants, exclusions and the atomic Family creation decision are established through PR #15.
2. **Family Membership Domain — completed and merged** — Family, its membership Entities, typed Value Objects, temporal behavior and approved internal invariants were merged through PR #16.
3. **Family Membership Persistence — completed, MariaDB validated and merged** — the minimal contract and PDO repository persist the complete Aggregate through `families`, `family_representatives` and `family_students`. The 26 SQLite persistence tests and physical MariaDB 10.4 validation approved atomic creation, database-managed AUTO_INCREMENT identities, complete reconstruction, Representative and Student lookups, membership history, active uniqueness, UTC timestamps, exact GENERAL_STATUS mapping and transactional rollback. Disposable partial-creation and final cleanup were confirmed with no temporary database remaining, and PR #17 merged the phase.
4. **Family Membership Application — completed and merged** — seven focused use cases create, query, add and end memberships through Domain contracts. Immutable DTOs expose complete active and historical membership state; specific errors cover missing external entities, RelationshipType and invalid persisted identities. Representative, Student and RelationshipType existence are prevalidated, a Student cannot have more than one active Family, dates are explicit, and Application owns no transaction or infrastructure concern. PR #18 merged the phase.
5. **Composite administrative orchestration — completed, validated and merged** — `TransactionRunner` and `PdoTransactionRunner` provide one outer shared-PDO transaction per operation. CreateRepresentativeFamily coordinates Person → Representative → Family with its primary membership, while CreateStudentInFamily validates an existing Family before coordinating Person → Student → FamilyStudent. Local and MariaDB 10.4 validation approved complete physical commits, total rollback, unchanged error propagation, preservation of the existing Family and disposable cleanup; PR #19 merged the phase.
6. **Administrator Delivery integration — completed, MariaDB validated and merged** — exactly six protected White Label Family routes expose entry/detail, one composite Representative/Family form and one composite Student form. FamilyController invokes only the approved orchestrators, the temporary gate accepts only authenticated `admin`, POSTs use CSRF, strict HTTP validation and safe known-error mapping, and Student Family authority is bound to session. The 302 local tests and three HTTP/session scenarios pass. MariaDB 10.4 physically approved PdoRelationshipTypeLookup, PdoFamilyFormOptionsProvider, active-only RelationshipTypes, exact ACTIVE/INACTIVE FamilyStatus values, complete commits and deliberate rollbacks for both composite flows, UTC safeguards and partial/final disposable cleanup. No `antares_e0065_delivery_tmp%` database remained, production required no correction and PR #20 merged the phase.
7. **Validation and closure — completed** — the final audit against updated `main` confirmed all PR #10–#20 merges, architectural and functional coherence, 183 optimized autoload classes, 302 local tests with 0 failures, three passing HTTP/session scenarios, complete PHP lint, security, White Label, physical-model parity and preserved exclusions. The previously approved Phase 6 MariaDB 10.4 evidence remains valid; no additional closure run was made because the disposable `E0041_DB_*` environment was unavailable.

### Immediate Action

E006 and E006.5 have no remaining approved phase. E007 — Representative Access Baseline follows as the current functional milestone.

# Current Functional Milestone

## E007 — Representative Access Baseline

**Status:** In progress — Phase 1 Documentation and Functional Alignment current; Phases 2–7 planned

### Objective

Establish the secure Representative access boundary required before the Representative Portal: provision and maintain a Representative User, synchronize its document-based login with Person Identification, resolve the Representative role and authorize an effective Family context on the server.

### Authorized Access Chain

```text
User
→ Person
→ Representative
→ active FamilyRepresentative
→ authorized Family
```

User must be enabled under Identity & Access. Person must resolve the Representative role, and Representative must have an active membership in the effective Family. A Family selected by the client never authorizes by itself. One active Family permits direct entry; multiple active Families require selection from the authorized set and later changes only within that set.

### Approved Functional Decisions

- UserId is the stable technical User identity, independent from personal identification and never used as the visible username.
- User belongs to exactly one Person; Person may exist without User, but User cannot exist without Person.
- For Representative User, LoginIdentifier equals the current Person DocumentNumber. UserId, email and aliases are not alternative login identifiers.
- A Person with Representative User must retain complete Identification.
- Updating DocumentNumber synchronizes Person and User atomically while preserving UserId, PersonId, PasswordHash, UserStatus, failed-login state and relationships.
- LoginIdentifier remains globally unique in the institutional database; Application prevalidation complements the physical UNIQUE concurrency guarantee.
- Cross-Aggregate coordination belongs to Application and one TransactionRunner boundary. It is not Controller logic, SQL ad hoc or a Person persistence side effect.
- Secretaría provisions the User for an existing Representative only after validating Person, role ownership, complete Identification, absence of another User for Person and login availability.
- Secretaría supplies the initial password and may replace it administratively without the old password. The minimum is five characters; letters and/or numbers are allowed without mandatory mixture, uppercase or symbol.
- Only PasswordHash is persisted. The SIS does not email, log, report, export or retain readable credentials, and does not require first-login activation or password change.
- Student has no User and no Portal in the MVP.
- Representative Forgot Password is planned, but its mechanism is intentionally unresolved until Phase 6.

### Phase 2 Planned Scope

Without prescribing implementation names before Phase 2 review, the planned scope covers:

- explicit User Domain creation/reconstitution and changes to LoginIdentifier and PasswordHash;
- UserRepository lookup by LoginIdentifier and PersonId plus persistence of new and authorized changed Users;
- PdoUserRepository INSERT and UPDATE support;
- administrative Representative User provisioning, duplicate-User prevention and document-derived login;
- password hashing and administrative password replacement;
- atomic Identification/LoginIdentifier synchronization and prevention of Identification removal while a Representative User exists;
- understandable duplicate handling with physical UNIQUE as the final concurrency guarantee;
- one TransactionRunner boundary for cross-Aggregate writes;
- Domain, Application, Persistence and disposable MariaDB coverage;
- minimal administrative Delivery only if Phase 2 review confirms it belongs there.

### Phases

1. **Documentation and Functional Alignment — current** — synchronize permanent Representative User identity, credential, login and access decisions before implementation.
2. **Representative User Provisioning & Administrative Credential Management — planned** — implement the approved User lifecycle extensions, provisioning, administrative password management and atomic Person/User synchronization.
3. **Representative Access Resolution — planned** — resolve authenticated User through Person to Representative.
4. **Family Context Authorization — planned** — authorize active Family memberships and effective Family context exclusively on the server.
5. **Representative Portal Entry — planned** — expose the minimum protected Representative entry boundary.
6. **Forgot Password — planned** — discover and implement only a separately approved recovery mechanism.
7. **Validation and Closure — planned** — validate the integrated E007 baseline and synchronize final status.

### Exclusions

- User and Portal for Student;
- FamilyAddress, address assignments, Emergency Contacts and Authorized Pickups;
- Enrollment, Institutional Documents, Document Acceptance, Submission and Submission Snapshot;
- BillingInformation, MedicalInformation, Transportation and AcademicPlacement;
- Grade or Section administration, enrollment autosave, import, reports and payments;
- definitive Secretaría, DECE or Enfermería roles and generic RBAC;
- TEST-001 and direct RepresentativeStudent association;
- credential reports, exports or readable password storage;
- any inferred Forgot Password token, OTP, email, SMS, duration, expiration or URL.

### Immediate Action

Complete technical review and merge of Phase 1, then explicitly authorize Phase 2. Do not implement Phases 2–7 from the documentation branch.

# Development Workflow

Every future milestone shall follow the same lifecycle:

1. Business analysis.
2. Domain validation.
3. Technical design.
4. Implementation.
5. Testing.
6. Technical review.
7. Documentation update.
8. Commit.
9. Repository synchronization.

No milestone is complete until implementation and documentation are synchronized.

---

# Scope Management

During a milestone:

- no future functionality is incorporated;
- architectural changes require documented justification;
- undefined rules are not implemented;
- permanent project knowledge is recorded in the repository;
- database execution requires explicit authorization.

---

# Architectural Governance

- GitHub is the single source of truth.
- `.ai` contains the official project documentation.
- Approved architecture and domain decisions precede implementation.
- `DATABASE_DESIGN.md` governs the resulting physical schema.
- Business rules drive technical design.
- Long-term maintainability has priority over short-term speed.
- Compatibility is preserved whenever reasonably possible, subject to the pre-production boundary established by ADR-0018.
