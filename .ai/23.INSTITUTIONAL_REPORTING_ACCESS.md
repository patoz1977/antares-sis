# Institutional Reporting Access Baseline

## Document Status

**Version:** 1.0

**Status:** Approved analysis and design baseline; not implemented

**Date:** 2026-10-29

---

# 1. Purpose and Authority

This document is the functional, authorization and implementation-planning authority for the minimum institutional read-only access to every existing Enrollment report and its CSV representation.

The approved user is an **Institutional Reporting User**. This is a descriptive actor, not a persisted role and not an institution-specific product role such as DECE, Enfermería or Inspección. Access is expressed through one reusable capability assigned to User independently of every institutional role associated with the User's Person:

```text
REPORTS_VIEW_ALL
```

This baseline authorizes documentation and separately authorized implementation phases. It does not itself change product code, schema, production data or credentials.

---

# 2. Approved Functional Boundary

An authenticated active User with `REPORTS_VIEW_ALL` may consult and export exactly the current six reports:

1. Enrollment Summary;
2. Student Enrollment List;
3. Student and Representative Directory;
4. Billing;
5. Medical;
6. Inspección physical-departure information.

The capability grants the HTML and CSV representations together. By itself it never grants mutation, administrative discovery, Representative Portal access or any other administrative capability. Existing authority obtained independently through Admin or Representative access remains cumulative and is not removed by this capability.

A User whose only approved access is `REPORTS_VIEW_ALL` cannot:

- create, edit, activate, deactivate or delete data;
- discover or administer Persons or Families;
- provision or change Representative Users;
- review, reopen, complete or cancel Enrollment;
- use Bulk Import or Academic Initialization;
- administer Institutional Acknowledgements or AcademicPeriod lifecycle;
- access the Representative Portal unless the same User independently resolves an authorized Representative context through the existing rules;
- administer users, capabilities, configuration, branding or system behavior.

Admin retains every existing administrative capability and navigation in addition to `REPORTS_VIEW_ALL`. A User that also resolves as Representative retains exactly the existing Family-context and Representative Portal behavior and gains report access alongside it. Authorization is cumulative: neither capability becomes authority for the other. A Student role associated with the same Person neither grants nor blocks report access and still grants no Student Portal. This milestone does not convert any actor into a generic role.

---

# 3. Current State and Required Correction

At the approved source baseline, User persists authentication and access state but no role or permission. All report routes reuse `EnrollmentAdministrationMiddleware`, whose temporary policy is the exact `loginIdentifier === 'admin'` check. The shared shell and root dispatch also distinguish Admin through that legacy identifier.

That gate cannot safely authorize another institutional account: adding another username, an environment list or a controller exception would make identity equal permission and would duplicate policy between HTML, CSV, navigation and root dispatch.

The implementation must therefore separate report authorization from Enrollment administration. The existing administrative middleware continues to protect Enrollment administration, Bulk Import and Academic Initialization. A dedicated report middleware protects the report hub, every report HTML route and every CSV route through one Application policy.

# 4. Minimal Authorization Model

## 4.1 Capability

`REPORTS_VIEW_ALL` is a stable product capability code owned by Identity & Access authorization. It is not:

- a job title;
- an institutional department;
- a catalog value;
- a configurable environment value;
- a username convention;
- a hierarchy of roles or permissions.

Presence of one active assignment grants all six reports and their CSV exports. Absence denies them. There is no per-report grant, deny override, role inheritance, group, scope expression, wildcard or permission-administration UI in this milestone.

## 4.2 Runtime policy

The report policy is:

```text
authenticated active User
AND persisted REPORTS_VIEW_ALL assignment
```

The policy is evaluated from the authenticated `UserId`, never from `loginIdentifier`, Person roles or data, a browser value, session-cached capability list or navigation visibility. Representative or Student roles associated with the same Person neither grant nor deny `REPORTS_VIEW_ALL`.

Admin receives the same persisted assignment, so report runtime authorization no longer depends on the legacy Admin username. Existing exact-Admin checks remain unchanged for non-report administrative routes until a separately approved authorization milestone replaces them.

Authentication failure preserves the existing redirect-to-login behavior. An authenticated User without the assignment receives HTTP 403. Unknown or malformed persisted capability data fails closed.

## 4.3 Layer responsibilities

- **Domain:** Enrollment, Person, Family, Representative, Student and User authentication behavior do not change. Person remains multi-role and User remains associated with Person independently of those roles. No report behavior is added to an Aggregate. The capability is an authorization concept, not a business role.
- **Application:** one `CanAccessAllReports` policy/use case resolves the authenticated User identity through a narrow `UserCapabilityLookup` contract and returns an authorization decision. Root dispatch and shell composition consume the same decision.
- **Infrastructure:** one PDO adapter reads capability assignments with a prepared query. A separate write boundary is used only by the approved provisioning/grant operation; report queries remain read-only.
- **Delivery:** one `ReportingAccessMiddleware` is attached to all report HTML and CSV routes after authentication. Controllers and Views contain no authorization policy. Navigation uses the same Application decision and never substitutes for middleware.

# 5. Physical Model and Migration Impact

An evolutionary migration is required because the production installation contains real data and the current schema has no persisted authorization assignment.

The minimum target is one assignment table; no `roles`, `permissions`, `role_permissions`, hierarchy, tenant column, capability catalog or seeder is added.

```text
user_capabilities
├── id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
├── user_id BIGINT UNSIGNED NOT NULL
├── capability_code VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL
└── granted_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
```

Physical rules:

- FK `user_id -> users.id` with `ON DELETE RESTRICT ON UPDATE RESTRICT`;
- UNIQUE `(user_id, capability_code)` prevents duplicate grants;
- the UNIQUE also supports the authorization lookup; no speculative secondary index is required;
- `capability_code` is compared exactly and case-sensitively;
- unknown codes are not treated as authority;
- UTC connection conventions remain in force.

The next implementation migration is expected to be `012_create_user_capabilities`. It must:

1. create the table without altering existing User rows;
2. identify the one existing legacy Admin account only for the controlled compatibility backfill and assign `REPORTS_VIEW_ALL`;
3. fail closed if an existing installation contains an incoherent Admin identity instead of selecting an arbitrary User;
4. require the updated AdminSeeder to grant the capability idempotently both when it creates Admin and when Admin already exists; the current early return must be revised so an existing Admin cannot skip capability reconciliation;
5. preserve all existing IDs, credentials, statuses, lockout state and application data.

Migration 012 may use the legacy Admin identifier only to locate the existing account for this initial backfill. This transitory migration use does not authorize any runtime gate by username. The identifier is not consulted by report authorization after the assignment exists.

`12.DATABASE_DESIGN.md` and `13.ERD.md` remain descriptions of the implemented 001-011 schema during this documentation phase. They must be updated atomically with migration 012 implementation, not before the table exists.

# 6. Exact Route Authorization

## 6.1 Authorized authenticated routes

`REPORTS_VIEW_ALL` authorizes exactly these GET routes:

```text
/
/reports/enrollments
/reports/enrollments/summary
/reports/enrollments/summary/csv
/reports/enrollments/students
/reports/enrollments/students/csv
/reports/enrollments/directory
/reports/enrollments/directory/csv
/reports/enrollments/billing
/reports/enrollments/billing/csv
/reports/enrollments/medical
/reports/enrollments/medical/csv
/reports/enrollments/inspection
/reports/enrollments/inspection/csv
```

`GET /` is only a landing/dispatch route and redirects a capability-only User to `/reports/enrollments`; it does not expose the administrative Dashboard. `POST /logout` remains authorized through the existing authenticated session and CSRF boundary.

Root and shell resolution compose access without treating route precedence as authorization:

- Admin keeps the administrative Dashboard and complete existing navigation, including Reports;
- a User with Representative access and `REPORTS_VIEW_ALL` keeps the Representative Portal and receives a reachable Reports destination in the authenticated navigation;
- a User with `REPORTS_VIEW_ALL` and no other navigable access is redirected to the report hub and receives the Reports/Logout shell.

Admin's persisted capability is still required when Admin enters a report route. Representative access never substitutes for `REPORTS_VIEW_ALL`, and `REPORTS_VIEW_ALL` never substitutes for Representative contextual authorization.

The public `/login` GET/POST and `/forgot-password` GET retain their existing behavior and are not capability grants.

## 6.2 Explicitly unauthorized routes

A User whose only access is `REPORTS_VIEW_ALL` receives HTTP 403 when directly requesting any existing administrative route outside `/reports/enrollments...`, including every current route under:

```text
/persons
/families
/representative-users
/enrollments
/institutional-acknowledgements
/admin/bulk-import
/admin/academic-initialization
```

This includes their GET, POST, template, result, error-download, discovery, lifecycle and mutation endpoints. The current exact-Admin middleware remains their authority.

Every current route under `/representative` remains governed exclusively by the existing Representative contextual authorization. A capability-only User receives HTTP 403; a User that independently has valid Representative access keeps that Portal access. `REPORTS_VIEW_ALL` neither creates nor infers Representative, Family or Student context.

No reporting POST route, alias, API, public export or per-report exception is added.

# 7. Navigation and Presentation

The capability-only shell contains exactly:

- `Reportes`, linking to `/reports/enrollments`;
- `Cerrar sesión`, using the existing CSRF-protected POST action.

The White Label brand link also returns to `/reports/enrollments`. Administrative Dashboard, Persons, Families, Import, Academic Initialization, Acknowledgements and Enrollments links are absent unless another independently authorized access grants them.

Admin keeps its complete existing navigation. A User with both Representative access and `REPORTS_VIEW_ALL` keeps the Representative navigation and receives an additional Reports destination; Logout remains shared. Navigation composition must make both access paths reachable without using either one as authority for the other.

The existing report hub is the minimum read-only landing; no new Dashboard or duplicate report screen is required. Hiding navigation never replaces route authorization.

All existing Spanish, responsive, semantic-table, keyboard, no-JavaScript, safe-error and White Label behavior remains unchanged.

---

# 8. HTML, CSV and Privacy Controls

All 13 report routes use the same `AuthenticationMiddleware + ReportingAccessMiddleware` chain. HTML and CSV cannot be registered under different policies.

The implementation preserves:

- exact server-side authorization before any dataset query or CSV generation;
- `Cache-Control: no-store` for HTML, CSV and safe report errors;
- current authoritative AcademicPeriod and Grade/Section validation;
- escaped HTML and existing semantic/responsive report Views;
- exactly the approved columns for each report;
- UTF-8 BOM, native CSV quoting, deterministic order and spreadsheet-formula neutralization;
- generic errors without SQL, paths, stack traces, names, identification, medical data, billing data, contact data or selectors in logs/flash;
- read-only projections and existing fail-closed multiplicity behavior.

The capability changes only who may invoke the existing report boundary. It does not change datasets, report semantics, routes, filters or output fields.

# 9. Initial Institutional User Strategy

The initial account must be a normal active User attached to exactly one existing Person. Operationally, the institution may choose a Person without Representative or Student roles for the first account, but that is not a product restriction, business rule or invariant. Person remains multi-role, and the persisted capability belongs exclusively to User by UserId. No department name is persisted as a role.

The recommended creation sequence is:

1. Admin creates or confirms the institutional Person through the existing Person capability.
2. A narrow Identity & Access Application operation resolves whether the Person already has a User. If one exists, it preserves that User, credential, status and access state and grants `REPORTS_VIEW_ALL` idempotently. If none exists, it validates global normalized-login uniqueness, hashes the initial password through the existing PasswordHasher, creates an ACTIVE User and inserts `REPORTS_VIEW_ALL` in the same transaction.
3. For a newly created User, plaintext password exists only during that operation, is never stored, logged, displayed after completion, committed to Git or exported, and is delivered through the institution's external credential channel. Granting the capability to an existing User receives no password and changes no credential.
4. The account authenticates through the existing login, lockout, session-regeneration and logout behavior.

This operation is not Representative provisioning: a newly created institutional User does not derive LoginIdentifier automatically from Person.DocumentNumber, while an existing Representative User retains its established document-based LoginIdentifier unchanged. No Representative, Student or Family membership is created. Existing roles of the selected Person are left unchanged. If the User already has or later obtains valid Representative access, that access coexists with `REPORTS_VIEW_ALL`.

The productive Delivery mechanism for this one-time operation must be approved before implementation. The recommended minimum is an operator-only provisioning entry point outside public navigation that calls the Application operation; it must not become a generic role/permission editor. Direct ad-hoc SQL, a username exception, an environment allowlist or creation inside the schema migration is prohibited.

# 10. Required Tests

## 10.1 Domain/Application

- exact capability-code validation and unknown-code fail-closed behavior;
- positive/negative `CanAccessAllReports` decisions by UserId;
- disabled/missing User denial;
- transactional existing-User grant and new-User provisioning with rollback;
- existing User credential/status/access-state preservation, duplicate normalized-login rejection and idempotent duplicate-capability handling;
- capability decisions remain identical for Persons with no role, Representative role, Student role or both roles;
- no Representative, Family, Student or Enrollment creation during provisioning.

## 10.2 Persistence and migration

- migration 012 fresh install, upgrade from 001-011 and rollback policy;
- Admin capability backfill without changing Admin credentials/state;
- fresh AdminSeeder capability assignment and idempotency;
- FK, UNIQUE, exact code/collation and prepared lookup;
- MariaDB 10.4.32 physical validation on a disposable database;
- existing production-like data preservation and zero report-side mutations.

## 10.3 Delivery and authorization matrix

- anonymous report HTML/CSV redirect to login;
- Admin retains every existing route and all reports;
- Institutional Reporting User receives all six HTML reports and all six CSV exports;
- the hub and every report/CSV route use the same middleware chain;
- a capability-only User receives 403 for every non-report administrative route and every Representative route;
- a User with Representative access plus `REPORTS_VIEW_ALL` reaches both Representative Portal and all reports, with cumulative navigation and independent authorization;
- Representative behavior and denials remain byte/semantic compatible for Users without the capability;
- root dispatch and shell expose only Reports and Logout when no other independently authorized navigation exists;
- direct URLs cannot bypass hidden navigation;
- `no-store`, safe HTML, safe errors, CSV BOM/quoting/formula protection and no-PII logging remain covered.

The complete regression, route inventory, UI/UX closure tests, PHP lint, `git diff --check` and disposable MariaDB campaign are required before closure.

# 11. Planned Implementation Sequence

1. **Phase 1 — Analysis and design baseline:** this document, ADR-0032 and cross-document synchronization; no product, schema or production change.
2. **Phase 2 — Capability persistence and Application policy:** migration 012, assignment lookup, Admin upgrade/fresh-install compatibility and focused physical tests.
3. **Phase 3 — Report Delivery integration:** dedicated report middleware, exact route regrouping, root dispatch and reporting-only shell; no report dataset change.
4. **Phase 4 — Initial institutional User provisioning/grant:** the approved narrow Application operation for an existing or new User and separately approved operator Delivery mechanism; no generic RBAC or user-management module.
5. **Phase 5 — Integrated validation and closure:** full authorization matrix, privacy/UI/CSV regression, migration upgrade/fresh-install evidence and isolated MariaDB validation.

Each implementation phase requires separate authorization. This baseline does not authorize production migration, user creation, credential handling or automatic progression.

---

# 12. Explicit Exclusions

This milestone does not authorize:

- DECE, Enfermería, Inspección, Secretaría or other department/job-title roles;
- generic RBAC, groups, hierarchies, per-report permissions, deny rules or scopes;
- capability administration by the reporting-only User;
- report mutation, new reports, new fields, changed datasets or changed state semantics;
- Person/Family discovery or Enrollment administration from `REPORTS_VIEW_ALL` alone; Representative Portal remains available only through its independent contextual authorization;
- environment/user-name allowlists or hard-coded additional usernames;
- public reports, APIs, tokens, share links or scheduled delivery;
- production execution during analysis/design;
- SQL artifacts, migrations or credentials in this phase.

# 13. Open Decisions and Risks

The authorization model, capability code, route matrix, schema target and migration need are approved. Before Phase 4 implementation, the owner must still approve:

1. the exact operator Delivery mechanism for the one-time institutional User provisioning operation in the supported shared-hosting environment;
2. when no User already exists, the institution-supplied initial LoginIdentifier and credential-delivery procedure;
3. the operational revocation procedure beyond immediate `USER_STATUS = DISABLED` until a future narrowly authorized account-management capability exists.

These decisions do not justify username authorization, direct production SQL or a generic RBAC UI. If they are not resolved, capability and route implementation may proceed through Phase 3, but initial institutional access must not be provisioned or granted.

Primary risks are accidental route regrouping that broadens Enrollment administration, navigation-only authorization, Admin capability omission during upgrade/fresh install, navigation that hides one of several cumulative accesses, coupling the capability to Person roles, and divergence between HTML and CSV middleware. The required policy, migration and matrix tests close those risks fail-securely.
