# 1. Purpose and Authority

This document is the functional, authorization and implementation-planning authority for the minimum institutional read-only access to every existing Enrollment report and its CSV representation.

The approved user is a dedicated **Institutional Reporting User**. This is a constrained access profile, not a persisted role and not an institution-specific product role such as DECE, Enfermería or Inspección. It belongs to exactly one Person under the existing one-User-per-Person model and receives one reusable capability:

```text
REPORTS_VIEW_ALL
```

Phase 2 implements capability persistence, exact read-side lookup, the Application report-access decision and Admin compatibility; PR #97 merged it into `main` at `a3968ad60d24d000d05947d02dae4b36785e283e`. Phase 3 attaches that decision to report Delivery, root dispatch and the shared shell; PR #98 merged it into `main` at `87ef637e38c228a8d4871adead74418b360d07fa`. Phase 4 implements the separately authorized dedicated provisioning/lifecycle behavior locally without schema, production-data or report-delivery changes; it has not provisioned a production institutional account or handled a real credential.

# 2. Approved Functional Boundary

An authenticated active User with `REPORTS_VIEW_ALL` may consult and export exactly the current six reports:

1. Enrollment Summary;
2. Student Enrollment List;
3. Student and Representative Directory;
4. Billing;
5. Medical;
6. Inspección physical-departure information.

The capability grants the HTML and CSV representations together. For a non-Admin User, assignment is permitted only when the User is ACTIVE, its Person exists and that Person resolves to neither Representative nor Student. The account is dedicated to institutional reporting and never combines this capability with Representative or Student access.

The dedicated Institutional Reporting User cannot:

- create, edit, activate, deactivate or delete data;
- discover or administer Persons or Families;
- provision or change Representative Users;
- review, reopen, complete or cancel Enrollment;
- use Bulk Import or Academic Initialization;
- administer Institutional Acknowledgements or AcademicPeriod lifecycle;
- access the Representative Portal or belong to a Family through Representative access;
- administer users, capabilities, configuration, branding or system behavior.

Admin retains every existing administrative capability and navigation and receives the persisted `REPORTS_VIEW_ALL` assignment through migration/seeder compatibility. Phase 3 switches report Delivery from the temporary username gate to this capability while keeping exact-Admin authority on non-report administration. Admin is not treated as an Institutional Reporting User profile and is not constrained by the dedicated-account eligibility rule.

Representative Users remain exactly as currently implemented. They do not receive `REPORTS_VIEW_ALL`, continue resolving `User -> Person -> Representative` and retain their Portal, Enrollment and data-update behavior without report access through this milestone. Student remains without User or Portal under the current model. This milestone does not convert any actor into a generic role.

# 3. Implemented Delivery Correction

Before Phase 3, all report routes reused `EnrollmentAdministrationMiddleware`, whose temporary policy was the exact `loginIdentifier === 'admin'` check. The shared shell and root dispatch also distinguished Admin through that legacy identifier.

That gate cannot safely authorize another institutional account: adding another username, an environment list or a controller exception would make identity equal permission and would duplicate policy between HTML, CSV, navigation and root dispatch.

Phase 3 separates report authorization from Enrollment administration. The existing administrative middleware continues to protect Enrollment administration, Bulk Import and Academic Initialization. A dedicated report middleware protects the report hub, every report HTML route and every CSV route through one Application policy.

# 4. Minimal Authorization Model

## 4.1 Capability

`REPORTS_VIEW_ALL` is a stable product capability code owned by Identity & Access authorization. It is not:

- a job title;
- an institutional department;
- a catalog value;
- a configurable environment value;
- a username convention;
- a hierarchy of roles or permissions.

Presence of one active assignment grants all six reports and their CSV exports. Absence denies them. There is no per-report grant, deny override, role inheritance, group, scope expression, wildcard or permission-administration UI in this milestone.

## 4.2 Runtime policy

The report policy is:

```text
authenticated active User
AND persisted REPORTS_VIEW_ALL assignment
```

The policy is evaluated from the authenticated `UserId` and exact persisted capability assignment, never from `loginIdentifier`, a browser value, session-cached capability list or navigation visibility. Non-Admin capability assignment and reactivation additionally require the dedicated-account eligibility policy: ACTIVE User, existing Person and absence of Representative and Student resolution. Eligibility is evaluated server-side and fails closed.

Admin receives the same persisted assignment. Phase 3 makes report runtime authorization independent of the legacy Admin username; all existing non-report administrative routes retain their exact-Admin checks.

Authentication failure preserves the existing redirect-to-login behavior. An authenticated User without the assignment receives HTTP 403. Unknown or malformed persisted capability data fails closed.

## 4.3 Layer responsibilities

- **Domain:** Enrollment, Person, Family, Representative, Student and User authentication behavior do not change. User remains singular per Person, `uq_users_person` and singular `UserRepository::findByPersonId` remain authoritative, and Representative access resolution remains unchanged. No report behavior is added to an Aggregate. The capability is an authorization concept, not a business role.
- **Application:** one `CanAccessAllReports` policy/use case resolves the authenticated User identity through a narrow `UserCapabilityLookup` contract and returns an authorization decision. A narrow provisioning/reactivation policy verifies the dedicated non-Admin eligibility through existing User, Person, Representative and Student boundaries. Later Representative or Student creation for that dedicated Person must also fail closed while the assignment exists, without changing Representative access resolution. Root dispatch and shell composition consume the report decision.
- **Infrastructure:** one PDO adapter reads capability assignments with a prepared query. A separate write boundary is used only by the approved provisioning/grant operation; report queries remain read-only.
- **Delivery:** one `ReportingAccessMiddleware` is attached to all report HTML and CSV routes after authentication. Controllers and Views contain no authorization policy. Navigation uses the same Application decision and never substitutes for middleware.

# 5. Physical Model and Migration Impact

The production installation contains real data and remains deployed at 001–011 without a persisted authorization assignment. The repository therefore implements the required evolutionary migration 012 without executing it in production.

The minimum target is one assignment table; no `roles`, `permissions`, `role_permissions`, hierarchy, tenant column, capability catalog or seeder is added.

```text
user_capabilities
├── id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
├── user_id BIGINT UNSIGNED NOT NULL
├── capability_code VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL
└── granted_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
```

Physical rules:

- FK `user_id -> users.id` with `ON DELETE RESTRICT ON UPDATE RESTRICT`;
- UNIQUE `(user_id, capability_code)` prevents duplicate grants;
- the UNIQUE also supports the authorization lookup; no speculative secondary index is required;
- `capability_code` is compared exactly and case-sensitively;
- unknown codes are not treated as authority;
- UTC connection conventions remain in force.

Migration `012_create_user_capabilities` implements this target. It:

1. creates the table without altering existing User rows;
2. identifies the one existing legacy Admin account only for the controlled compatibility backfill and assigns `REPORTS_VIEW_ALL`;
3. fails closed if an existing installation contains an incoherent Admin identity instead of selecting an arbitrary User;
4. works with the updated AdminSeeder, which grants the capability idempotently both when it creates Admin and when Admin already exists;
5. preserves all existing IDs, credentials, statuses, lockout state and application data.

Migration 012 may use the legacy Admin identifier only to locate the existing account for this initial backfill. This transitory migration use does not authorize any runtime gate by username. The identifier is not consulted by report authorization after the assignment exists.

`12.DATABASE_DESIGN.md` and `13.ERD.md` now describe the implemented repository schema through migration 012. Production remains at its separately managed deployed ledger until an authorized deployment; Phase 2 performed no production action.

# 6. Exact Route Authorization

## 6.1 Authorized authenticated routes

`REPORTS_VIEW_ALL` authorizes exactly these GET routes:

```text
/
/reports/enrollments
/reports/enrollments/summary
/reports/enrollments/summary/csv
/reports/enrollments/students
/reports/enrollments/students/csv
/reports/enrollments/directory
/reports/enrollments/directory/csv
/reports/enrollments/billing
/reports/enrollments/billing/csv
/reports/enrollments/medical
/reports/enrollments/medical/csv
/reports/enrollments/inspection
/reports/enrollments/inspection/csv
```

`GET /` is only a landing/dispatch route and redirects a capability-only User to `/reports/enrollments`; it does not expose the administrative Dashboard. `POST /logout` remains authorized through the existing authenticated session and CSRF boundary.

Root and shell resolution distinguishes the two approved profiles without treating navigation as authorization:

- Admin keeps the administrative Dashboard and complete existing navigation, including Reports;
- the dedicated Institutional Reporting User is redirected to the report hub and receives only the Reports/Logout shell.

Admin's persisted capability is still required when Admin enters a report route. Representative access never substitutes for `REPORTS_VIEW_ALL`; Representative Users do not receive that capability in this milestone.

The public `/login` GET/POST and `/forgot-password` GET retain their existing behavior and are not capability grants.

## 6.2 Explicitly unauthorized routes

The dedicated Institutional Reporting User receives HTTP 403 when directly requesting any existing administrative route outside `/reports/enrollments...`, including every current route under:

```text
/persons
/families
/representative-users
/enrollments
/institutional-acknowledgements
/admin/bulk-import
/admin/academic-initialization
```

This includes their GET, POST, template, result, error-download, discovery, lifecycle and mutation endpoints. The current exact-Admin middleware remains their authority.

Every current route under `/representative` remains governed exclusively by the existing Representative contextual authorization. The dedicated Institutional Reporting User receives HTTP 403 for every such route. `REPORTS_VIEW_ALL` neither creates nor infers Representative, Family or Student context, and assignment must be rejected if the non-Admin User's Person resolves to either role.

No reporting POST route, alias, API, public export or per-report exception is added.

# 7. Navigation and Presentation

The dedicated reporting shell contains exactly:

- `Reportes`, linking to `/reports/enrollments`;
- `Cerrar sesión`, using the existing CSRF-protected POST action.

The White Label brand link also returns to `/reports/enrollments`. Administrative Dashboard, Persons, Families, Import, Academic Initialization, Acknowledgements and Enrollments links are absent.

Admin keeps its complete existing navigation, including Reports. Representative Users keep their existing Representative navigation without a Reports destination from this milestone. The dedicated reporting shell never exposes Representative navigation.

The existing report hub is the minimum read-only landing; no new Dashboard or duplicate report screen is required. Hiding navigation never replaces route authorization.

All existing Spanish, responsive, semantic-table, keyboard, no-JavaScript, safe-error and White Label behavior remains unchanged.

# 8. HTML, CSV and Privacy Controls

All 13 report routes use the same `AuthenticationMiddleware + ReportingAccessMiddleware` chain. HTML and CSV cannot be registered under different policies.

The implementation preserves:

- exact server-side authorization before any dataset query or CSV generation;
- `Cache-Control: no-store` for HTML, CSV and safe report errors;
- current authoritative AcademicPeriod and Grade/Section validation;
- escaped HTML and existing semantic/responsive report Views;
- exactly the approved columns for each report;
- UTF-8 BOM, native CSV quoting, deterministic order and spreadsheet-formula neutralization;
- generic errors without SQL, paths, stack traces, names, identification, medical data, billing data, contact data or selectors in logs/flash;
- read-only projections and existing fail-closed multiplicity behavior.

The capability changes only who may invoke the existing report boundary. It does not change datasets, report semantics, routes, filters or output fields.

# 9. Dedicated Institutional User Strategy and Lifecycle

The institutional reporting account must be a normal ACTIVE User attached to exactly one existing Person under the unchanged one-User-per-Person model. That Person must resolve to neither Representative nor Student. This eligibility is a product rule for the dedicated non-Admin reporting profile. No department name is persisted as a role.

The recommended creation sequence is:

1. Admin creates or confirms the institutional Person through the existing Person capability.
2. A narrow Identity & Access Application operation verifies that the Person resolves to neither Representative nor Student and resolves whether it already has its singular User. If an ACTIVE eligible User exists, it may be designated as the dedicated reporting account and receive `REPORTS_VIEW_ALL` idempotently. If none exists, the operation validates global normalized-login uniqueness, hashes the initial password through the existing PasswordHasher, creates one ACTIVE User and inserts `REPORTS_VIEW_ALL` in the same transaction. A Representative or Student Person, missing Person, non-ACTIVE User or incoherent resolution fails closed.
   The normalized exact `admin` LoginIdentifier is always reserved before persistence, independently of whether a legacy Admin row currently exists. It remains an identity-integrity rule and never grants report access.
3. For a newly created User, plaintext password exists only during that operation, is never stored, logged, displayed after completion, committed to Git or exported, and is delivered through the institution's external credential channel. Granting the capability to an existing User receives no password and changes no credential.
4. The account authenticates through the existing login, lockout, session-regeneration and logout behavior.

This operation is not Representative provisioning: a newly created institutional User does not derive LoginIdentifier automatically from Person.DocumentNumber. No Representative, Student or Family membership is created. An existing Representative User cannot be reused or granted the capability. This milestone does not authorize a second Person record for the same human or multiple Users for one Person merely to separate access profiles. The scenario in which one real person requires both Representative Portal and Institutional Reporting access is explicitly out of scope and requires a separately approved Identity & Access decision/milestone if it arises.

Normal operational revocation sets the dedicated reporting User to `USER_STATUS = DISABLED`, removing all of that account's SIS access. This milestone adds no capability deletion/removal workflow or generic capability-revocation UI. Reactivation uses the existing User lifecycle and must revalidate that the Person still resolves to neither Representative nor Student before restoring access. The implemented Delivery mechanism is contextual exact-Admin Person administration with trusted Person context, CSRF, POST-only mutation and PRG.

Provisioning, capability assignment, disabling and reactivation are security-relevant operations. The implementation emits only the four ADR-0033 event names after successful commit through the existing security logger, without a generic audit subsystem or table. Logs exclude plaintext passwords, password hashes, identifiers, medical or billing data and unnecessary PII.

The productive Delivery mechanism is an exact-Admin-only contextual entry from Person detail and calls narrow Application operations; it is not a generic role/permission editor and adds no global navigation item. Direct ad-hoc SQL, a report-authorization username exception, an environment allowlist or creation inside the schema migration is prohibited.

# 10. Required Tests

## 10.1 Domain/Application

- exact capability-code validation and unknown-code fail-closed behavior;
- positive/negative `CanAccessAllReports` decisions by UserId;
- disabled/missing User denial;
- transactional eligible existing-User designation and new-User provisioning with rollback;
- existing User credential/status/access-state preservation, duplicate normalized-login rejection and idempotent duplicate-capability handling;
- grant rejection when Person resolves to Representative;
- grant rejection when Person resolves to Student;
- later Representative or Student creation rejection for the dedicated reporting Person while the assignment exists;
- disabled reporting User denial and reactivation eligibility revalidation;
- no Representative, Family, Student or Enrollment creation during provisioning.

## 10.2 Persistence and migration

- migration 012 fresh install, upgrade from 001-011 and rollback policy;
- Admin capability backfill without changing Admin credentials/state;
- fresh AdminSeeder capability assignment and idempotency;
- FK, UNIQUE, exact code/collation and prepared lookup;
- MariaDB 10.4.32 physical validation on a disposable database;
- existing production-like data preservation and zero report-side mutations.

Phase 2 permanent local coverage implements the schema/source, Application, PDO lookup and AdminSeeder cases above. Phase 3 adds permanent middleware, exact-route, root-dispatch, shell and authorization-boundary coverage. Phase 4 has 17 focused Domain/Application/Persistence/Delivery/architecture tests and extends affected Representative, Student, Bulk Import, route and UI regressions. The complete official runner passes 909 tests with zero failures, and all three official HTTP/session scenarios pass. Permanent coverage now includes real-container construction/route registration, normalized reserved-Admin rejection before persistence, transaction-required capability current reads and an adversarial MariaDB scenario in which a transaction establishes a `REPEATABLE READ` snapshot before the Person lock. All 6/6 authorized `E0041_DB_*` variables are available, but the configured disposable endpoint actively refused the connection before database creation; the new physical scenario and fresh MariaDB 10.4.32 evidence remain pending and are not represented as PASS.

## 10.3 Delivery and authorization matrix

- anonymous report HTML/CSV redirect to login;
- Admin retains every existing route and all reports;
- dedicated Institutional Reporting User receives all six HTML reports and all six CSV exports only;
- the hub and every report/CSV route use the same middleware chain;
- the dedicated reporting User receives 403 for every non-report administrative route and every Representative route;
- Representative User without `REPORTS_VIEW_ALL` retains Representative Portal only and existing behavior remains byte/semantic compatible;
- root dispatch and the dedicated shell expose only Reports and Logout;
- direct URLs cannot bypass hidden navigation;
- `no-store`, safe HTML, safe errors, CSV BOM/quoting/formula protection and no-PII logging remain covered;
- provisioning/grant and disable/reactivate operations produce authorized audit evidence without secrets or unnecessary PII.

The complete regression, route inventory, UI/UX closure tests, PHP lint, `git diff --check` and disposable MariaDB campaign are required before closure.

# 12. Explicit Exclusions

This milestone does not authorize:

- DECE, Enfermería, Inspección, Secretaría or other department/job-title roles;
- generic RBAC, groups, hierarchies, per-report permissions, deny rules or scopes;
- capability administration or deletion/removal workflow by the reporting User;
- report mutation, new reports, new fields, changed datasets or changed state semantics;
- Person/Family discovery, Enrollment administration or Representative Portal access for the dedicated reporting User;
- environment/user-name allowlists or hard-coded additional usernames;
- public reports, APIs, tokens, share links or scheduled delivery;
- production migration or SQL execution without a separately authorized deployment;
- additional unapproved schema changes, SQL artifacts or credentials.

# 13. Open Decisions and Risks

The authorization model, capability code, route matrix, schema target and migration need are approved. ADR-0033 resolves the remaining Phase 4 decisions: exact-Admin contextual Person Delivery; institution-supplied LoginIdentifier and external credential handoff for a new User; the same profile-specific five-character minimum as Representative without making it universal; exact legacy Admin exclusion only for dedicated-profile classification; status-only disable/reactivate; future Representative/Student prohibition; and the four minimal existing security-event names. No new audit subsystem, table, UI, report, dependency or PII-rich payload is authorized.

The exact Admin identifier never authorizes reports: runtime report authority remains active User plus persisted capability. The approved classification exclusion does not justify any additional username authorization, direct production SQL or generic RBAC UI.

Phase 3 closes accidental report-route regrouping, navigation-only authorization and HTML/CSV middleware divergence. Phase 4 closes local eligibility, lifecycle, future-role, stale-snapshot and sensitive-event risks through fail-closed Application policies, current/locking reads after Person serialization and permanent tests. Remaining risk is execution of the pending physical MariaDB/concurrency scenario plus the separately authorized Phase 5 integrated closure; production migration 012 and real account provisioning remain outside this local implementation.
