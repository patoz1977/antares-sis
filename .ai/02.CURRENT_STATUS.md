# Project Status

## Overall Status

The Enrollment Domain Discovery is closed and the AUDIT-001 documentation reconstruction is technically approved as the official Enrollment baseline.

E004.1 — Identity & Access Baseline is completed and merged into `main` through PR #3.

E005 — Person Baseline is the current functional milestone. Phase 1 established ADR-0018 and the pre-production rebaseline boundary. Phase 2 completed the IdentityAccess persistence alignment, the general schema rebaseline and the retirement of incompatible legacy Person/Family flows.

Phase 3A implements the approved Person Domain as an isolated Aggregate Root with its documented Value Objects and invariants. Phase 3B added the minimal Person Repository contract and PDO implementation, passed disposable MariaDB 10.4 validation and was merged through PR #7. Phase 3C added the minimal CreatePerson, GetPerson and UpdatePerson application use cases with typed input/output DTOs and was merged through PR #8.

Phase 4 now provides the minimal White Label web delivery for the existing administrator: create Person, query Person by positive ID and update an existing Person. Access is temporarily restricted to the authenticated `login_identifier = admin`; this is an MVP constraint and not the definitive authorization model. Secretaría, DECE and Enfermería roles remain pending future definition.

IdentityAccess persistence now targets the official `users` structure without `deleted_at` or `locked_until`. Its domain, application, HTTP, session, CSRF and authentication behavior remain unchanged.

## Current Risks

- The destructive authorization is valid only while the target remains pre-production and disposable; it must not be applied to an institutional or production database containing real data.
- The clean migration sequence is destructive by design under ADR-0018 and must never be pointed at an institutional or production database.
- The 36-table functional inventory, documented-column parity, Person Persistence and disposable MariaDB 10.4 scenarios passed validation. Future database execution remains restricted to explicitly authorized disposable `E0041_DB_*` environments.
- Official catalog values not yet supplied remain a data-master concern, not a schema decision. Person forms fail closed when the required active sex and GENERAL_STATUS options are unavailable.

## Pending Decisions

The temporary `admin` gate does not define the future role model. Authorization for Secretaría, DECE and Enfermería remains pending a separately approved definition; no role, permission or authorization catalog was introduced by Phase 4.

## Repository Status

- PR #3 was merged into `main` at commit `60a444d`.
- PR #7 merged Person Persistence into `main` at commit `1c936ce` after local and disposable MariaDB 10.4 validation.
- PR #8 merged Person Application into `main` at commit `9587d68`.
- E004.1 remains functionally unchanged.
- IdentityAccess persistence and its tests remain aligned with the official `users` columns.
- Migrations 002–009 now define the clean 36-table functional baseline; migration 001 and the runner-owned `migrations` table remain technical metadata.
- Legacy Person/Family controllers, services, repositories, views and routes incompatible with the approved model were retired pending their milestone implementations.
- Seeders now provide only approved status types and statuses. No institutional catalog value or synthetic Person is invented; optional administrator creation requires an existing Person identifier and an external initial password.
- Local PHP, Composer, schema-parity, application-bootstrap, IdentityAccess, Person Domain, Person Persistence, Person Application and Person Delivery validations passed. Phase 4 did not execute migrations or database operations.
- Person Domain now contains only the Person Aggregate Root, PersonId, PersonalName, Identification, ContactInformation, GENERAL_STATUS lifecycle and domain exceptions.
- Person unit tests cover valid construction, optional identity/contact data, Value Object equality, invalid formats and bounds, non-future birth date, Catalog references, atomic identity replacement, contact replacement and activation lifecycle.
- PersonRepository exposes only lookup by PersonId, lookup by Identification and save. PdoPersonRepository maps every approved `persons` column, validates GENERAL_STATUS, preserves nullable fields, inserts new Persons through database-generated AUTO_INCREMENT identities and performs exact-row updates.
- Local persistence tests cover complete reconstruction, present and absent parameterized identification lookups, optional fields, ACTIVE and INACTIVE, invalid status ownership/code, insertion, update, null removal, normalized identification uniqueness and a disappearing update target.
- MariaDB connections explicitly use `utf8mb4` with `utf8mb4_unicode_ci`. Person identification lookup compares the bare indexed `identification_key` with one prepared key parameter instead of constructing a connection-collated SQL expression.
- The disposable MariaDB harness now includes real Person insert, ID and identification lookup, update, GENERAL_STATUS mapping, normalized uniqueness, connection/column collation verification, safe collation diagnostics and cleanup coverage without institutional seed data.
- Person Application contains only CreatePerson, GetPerson and UpdatePerson, one typed input per write use case, one common immutable output and specific not-found, duplicate-identification and invalid-persisted-result errors.
- Create and Update receive an explicit current date, use only PersonRepository, preserve domain exceptions and perform no transaction, locking, retry or infrastructure work.
- Local Application coverage uses a test-only in-memory repository and verifies creation, complete output, repository-generated identity, lookup, full replacement, optional-data removal, status changes, duplicate identification handling, identity preservation and atomic domain failure.
- Person Delivery provides exactly six protected routes for index, create, detail and update, with no list, name search, pagination, delete, import, API or report flow.
- Every Person route runs AuthenticationMiddleware followed by the temporary Person administrator middleware. Authenticated non-admin users receive HTTP 403, and only `admin` sees the dashboard navigation entry.
- PersonController adapts HTTP to CreatePerson, GetPerson and UpdatePerson, validates only request shape, protects POST with the existing CSRF service, preserves safe form input, binds the edited identity to server-side session state and maps known application/domain errors without exposing SQL or internal details.
- Person form options are read by a specific PDO infrastructure provider from active document type, sex, marital status and education level rows plus active GENERAL_STATUS ACTIVE/INACTIVE values. Required catalog absence disables persistence.
- White Label HTML views cover Person index, create/edit, detail and safe not-found output. No institution is hardcoded.
- The accumulated local suite contains 103 passing tests plus three HTTP/session scenarios. The disposable MariaDB harness now also validates physical Person form-option loading, but its Phase 4 execution remains pending for the explicitly authorized XAMPP environment.
- No role model, User creation, Representative, Student, Family, Enrollment, import, report or generic administration framework was added.
- GitHub remains the single source of truth.
