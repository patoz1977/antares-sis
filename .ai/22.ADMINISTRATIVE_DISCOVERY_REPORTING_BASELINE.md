# Administrative Discovery and Operational Reporting Baseline

## Document Status

**Version:** 1.4

**Status:** Approved functional and architectural baseline

**Date:** 2026-10-04

---

# 1. Purpose and Authority

This document is the permanent source for four related post-MVP administrative capabilities:

1. evolution of the existing E013 Student and Representative Directory;
2. administrative discovery of Persons and Families without requiring operators to know internal IDs;
3. an operational physical-departure report for Inspección;
4. a reusable multiple Grade/Section reporting filter.

It authorizes documentation and phased implementation. Phases 2–5 implement the reusable filter, evolve the existing Directory, add administrative Person/Family discovery and deliver the Inspección operational report without migrations or indexes; later capabilities remain separately authorized.

The original E013 five-report baseline remains the historical authority for what E013 delivered. This document authorizes a later evolution of that baseline; it does not rewrite E013 history or create a second Directory.

---

# 2. Existing Model and Ownership

The approved model already contains all information required by these capabilities:

- Person owns current names, identification and contact information;
- Representative and Student reference their Person;
- FamilyRepresentative owns the current Representative-to-Family membership, RelationshipType and Primary marker;
- FamilyStudent owns the current Student-to-Family membership;
- StudentAddressAssignment identifies the current FamilyAddress applicable to a Student;
- Enrollment owns selected-period AcademicPlacement, EnrollmentStatus and IsAuthorizedToLeaveAlone;
- FamilyAuthorizedPickup and AuthorizedPickupAssignment own current authorized-pickup information and its Student assignment.

There is no direct Representative-to-Student relationship. Nothing in this baseline creates or implies one. Relationship labels shown for Representatives or AuthorizedPickups describe the existing Family-owned relationship data.

No schema change is required for the approved scope. Future index work requires measured evidence through representative-volume analysis and/or `EXPLAIN` before a migration may be authorized.

---

# 3. Existing E013 Population and Time Semantics

Unless a report-specific rule below says otherwise, the E013 population and time semantics remain in force:

- Enrollment Summary operates over existing Enrollments in the selected AcademicPeriod;
- Student Enrollment List, Directory, Billing and Medical begin from currently ACTIVE Students and left-associate the optional Enrollment for the selected AcademicPeriod;
- absent Enrollment derives reporting-only `NOT STARTED` where the existing report contract requires it;
- Grade, Section, EnrollmentStatus and annual values come only from the Enrollment in the selected AcademicPeriod;
- Person, Representative, Family membership, contact and address data are current live SIS information, not historical snapshots;
- missing valid optional relationships produce empty report fields, while physically incoherent multiplicity fails closed.

The Inspección report has its own current-period rule in section 6 and is not a historical report.

# 4. Existing Directory Evolution

## 4.1 Identity and Period

The existing E013 Student and Representative Directory evolves in place. No second Directory is created.

The Directory works over one selected AcademicPeriod and accepts the reusable multiple Grade/Section filter defined in section 7. HTML and CSV use the same Application dataset and the same filter.

Each logical Directory row represents exactly one Student. Representative joins or multiplicity must never multiply Student rows.

## 4.2 Academic Columns

The row contains:

- Grade;
- Section;
- the selected-period Enrollment reporting status.

Grade and Section remain empty when the selected-period Enrollment or AcademicPlacement does not exist. They are never inferred from age, Family, another period or history.

## 4.3 Student Columns

The Directory dataset exposes atomic columns for:

- first name;
- middle name;
- first surname;
- second surname;
- identification under the current Person model.

Names and surnames are not concatenated inside the Application read model or CSV dataset. Optional name and identification components remain empty rather than being invented.

## 4.4 Representative Columns

Representative 1 and Representative 2 each expose atomic columns for:

- first name;
- middle name;
- first surname;
- second surname;
- current Representative-to-Family relationship label;
- identification;
- personal email;
- mobile phone;
- landline phone.

The relationship is the current `family_representatives.relationship_type_id` reference. It is not described as a direct relationship with the Student.

## 4.5 Representative 1

Representative 1 is always the current active Primary FamilyRepresentative of the Student's current active Family.

The existing invariant of at most one active Primary applies. Missing valid current data produces empty columns under the existing Directory rules; incoherent active-Primary multiplicity fails closed.

When the current active Family has one or more active FamilyRepresentatives but none is Primary, both Representative 1 and Representative 2 remain empty. A secondary Representative is never promoted, and Representative 2 selection is not evaluated until one valid Primary Representative has been resolved. The Directory exposes this absence/inconsistency instead of masking it through an arbitrary substitute.

## 4.6 Representative 2

Representative 2 is selected only from the other current active FamilyRepresentatives of the same Family, using exactly this rule:

1. When there is no active secondary Representative, Representative 2 is empty.
2. When there is exactly one active secondary Representative, that Representative is selected regardless of RelationshipType.
3. When there are two or more active secondary Representatives:
   - if Representative 1 has code `FATHER`, Representative 2 is the secondary Representative with code `MOTHER`;
   - if Representative 1 has code `MOTHER`, Representative 2 is the secondary Representative with code `FATHER`;
   - if Representative 1 has neither code, Representative 2 is the secondary Representative with code `FATHER`;
   - if the preceding case finds no `FATHER`, Representative 2 is the secondary Representative with code `MOTHER`;
   - if no applicable `FATHER` or `MOTHER` exists, Representative 2 is empty.
4. With two or more secondary Representatives, no fallback may select by ID, membership age, alphabetical order, creation order or any other unapproved criterion.

`FATHER` and `MOTHER` are the current institution-approved stable RelationshipType codes recorded in `18.DEPLOYMENT_BASELINE.md`. Future implementation resolves and compares stable codes, never physical RelationshipType IDs. If invalid data yields more than one applicable active `FATHER` or `MOTHER`, the query fails closed rather than choosing arbitrarily.

## 4.7 Current Address

The authoritative Directory address is the current active StudentAddressAssignment to an active FamilyAddress in the Student's current active Family.

No arbitrary Family address, Representative address, historical assignment or inferred fallback replaces a missing Student assignment. A valid absence produces empty address columns; incoherent active multiplicity fails closed.

## 4.8 HTML and CSV

- HTML and CSV originate from the same Application read model.
- HTML renders one logical row per Student.
- CSV renders one row per Student with atomic columns.
- A Representative never creates an additional CSV row.
- Existing UTF-8 BOM, deterministic ordering, native quoting and spreadsheet-formula protection remain mandatory.

# 5. Administrative Person and Family Discovery

## 5.1 Shared Boundary

Administrative discovery removes the operational requirement to know internal positive IDs. Search is read-only and uses dedicated Application query ports and immutable result DTOs; transactional Aggregate repositories do not become mass-search services.

Sensitive criteria are submitted through POST with CSRF protection. Search responses use `Cache-Control: no-store`. Names, identification numbers and emails do not appear in URLs, browser history, flash messages or logs.

Each search returns at most 30 results. The implementation may fetch one additional row only to determine that more results exist; when it does, the UI instructs the operator to refine the search. This baseline does not authorize pagination or fuzzy search.

## 5.2 Person Search

Person search supports exactly:

- first/middle name by word prefix;
- first/second surname by word prefix;
- exact identification number;
- exact personal email.

Phone search is excluded.

Name and surname criteria require at least three trimmed characters. Whitespace may be normalized for comparison, but no fuzzy, phonetic or inferred equivalence is allowed. Identification and email comparisons are exact after the normalization already approved for their current model and database representation.

Results use deterministic order: first surname, second surname, first name, middle name and PersonId as the final stable tie-breaker. Visible results provide the current full name, available identification and available email needed to disambiguate, plus an action that opens the existing Person detail without requiring the operator to enter or understand the internal ID.

## 5.3 Family Search Through Current People

Family search supports the same Person criteria and matching semantics through only current active relationships:

- active FamilyRepresentative → Representative → Person;
- active FamilyStudent → Student → Person.

Historical ended memberships never produce a match.

Duplicate matches through multiple current members collapse to one Family result. Results show FamilyCode, display name, current status and enough matched-member name/role context to explain and disambiguate the match, then open the existing Family detail.

Additional direct Family criteria are:

- exact FamilyCode;
- display-name word prefix with the same three-character minimum.

FamilyCode remains the case-sensitive alphanumeric Domain value defined by the current model and is never cast, compared or displayed as an integer.

Family results use deterministic order: display name, FamilyCode and FamilyId as the final stable tie-breaker. Search returns no historical Family relation merely because the Person was previously associated.

## 5.4 Persistence and Performance

Initial implementation uses prepared read-only projections over the current schema. No index is authorized by this baseline.

Before proposing an index, implementation must record the representative dataset, query shape and `EXPLAIN`/measurement that demonstrates the need. Any approved index is a later migration reviewed independently from the functional search contract.

# 6. Operational Physical-Departure Report for Inspección

## 6.1 Responsibility and Time Boundary

The new report answers only:

> Can this Student leave campus alone, or must an authorized person collect the Student, and who is currently authorized?

It is an operational report for the single current ACTIVE AcademicPeriod. It is not a historical authorization report because FamilyAuthorizedPickup and its assignments are current live Family data, not annual snapshots.

The report is unrelated to institutional withdrawal, Enrollment cancellation, leaving the institution, promotion, repetition or graduation. It creates no Inspection User or role; the existing administrative gate remains authoritative.

## 6.2 Population and Sources

The report begins from currently ACTIVE Students, consistent with the operational E013 Student reports, and resolves the single ACTIVE AcademicPeriod server-side. Missing or multiple ACTIVE periods fail closed.

For each Student it exposes:

- Grade and Section from the Enrollment in the ACTIVE AcademicPeriod;
- atomic Student first name, middle name, first surname and second surname;
- Student identification under the current Person model;
- the physical-departure state derived only from Enrollment.IsAuthorizedToLeaveAlone;
- current ACTIVE FamilyAuthorizedPickups with current active AuthorizedPickupAssignments to that Student;
- each pickup's Family-owned relationship label;
- optional pickup identification when recorded;
- pickup mobile phone when recorded by the current model.

AuthorizedPickup information is current live data. No historical pickup is inferred, and no absence of pickup changes the Enrollment flag.

## 6.3 Required States

The visible state is determined exactly as follows:

| Condition | Visible state |
|---|---|
| No Enrollment exists in the ACTIVE AcademicPeriod | `Sin matrícula` |
| Enrollment exists and IsAuthorizedToLeaveAlone is true | `Sí puede salir solo` |
| Enrollment exists, the flag is false and at least one valid current pickup exists | `No puede salir solo`, with the pickup list |
| Enrollment exists, the flag is false and no valid current pickup exists | `Sin persona autorizada registrada` |

The final state requires attention and is never converted into permission to leave alone.

## 6.4 Cardinality and Representations

HTML renders one logical row per Student and lists all current valid pickups inside that Student record.

CSV renders one row per Student–AuthorizedPickup. A Student with no current valid pickup retains one row with atomic pickup columns empty. Student and departure-state values repeat as needed for each pickup row. Existing UTF-8 BOM, deterministic order, quoting and formula-injection protection remain mandatory.

The HTML and CSV representations originate from the same Application dataset and apply the same Grade/Section filter.

# 7. Reusable Multiple Grade/Section Filter

## 7.1 Concept

The filter operates on exact Grade + Section combinations, presented to Secretaría as **grado/paralelo**. Grade alone is not a valid selection unit.

It supports:

- all combinations;
- one exact Grade/Section combination;
- multiple exact Grade/Section combinations whose result is their union.

No Section, including `A`, is hardcoded.

## 7.2 Authoritative Options

For a selected AcademicPeriod, valid options are the distinct complete Grade/Section pairs present in AcademicPlacement of Enrollments in that period, joined to the current Grade and Section catalogs for stable codes, labels and ordering.

The current model contains no AcademicPeriod offering table. Catalog cross-products are therefore not authoritative and must not be offered. Incomplete placements do not create an option, and no artificial `Sin sección` option exists.

For the Inspección report, the selected period is the single ACTIVE AcademicPeriod.

## 7.3 Selection Semantics

- omitted filter means all;
- one pair means only that exact pair;
- multiple pairs mean their union;
- duplicates are normalized;
- malformed, unknown, incomplete or period-external pairs are rejected safely;
- Students without Enrollment or complete AcademicPlacement remain visible under `Todos` when the report's existing population contract includes them;
- those Students never match a specific Grade/Section pair.

The browser selection is only a proposal. Application resolves the period and validates every pair against the authoritative option set before querying report data.

## 7.4 Covered Reports

The reusable filter applies to:

1. Enrollment Summary;
2. Student Enrollment List;
3. the evolved Student and Representative Directory;
4. Billing;
5. Medical;
6. the operational Inspección physical-departure report.

Enrollment Summary is explicitly included. The filter is applied before aggregation, so its totals and breakdowns describe only the selected union.

Every HTML report and corresponding CSV use the same validated filter and logical subset. AcademicPeriod and selected pairs remain preserved when navigating between report representation and export.

Essential selection and submission are server-rendered and work without JavaScript. Progressive enhancement may improve interaction but cannot own correctness or availability.

# 8. Architecture and Delivery

The approved dependency direction remains:

```text
HTTP / UI → Application → Domain → Infrastructure
```

- Application owns search/report criteria, validation, use-case coordination, query ports and immutable read models.
- Infrastructure implements purpose-built prepared PDO projections.
- Controllers parse HTTP input and map safe outcomes; they contain no SQL or dataset business rules.
- Views render already-authorized data; they contain no SQL, selection rules or authority decisions.
- Domain Aggregates and transactional repositories are not expanded for mass search/report composition.
- HTML and CSV reuse the same Application dataset for each report.
- The existing exact-administrator authorization remains in force until a separately approved role milestone replaces it.

The Directory evolution extends ADR-0026. Administrative search and the Inspección report adopt the same proportional read-model pattern without introducing CQRS infrastructure, reporting tables, materialized views or another database.

# 9. Security and Privacy

These capabilities expose PII belonging to Students, Representatives and AuthorizedPickups, including identification, email, phone and address information.

Future implementation must:

- authenticate and enforce the existing administrative authorization on every request;
- revalidate all criteria and selected combinations server-side;
- use POST plus CSRF and `no-store` for Person/Family searches;
- use prepared statements and bounded results;
- keep names, identification, email, phones and addresses out of URLs, logs and flash messages;
- escape every HTML value;
- preserve CSV authorization, safe headers, UTF-8 BOM, native quoting and formula-injection protection;
- export only the fields approved for the selected report;
- use generic safe errors without SQL, stack, filesystem or unnecessary PII disclosure;
- preserve deterministic behavior and fail closed on incoherent multiplicity.

No permission, role, public endpoint or Representative access is added by this baseline.

## 11.1 Implemented Phase 2 contract

- `AcademicPeriod` remains the primary GET selector. Repeated `grade_section[]` values use the stable `GRADE_CODE:SECTION_CODE` representation; omission means **Todos**.
- One Application context resolves the period and its actual complete placement pairs, rejects any malformed, unknown or wrong-period value as a complete request, normalizes duplicates and binds the validated criterion to that period.
- The existing Enrollment Summary, Student Enrollment List, Directory, Billing and Medical projections consume that same criterion. Summary applies it before aggregation, and student reports preserve their previous population only under **Todos**.
- Server-rendered Spanish checkboxes provide keyboard-usable multiple selection and an explicit **Mostrar todos** action without JavaScript. Report navigation and CSV links preserve the normalized selection.
- Infrastructure uses prepared parameters for every selected Grade/Section identity. No route, permission, schema, migration, index, catalog or seeder was added.
- Phase 2 preserved the prior Directory columns and cardinality while introducing the shared filter. Person/Family discovery was reserved for Phase 4 and Inspección for Phase 5; their implemented contracts are recorded below.

## 11.2 Implemented Phase 3 contract

- The existing `/reports/enrollments/directory` HTML and CSV routes continue to use one Application dataset and the Phase 2 AcademicPeriod plus Grade/Section criterion; no second report or route exists.
- The read model exposes atomic Student names and identification plus two optional atomic Representative projections. Each Representative projection contains the current Family relationship label, identification and personal email/mobile/landline contacts; work contact fields are not part of this Directory contract.
- Infrastructure resolves current active Family, active Representative memberships and current StudentAddressAssignment through prepared read-only projections. Representatives are loaded once for the complete Family set rather than through per-row queries.
- Representative 1 is the unique active Primary. With no Primary, both slots are empty even when secondary Representatives exist. With a valid Primary, Representative 2 follows only the exact rule in section 4.6; ambiguity and incoherent multiplicity fail closed.
- The current address must belong to the same current active Family and reference an active FamilyAddress. Valid absence remains empty; multiple or cross-Family assignments fail closed.
- HTML groups the atomic values for readable responsive presentation, while CSV preserves exact atomic columns, deterministic one-row-per-Student cardinality, UTF-8 BOM, native quoting and spreadsheet-formula protection.
- No Domain Aggregate, transactional repository, route, permission, schema, migration, index, catalog or seeder changed.

## 11.3 Implemented Phase 4 contract

- `/persons` and `/families` retain their existing create actions and replace raw-ID lookup forms with one explicit criterion per server-rendered search. `POST /persons/search` and `POST /families/search` use the existing exact-administrator middleware, one-time CSRF and `Cache-Control: no-store`; criteria are never placed in URLs, session or flash.
- Person discovery supports only first name, middle name, first surname and second surname by escaped word prefix with the approved three-character minimum, plus exact normalized identification number and exact validated personal email. It returns current full name, optional identification and optional personal email in the approved deterministic order.
- Family discovery supports exact case-sensitive FamilyCode, display-name word prefix with the same minimum and every approved Person criterion. Person matching uses only `ended_at IS NULL` FamilyRepresentative and FamilyStudent memberships; historical memberships are excluded.
- Family identity rows are selected distinctly and ordered before context is loaded. Every matching current member of each visible Family is represented in deterministic name/role order; no member priority or arbitrary winner is introduced.
- Application query ports and readonly DTOs are implemented separately for Person and Family. PDO adapters use prepared read-only projections, fetch at most 31 Family/Person identities and expose at most 30; an additional row produces the refine-search notice. Transactional repositories and Aggregates are unchanged.
- Existing Person/Family detail GET routes remain compatible and receive the internal ID only through the result action. No phone, fuzzy, phonetic, similarity, pagination, infinite-scroll or multi-criterion semantics were added.
- The query shapes use the existing schema and indexes. No representative-volume MariaDB `EXPLAIN` was available in the local process, so no index observation is elevated into a proposal and no migration or physical change is made.
- Review removed the temporary Family Infrastructure dependency on the concrete Person PDO adapter. `PdoFamilyDiscoveryQuery` translates only the approved Person Application discovery semantics privately, `PdoPersonDiscoveryQuery::predicate()` is private, and permanent regressions preserve both the historical Family Application boundary and the narrow Discovery dependency allowlist.

# 12. Explicit Exclusions

This baseline does not authorize:

- a direct Representative-to-Student relationship;
- historical snapshots of Person, FamilyAddress or AuthorizedPickup;
- a second Directory or one row per Student–Representative relationship;
- phone search, fuzzy search, search pagination or a search engine;
- an Inspection role or user;
- institutional withdrawal, promotion, repetition, graduation or AcademicPeriod opening/closing;
- schema, migration, index, table, column, foreign key, catalog or seeder changes;
- reports outside the six explicitly listed in section 7.4;
- production data access or execution.
