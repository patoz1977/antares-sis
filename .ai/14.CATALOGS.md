# Catálogos del Sistema (CATALOGS)

**Versión:** 2.0
**Estado:** Aprobado
**Última actualización:** Julio 2026

---

# 1. Objetivo

Este documento define la arquitectura, clasificación y reglas de uso de los catálogos oficiales de Antares SIS.

Su propósito es mantener vocabularios estables y reutilizables sin trasladar reglas de negocio al modelo de catálogos. La estructura física definitiva corresponde a `12.DATABASE_DESIGN.md`.

---

# 2. Alcance

Este documento define:

- la clasificación de los catálogos;
- sus responsabilidades;
- las dependencias entre catálogos;
- las convenciones de nomenclatura y códigos;
- los valores funcionales expresamente aprobados.

No define:

- reglas de negocio;
- permisos;
- interfaces de usuario;
- columnas físicas definitivas;
- datos iniciales no aprobados.

---

# 3. Relación con la documentación

- `11.DOMAIN_MODEL.md` define el significado de los conceptos.
- `12.DATABASE_DESIGN.md` define tablas, columnas y restricciones físicas.
- `13.ERD.md` representa las relaciones físicas.
- `20.DECISIONS.md` registra las decisiones permanentes.
- `14.CATALOGS.md` clasifica y gobierna los catálogos.

Ante una discrepancia física prevalece `12.DATABASE_DESIGN.md`. Ante una discrepancia de negocio prevalecen el modelo de dominio y las decisiones aprobadas.

---

# 4. Principios de diseño

Los catálogos deben:

- representar vocabularios estables;
- tener responsabilidad única;
- evitar valores codificados en la aplicación;
- usar códigos funcionales estables;
- evitar duplicación y dependencias circulares;
- permitir desactivación cuando corresponda;
- conservar trazabilidad.

Un catálogo no reemplaza una Entity, un Aggregate ni una regla de negocio.

---

# 5. Clasificación oficial

## 5.1 Infraestructura

Catálogos transversales utilizados para clasificar estados.

| Catálogo | Responsabilidad |
|---|---|
| `status_types` | Define tipos funcionales de estado. |
| `statuses` | Define los estados pertenecientes a cada tipo. |

`status_types` no contiene estados ni se autorreferencia. Cada registro de `statuses` pertenece exactamente a un `status_type`.

Las entidades persisten únicamente `status_id`. La correspondencia del estado con el tipo funcional esperado se valida en el dominio y transaccionalmente en la aplicación.

## 5.2 Referencias generales

Vocabularios reutilizables por identidad, familia y matrícula.

| Catálogo | Responsabilidad |
|---|---|
| `document_types` | Tipos de documentos de identidad. |
| `sexes` | Sexo registrado para una Person. |
| `marital_statuses` | Estado civil registrado para una Person. |
| `education_levels` | Nivel educativo registrado para una Person. |
| `relationship_types` | Relación de una persona de contacto o retiro con el Student. |

`Occupation` no es catálogo. Cuando el dominio requiera ocupación, se conserva como texto libre.

## 5.3 Referencias geográficas

Vocabularios jerárquicos para direcciones familiares.

| Catálogo | Responsabilidad |
|---|---|
| `provinces` | Provincias. |
| `cantons` | Cantones pertenecientes a una Province. |
| `parishes` | Parroquias pertenecientes a un Canton. |

Dependencia obligatoria:

`Province → Canton → Parish`

Un Canton pertenece exactamente a una Province. Una Parish pertenece exactamente a un Canton.

## 5.4 Referencias de Academic Core

Los siguientes conceptos son referencias del Bounded Context Academic Core. Enrollment los consume, pero no es su propietario.

| Referencia | Responsabilidad |
|---|---|
| `grades` | Grados disponibles en la oferta académica. |
| `sections` | Secciones académicas. |
| `academic_periods` | Períodos académicos anuales. |

Su inclusión en este inventario no transfiere su propiedad al dominio Enrollment.

# 6. Convenciones

## 6.1 Nombres físicos

Los nombres de tablas:

- se escriben en inglés;
- usan plural;
- usan `snake_case`;
- no usan prefijos ni abreviaturas ambiguas.

## 6.2 Códigos funcionales

El campo `code`:

- es único dentro de su catálogo o tipo;
- es estable e independiente del idioma;
- no cambia por modificaciones del nombre visible;
- no debe reutilizarse con otro significado;
- es la referencia funcional utilizada por el dominio.

La interfaz puede mostrar `name`; las reglas dependen de `code`.

## 6.3 Activación

La desactivación impide nuevas selecciones sin borrar referencias históricas. Las reglas físicas de integridad y eliminación se definen en `12.DATABASE_DESIGN.md`.

# 7. Estados aprobados

## 7.1 ENROLLMENT_STATUS

| Código | Significado |
|---|---|
| `DRAFT` | Matrícula editable que todavía no ha sido enviada. |
| `SUBMITTED` | Matrícula enviada para revisión institucional. |
| `COMPLETED` | Matrícula completada institucionalmente. |
| `CANCELLED` | Matrícula cancelada. |

## 7.2 USER_STATUS

| Código | Significado |
|---|---|
| `ACTIVE` | Cuenta habilitada para autenticación, salvo bloqueo temporal. |
| `DISABLED` | Cuenta deshabilitada. |

`locked_at` expresa el bloqueo temporal de User y no crea un estado `LOCKED`.

## 7.3 GENERAL_STATUS

| Código | Significado |
|---|---|
| `ACTIVE` | Aggregate Root o recurso configurable habilitado. |
| `INACTIVE` | Aggregate Root o recurso configurable deshabilitado para nuevos usos. |

No toda tabla tiene `status_id`. Las membresías y asignaciones históricas usan vigencia temporal; los snapshots no usan estados.

---

# 8. Valores oficiales

Los códigos de estado de la sección anterior son los únicos valores funcionales consolidados por esta sincronización.

Los valores oficiales de `document_types`, `sexes`, `marital_statuses`, `education_levels`, `relationship_types`, `provinces`, `cantons`, `parishes`, `grades`, `sections` y `academic_periods` deben conservar los datos institucionales ya aprobados o cargarse mediante el proceso de datos maestros correspondiente. Este documento no inventa valores faltantes.

---

# 9. Incorporación de nuevos catálogos

Un nuevo catálogo debe:

1. responder a una necesidad documentada;
2. no duplicar un catálogo existente;
3. tener propietario de contexto definido;
4. documentarse aquí antes de implementarse;
5. incorporarse al diseño físico y al ERD;
6. registrar una ADR cuando altere una decisión arquitectónica.

No debe crearse un catálogo para una regla interna sin necesidad de administración, reutilización o referencia estable.
