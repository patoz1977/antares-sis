# Development Workflow

## Purpose

This document defines the official software development workflow for the project.

All development activities must follow this workflow to ensure consistency, traceability and maintainability.

---

# Development Lifecycle

Every development task follows the same lifecycle:

1. Analysis
2. Design
3. Implementation
4. Validation
5. Documentation
6. Commit
7. Pull Request
8. Merge

No phase should be skipped.

---

# Analysis

Before writing code:

- Understand the business objective.
- Review the existing implementation.
- Identify impacted components.
- Identify risks and assumptions.
- Verify whether existing documentation must be updated.

Deliverable:

- Clear implementation plan.

---

# Design

Before implementation:

- Define the proposed solution.
- Evaluate alternative approaches when necessary.
- Minimize architectural impact.
- Preserve backward compatibility whenever possible.

If the solution affects the architecture, update:

- Architecture
- Domain Model
- Database Design
- ERD
- Decisions

when applicable.

---

# Implementation

Implementation should:

- Follow Coding Standards.
- Respect project architecture.
- Be incremental.
- Avoid unnecessary refactoring.
- Keep commits focused on a single objective.

---

# Validation

Before completing a task:

- Verify functionality.
- Execute available tests.
- Review edge cases.
- Validate business rules.
- Verify documentation consistency.

No task is considered complete until validation succeeds.

---

# Documentation

Documentation is part of development.

When required, update:

- Project Context
- Current Status
- Roadmap
- Architecture
- Domain Model
- Database Design
- ERD
- Decisions
- Development Log

Documentation should be updated before the final commit.

---

# Git Workflow

## Branches

Each feature, enhancement or fix must be developed in its own branch.

Branch naming:

- feature/<identifier>
- fix/<identifier>
- hotfix/<identifier>
- refactor/<identifier>
- docs/<identifier>

---

## Commits

Each commit should:

- Represent a single logical change.
- Be complete.
- Be testable.
- Include related documentation updates.

Avoid mixing unrelated changes.

---

## Pull Requests

Before opening a Pull Request:

- Verify all planned work is complete.
- Verify documentation is updated.
- Verify tests pass.
- Review the changes.

---

## Merge

A branch should only be merged after:

- Validation is complete.
- Documentation is synchronized.
- Pull Request is approved.

---

# Definition of Done

A task is complete only when:

- Requirements are implemented.
- Business rules are satisfied.
- Tests pass.
- Documentation is updated.
- Code has been reviewed.
- Commit has been created.
- Pull Request is ready or merged, according to the project workflow.

---

# General Principles

- GitHub is the single source of truth.
- Documentation evolves together with the software.
- Prefer simple solutions.
- Prefer consistency over complexity.
- Every significant decision must be traceable.
- Technical debt should be recorded instead of ignored.
