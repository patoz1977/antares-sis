# UI/UX and Navigation Baseline

## Purpose

This document is the permanent UI/UX source of truth for E014. It defines the visual, navigation, responsive, accessibility, White Label and Delivery-testing baseline for the existing server-rendered product.

It does not define business rules, authorization, Domain behavior, HTTP contracts, schema, catalogs or future functionality. Those responsibilities remain in their existing official documents and code boundaries.

---

# 1. Approved Functional Decisions

## 1.1 Product UI language

The user-visible language of the MVP is Spanish.

- User-facing navigation, headings, labels, help, actions, validation feedback, statuses and safe error messages are presented in Spanish.
- Code, class names, namespaces, technical routes, table and column names, catalog codes and all other internal identifiers remain in English under the existing conventions.
- Catalog values and codes remain stable and language-independent. Only their user-visible labels may be presented in Spanish when applicable.
- The `en_US.UTF-8` application fallback may remain as a technical runtime fallback; it does not define the UI language.
- The MVP has no i18n infrastructure, locale selector or multilingual content-management scope.
- Existing visible English text is progressively made consistent in Spanish during E014 without changing behavior, validation meaning, POST payloads or HTTP contracts.
- Future internationalization is outside E014 and requires a separately authorized milestone.

## 1.2 Enrollment initiation

The Representative initiates the Representative's own Enrollment process. Secretaría does not initiate Enrollment in the MVP.

The existing administrative Enrollment capabilities remain review, reopen, complete and cancel. UI navigation must expose only implemented and authorized capabilities and must not suggest an administrative initiation action.

# 3. Current Navigation and UX Findings

## 3.1 Navigation

- Administrative navigation starts at Dashboard and relies on repeated manual back links inside each module.
- Representative navigation starts at the Portal hub and uses local links among Acknowledgements, Enrollment and Family Resources.
- There is no persistent application navigation, active destination state, common breadcrumb or mobile navigation.
- Persons and Families are discoverable from Dashboard, but existing records are reached through raw positive-ID forms rather than a list or search capability.
- Navigation visibility is not authority. Authentication and authorization middleware remain mandatory for every route.

## 3.2 Layout

`layouts/app.php` is the common renderer target but currently provides only the document title and content. It lacks language, viewport, controlled CSS/icon assets, application container, context navigation and global feedback.

`dashboard/index.php` and `institutional-acknowledgements/index.php` each contain another complete HTML document inside that layout. E014 Phase 2 must normalize this without changing Controller contracts or screen behavior.

## 3.3 Main UX risks

- Weak orientation and repeated manual return paths.
- Long visually flat forms and multi-concept pages.
- No consistent presentation for validation, success, warning, forbidden, not-found or unexpected-error feedback.
- Actions with different consequences look similar.
- Wide tables have inconsistent responsive handling.
- Internal IDs and status codes are exposed without sufficient user-facing labels in several administrative screens.
- Existing Bootstrap classes are ineffective because no Bootstrap asset is loaded.
- UI text is predominantly English and must be progressively standardized to Spanish under the approved language decision.

# 4. Target Visual Architecture

## 4.1 Shared application shell

One reusable server-rendered shell owns:

- `html`, `head`, charset, viewport and Spanish language metadata;
- escaped page title;
- controlled CSS, Bootstrap Icons and optional page-script assets;
- configurable White Label identity;
- optional context-specific navigation;
- global flash/feedback region;
- main content container;
- a minimal footer only when it contributes useful product context.

Views remain presentation-only fragments. They do not reproduce complete HTML documents or contain business, authorization, repository or SQL logic.

## 4.2 Visual contexts

### Public/Auth

Uses the same visual identity and shell but omits authenticated navigation. Login remains a simple server-rendered form; Forgot Password remains generic assisted-recovery guidance.

### Administrative

The navigation exposes only existing capabilities:

- Dashboard;
- Persons;
- Families;
- Institutional Acknowledgements;
- Enrollments;
- Enrollment Reports;
- Logout.

Billing and Medical remain report destinations inside Enrollment Reports. E014 adds no Finance, Academic Management, Teachers, Courses, Attendance, Grades or Settings module.

### Representative Portal

The navigation exposes only current routes and valid anchors:

- Portal start;
- Personal, Contact and Employment sections within Enrollment;
- Students within the current authorized Family/Enrollment context;
- Family Resources;
- Enrollment;
- Acknowledgements;
- Logout.

No administrative link is rendered to a Representative. Hidden links never replace server-side authorization.

## 4.3 Responsive baseline

- Mobile First is mandatory.
- Desktop uses clear persistent context navigation.
- Mobile uses one simple collapsible navigation pattern.
- Forms use one column on small viewports and multiple columns only for naturally related fields when space permits.
- Long content uses sections and clear headings rather than an unapproved wizard.
- Wide tables use a consistent horizontal-scroll container; information is not silently truncated and tables are not automatically converted to cards.
- Browser zoom and reflow must remain usable.

# 5. Technology and Assets

## 5.1 Bootstrap 5

Bootstrap 5 remains the approved visual foundation from Architecture. E014 introduces no Tailwind, Material UI, React, Vue, Angular or frontend build system.

Project-controlled, version-pinned local assets are preferred over runtime CDN dependencies. This supports local/XAMPP deployment, predictable caching, offline institutional environments and controlled upgrades.

## 5.2 Bootstrap Icons

Bootstrap Icons are the approved icon system. Icons complement visible Spanish labels and never replace the label for an important action.

## 5.3 Alpine.js and JavaScript

Server-rendered operation remains fundamental. Alpine.js is not a general dependency and is not required for Phase 2.

It may be evaluated later only for small progressive enhancements such as disclosure or dismissible UI when Bootstrap or a smaller existing solution is not sufficient. It must not own business state, routing, data fetching, complex forms or validation.

Existing essential CRUD, Enrollment and lifecycle actions remain usable without JavaScript. The approved Enrollment autosave remains progressive enhancement over the HTML/PRG fallback.

## 5.4 Asset organization

The target asset boundary is deliberately small:

- version-pinned vendor CSS/JS/icon assets committed or otherwise controlled by the project;
- one small application stylesheet for layout, White Label variables and targeted adjustments;
- page-specific JavaScript only when behavior already requires it;
- stable public URLs with explicit asset versioning for cache invalidation;
- no remote font dependency or decorative image bundle.

Exact vendor versions and file paths are implementation details to verify in Phase 2, not a reason for a new architecture or build pipeline.

# 6. Reusable Presentation Baseline

Material reusable pieces are limited to:

- page header;
- context navigation;
- breadcrumbs where hierarchy is useful;
- flash alert;
- validation summary;
- field error;
- form group;
- status badge;
- empty state;
- responsive table container;
- action group;
- consequential-action panel;
- AcademicPeriod selector;
- section heading.

They should be small PHP partials/helpers compatible with the current renderer. E014 does not create a general design-system framework.

## 6.1 Forms

- Every control has an explicit associated label.
- Required fields have a consistent textual indicator; HTML attributes do not replace server validation.
- Help text and field errors are associated through native markup and `aria-describedby` only when needed.
- Text inputs, selects, textareas, checkbox/radio groups and disabled/read-only states have consistent presentation.
- Validation summary links or clearly corresponds to invalid fields.
- Primary submit, secondary navigation and cancel/consequential actions are visually distinct.
- Existing required fields, validations, field permissions, names, values, POST payloads and CSRF behavior do not change.

## 6.2 Tables

- Tables use captions when they clarify scope, semantic headers and `scope` attributes.
- Numeric columns align consistently.
- Empty datasets use an explicit empty state.
- Row actions retain visible text and keyboard access.
- Wide administrative and report tables use the shared responsive wrapper.
- E014 adds no sorting, filtering or pagination unless a later authorized phase proves it necessary.

## 6.3 Statuses

`ACTIVE`, `INACTIVE`, `DRAFT`, `SUBMITTED`, `COMPLETED`, `CANCELLED`, reporting-only `NOT STARTED` and acknowledgement states use consistent Spanish visible labels plus status styling. Text is always present; color is supplementary and Domain/catalog codes remain unchanged.

## 6.4 Feedback and errors

- Success, validation error, warning and informational feedback use a consistent alert region.
- Forbidden, not found and unexpected errors use the common shell where compatible with the existing response path.
- Existing HTTP status codes and safe external messages remain unchanged.
- Internal exceptions, credentials and sensitive information are never rendered.
- Dangerous or consequential actions such as deactivate, end assignment, reopen, complete and cancel receive clear labels and visual hierarchy. E014 does not automatically add client-side confirmation or alter operation semantics.

# 7. Accessibility, Security and Quality

## 7.1 Accessibility baseline

- semantic landmarks and hierarchical headings;
- associated form labels;
- complete keyboard navigation;
- visible focus;
- reasonable contrast;
- semantic table headers;
- native HTML before ARIA;
- no information communicated by color alone;
- distinguishable links and buttons;
- usable zoom and mobile reflow.

This is a practical MVP baseline, not a formal WCAG certification claim.

## 7.2 Security preservation

E014 preserves AuthenticationMiddleware, authorization middleware, the temporary exact admin gate, Family-context revalidation, CSRF, POST mutations, PRG, output escaping, safe errors and the prohibition on sensitive URL data.

Client state, disabled controls and navigation visibility are never security boundaries. UI modernization grants no new capability.

## 7.3 Performance and browser support

The interface targets current Chrome, Edge, Safari, Firefox and modern mobile browsers. Internet Explorer and historical polyfills are excluded.

E014 adds no SPA, large JavaScript bundle, remote font dependency, heavy decorative images, general client-state framework or unnecessary animation.

# 8. Focused UX Direction

## 8.1 Representative Portal

The existing page-oriented workflow remains. A lightweight progress/section navigation is justified to expose pending work and move among Representative, Student, Family Resources, Acknowledgements, annual Enrollment and review/submission, but it is not a new wizard or business workflow.

Editable live data and Enrollment-owned annual data must remain visibly distinct. Post-Submission, Reopen and Resubmission presentation must follow the existing lifecycle and the separate live/annual maintenance flags without introducing a new gate.

## 8.2 Administrative Delivery

- Person, Representative, Student and Family creation forms require clear semantic sections.
- Family detail should act as the navigation context for memberships, resources and Representative User management.
- Institutional Acknowledgements must distinguish AcademicPeriod lifecycle from Requirement lifecycle.
- Enrollment queue and review must make state, annual context and consequential actions clear.
- Reports keep their dedicated hub and shared period navigation.
- Raw-ID lookup remains existing functionality during E014; adding search or list behavior would require separately authorized functional scope.

# 9. Validation Strategy

## 9.1 Automated

- complete existing functional suite and three HTTP/session scenarios;
- exact route inventory;
- material HTML structure and shared-shell assertions;
- authentication and authorization regression;
- CSRF and PRG regression;
- output escaping/XSS coverage;
- fundamental no-JavaScript flows;
- focused assertions for Spanish visible navigation/labels without binding every Bootstrap class.

Tests must not become a snapshot of incidental class names or whitespace.

## 9.2 Runtime

Validate authenticated Public/Admin/Representative navigation, forms, tables, reports and error states on desktop and mobile viewports, with keyboard-only operation and with JavaScript disabled for fundamental operations.

## 9.3 Manual visual checklist

For each context verify:

1. identity and current location are clear;
2. navigation contains only real authorized destinations;
3. headings and Spanish labels are consistent;
4. focus, keyboard order and contrast are usable;
5. forms reflow without horizontal page scrolling;
6. tables scroll inside their container without losing important content;
7. success, error, empty and read-only states are understandable;
8. dangerous/consequential actions are distinguishable;
9. no institution-specific branding or content is hard-coded;
10. no-JavaScript fundamental behavior remains intact.

---

# 10. White Label Strategy

The existing product is White Label. No institution name, institutional logo, domain, colors or content may be hard-coded.

The minimum E014 implementation target is trusted application configuration for:

- application/institution display name;
- optional logo;
- primary visual identity expressed through a small controlled set of CSS variables.

The current `app_name` setting is insufficient for the complete target and is recorded as a gap. E014 must not add tenant tables, database-driven themes, arbitrary uploaded CSS or a complex theme engine.

The historical project name may remain in technical/project documentation. User-visible identity must come from the approved White Label configuration boundary.

# 11. E014 Delivery Plan

1. **Phase 1 — UI/UX Discovery & Baseline:** audit and this documentation baseline.
2. **Phase 2 — Shared Shell & Navigation:** controlled assets, common shell, contextual navigation, Dashboard, shared components and error/flash baseline.
3. **Phase 3 — Administrative UI:** Persons, Families, Institutional Acknowledgements, Enrollment Administration and Enrollment Reports.
4. **Phase 4 — Representative Portal UI:** Representative/Student live data, Family Resources, Enrollment, Acknowledgements and review/submission.
5. **Phase 5 — Responsive, Accessibility & Validation Closure:** cross-cutting desktop/mobile/keyboard, security/XSS/no-JavaScript/runtime validation and closure documentation.

Each implementation phase preserves existing business rules, authorization, routes and payloads unless a separately approved defect correction explicitly authorizes otherwise.

E015 — Bulk Import Baseline follows completed E014. MVP Validation & Closure follows completed E015. This document does not design either milestone.

# 12. Architecture and Data Impact

- No ADR is required for Bootstrap 5, Bootstrap Icons, server-rendered-first Delivery, visual preferences or the Phase 1 asset proposal because existing Architecture already approves the technology and no rendering architecture changes.
- Phase 1 has no product-code change.
- Phase 1 has no schema, migration, table, column, index, seeder or catalog impact.
- Any future need for schema-backed branding, multilingual content or a different rendering architecture requires explicit analysis and authorization outside this baseline.
