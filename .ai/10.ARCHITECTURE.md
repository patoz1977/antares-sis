# ARCHITECTURE

**Proyecto:** Antares SIS
**Versión:** 2.0
**Estado:** Aprobada
**Última actualización:** 2026-07-30

## 1. Propósito

Este documento define la arquitectura oficial de Antares SIS. Toda implementación evoluciona de forma incremental hacia estas reglas; una desviación permanente requiere ADR.

## 2. Objetivos

- claridad, mantenibilidad y pruebas;
- bajo acoplamiento y responsabilidades explícitas;
- compatibilidad con hosting compartido;
- crecimiento modular sin microservicios prematuros;
- seguridad y aislamiento institucional;
- White Label con un único código fuente.

## 3. Stack tecnológico

- PHP 8.2;
- Composer y PSR-4;
- framework propio separado de la aplicación;
- PDO y MySQL 8;
- Bootstrap 5, Bootstrap Icons, Alpine.js y JavaScript Vanilla;
- diseño Mobile First.

Toda dependencia nueva requiere justificación técnica y aprobación.

## 4. Estilo arquitectónico

Antares SIS es un **modular monolith**. MVC permanece en la capa de entrega; el núcleo usa capas explícitas:

```text
HTTP / UI
    ↓
Application
    ↓
Domain
    ↓
Infrastructure
```

Las dependencias apuntan hacia Domain. Domain no depende de HTTP, interfaz, PDO, sesiones ni implementaciones de Infrastructure.

## 5. HTTP / UI

### Front Controller

Inicializa configuración, autoloading, errores, sesión y Router. No contiene reglas de negocio.

### Router y Middleware

Resuelven rutas y ejecutan controles transversales. No acceden directamente a persistencia.

### Controllers

Adaptan HTTP, validan forma básica de entrada, invocan Application Services y construyen respuestas. No contienen invariantes, autorización contextual ni SQL.

### Views

Presentan datos preparados. No contienen SQL, reglas de negocio ni validaciones complejas; escapan salida según contexto.

## 6. Application

Application Services orquestan casos de uso, autorización, límites transaccionales y colaboración entre Aggregates. Pueden utilizar contratos de Repository y servicios de infraestructura mediante interfaces.

No reemplazan las invariantes del dominio. Entregan valores como el tiempo actual a los Aggregates y publican efectos externos solo después del commit.

## 7. Domain

Domain contiene:

- Aggregate Roots y Entities;
- Value Objects;
- invariantes y comportamiento;
- Domain Services para reglas cross-Aggregate;
- Domain Events que expresan hechos aprobados;
- contratos conceptuales necesarios para cargar y guardar Aggregates.

Business invariants belong to Aggregates, Entities and Value Objects. Cross-Aggregate business rules belong to Domain Services. Use-case orchestration, authorization and transaction coordination belong to Application Services. Controllers and Repositories do not contain business rules.

Los objetos de dominio no son Models anémicos: protegen su estado y exponen operaciones con significado. No conocen HTML, SQL, HTTP ni PDO.

## 8. Infrastructure

Infrastructure implementa:

- Repositories con PDO y consultas parametrizadas;
- transacciones;
- sesiones;
- password hashing;
- email y SMS;
- almacenamiento de archivos;
- reloj, auditoría y adaptadores externos.

Los contratos de Repository se definen cerca de Domain o Application; sus implementaciones viven en Infrastructure. Repository no contiene reglas de negocio.

## 9. Bounded Contexts

El MVP se divide lógicamente en:

```text
identity_access
family_management
academic_core
enrollment
catalogs
institutional_documents
```

Cada contexto posee sus conceptos y publica contratos explícitos. La integración usa identificadores, Application Services y Domain Events aprobados; ningún módulo obtiene acceso irrestricto a estructuras internas de otro.

La estructura física del código puede evolucionar gradualmente. Esta decisión no obliga a una migración masiva de carpetas durante la reconstrucción documental.

## 10. Autorización contextual

Authentication establishes User identity. Authorization validates the requested institutional role, active membership and selected Family on the server for every protected operation.

Cadena del Representative Portal:

```text
User
→ Person
→ Representative
→ FamilyRepresentative activo
→ Family seleccionada
```

La selección enviada por el cliente nunca constituye autorización. El control combina identidad, rol, relación activa, recurso solicitado y contexto Family; no se limita a autorización genérica por roles.

## 11. Persistencia

Toda comunicación con MySQL usa PDO y Prepared Statements. No se permite:

- SQL en Controllers o Views;
- concatenación de valores en consultas;
- acceso directo a PDO fuera de Infrastructure;
- relaciones implícitas sin documentación física.

`12.DATABASE_DESIGN.md` es la fuente oficial del modelo físico y `13.ERD.md` su representación. El dominio gobierna la persistencia.

## 12. Multiinstitución y aislamiento

Una instancia desplegada utiliza una base de datos por institución. El producto conserva un único código fuente y configuración independiente por institución. No se añade `institution_id` a todas las tablas del MVP.

Credenciales, configuración, archivos y base de datos se aíslan por despliegue institucional. Cambiar esta estrategia requiere una nueva ADR.

## 13. White Label y configuración

Nombre, logotipo, colores, favicon y opciones institucionales provienen de configuración, nunca de reglas codificadas en el núcleo. No se crean variantes de código por institución.

## 14. Seguridad

La arquitectura exige:

- Prepared Statements;
- hash seguro de contraseñas y ausencia de credenciales reversibles;
- CSRF, escape de salida y validación de entrada;
- regeneración y manejo central de sesión;
- autorización contextual en servidor;
- errores sin filtración de información sensible.

Los controles detallados pertenecen a `31.SECURITY_GUIDELINES.md`.

## 15. Errores y observabilidad

Las excepciones se propagan al manejador central. `die`, `exit` y `var_dump` no son mecanismos normales de control. Las operaciones críticas deben permitir auditoría sin acoplar el dominio a una implementación concreta.

## 16. Organización e independencia

`core/` contiene infraestructura reutilizable del framework y nunca depende de `app/`. `app/` contiene la aplicación y puede depender de `core/`.

La evolución por módulos debe respetar capas internas y evitar dependencias circulares. SOLID, DRY, KISS y YAGNI guían decisiones, con claridad sobre abstracción prematura.

## 17. Flujo de caso de uso

```text
HTTP Request
→ Router / Middleware
→ Controller
→ Application Service
→ Aggregate / Domain Service
→ Repository contract
→ Infrastructure implementation
→ Commit
→ post-commit effects
→ HTTP Response / View
```

## 18. Restricciones

No se permite:

- reglas de negocio en Controllers, Views o Repositories;
- Models pasivos como sustituto obligatorio de Aggregates con comportamiento;
- Domain dependiente de Infrastructure;
- acceso contextual confiado al cliente;
- dependencias circulares;
- configuración institucional escrita directamente en código;
- introducir microservicios sin una decisión arquitectónica.

## 19. Evolución

La arquitectura se adopta incrementalmente. Cada módulo nuevo respeta estas fronteras; el código existente se migra al tocarse, con pruebas y commits acotados. Las decisiones relevantes se registran en `20.DECISIONS.md` antes de implementación.
