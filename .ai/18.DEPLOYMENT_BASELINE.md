# Manual Shared Hosting Deployment Baseline

**Version:** 1.3
**Status:** DEPLOY-001 completed, validated and merged through PR #83
**Last updated:** 2026-09-15

---

# 1. Purpose

This document is the permanent operational baseline for manually installing the Antares SIS MVP on supported shared hosting. It defines the production layout, local preparation, environment configuration, institutional `install.sql` contract, White Label assets and minimum verification procedure.

Migrations remain the development source of truth for the physical schema. This document does not define business rules, schema changes, institution-independent catalog values or an automated deployment system.

`14.CATALOGS.md` governs product-level catalog definitions, stable codes, semantics and general catalog rules. This deployment baseline owns only the concrete institution-approved initial values required by the current installation contract. The subsequent persistent local review, owner acceptance and formal MVP closure procedure belongs to `19.MVP_VALIDATION_BASELINE.md`.

---

# 2. Target Environment

The supported target is shared hosting managed by a technical operator with:

- cPanel or equivalent hosting control panel;
- File Manager or FTP;
- phpMyAdmin;
- database and database-user management;
- PHP version and extension selection;
- domain or subdomain DocumentRoot management;
- HTTPS.

The production hosting is assumed to have no SSH, terminal, Composer or permission to execute project CLI scripts. Composer and any PHP CLI preparation happen on the operator's local computer before upload. Production installation never runs `php bin/migrate`.

MariaDB 10.4.32 or later is the first supported physical target because that engine has the accumulated approved repository evidence. MySQL 8 requires validation of the exact installation SQL before use.

# 3. Supported Layout

DEPLOY-001 supports one layout:

```text
/home/account/antares-sis/
├── .env
├── app/
├── bin/
├── bootstrap/
├── config/
├── core/
├── database/
├── resources/
├── routes/
├── storage/
├── vendor/
└── public/                  ← domain/subdomain DocumentRoot
    ├── index.php
    ├── .htaccess
    ├── css/
    ├── js/
    ├── vendor/
    └── institution/
```

The project root and `.env` stay outside the DocumentRoot. `public/` is the only web-accessible application directory. The current front controller resolves the application root through `dirname(__DIR__)`; no configurable root or split-root is part of this baseline.

A hosting provider that cannot point a domain or subdomain to this internal `public/` directory is not supported by DEPLOY-001 and requires separate evaluation before deployment.

# 4. PHP Requirements

Required:

- PHP 8.2, 8.3 or 8.4;
- PDO;
- `pdo_mysql`;
- `mbstring`;
- `session`;
- `dom`;
- `fileinfo`;
- `filter`;
- `libxml`;
- `xmlreader`;
- `zip`.

`opcache` is recommended but not required. The operator enables these extensions in cPanel before opening the application. DEPLOY-001 adds no runtime preflight subsystem.

The hosting must allow uploads larger than the approved 5 MiB Bulk Import maximum and provide a private writable PHP session path. The project `storage/` directory must be writable by the application while remaining outside `public/`.

# 5. Local Preparation

On a trusted local computer, start from the exact approved release and run:

```text
composer install --no-dev --optimize-autoloader
```

Composer is not required on the hosting. The resulting `vendor/` directory is copied with the application.

Prepare the institution-specific `.env` before upload. Use `.env.example` as a production-safe checklist and replace every `CHANGE_ME` value. The production contract includes only:

- `APP_NAME`;
- `APP_LOGO_PATH`;
- `APP_FAVICON_PATH`;
- `APP_PRIMARY_COLOR`;
- `APP_ASSET_VERSION`;
- `APP_ENV`;
- `APP_DEBUG`;
- `APP_TIMEZONE`;
- `APP_LOCALE`;
- `DB_CONNECTION`;
- `DB_HOST`;
- `DB_PORT`;
- `DB_DATABASE`;
- `DB_USERNAME`;
- `DB_PASSWORD`;
- `DB_CHARSET`;
- `AUTH_MAX_FAILED_ATTEMPTS`;
- `AUTH_LOCKOUT_DURATION_SECONDS`.

Production uses `APP_ENV=production` and `APP_DEBUG=false`. Database credentials and institution-specific values never enter Git.

# 6. Files to Upload

Copy the production runtime:

- `app/`;
- `bin/`;
- `bootstrap/`;
- `config/`;
- `core/`;
- `database/`;
- `resources/`;
- `routes/`;
- `storage/` without local runtime contents;
- `vendor/` prepared locally;
- `public/`, including hidden `.htaccess`;
- `composer.json` and `composer.lock`;
- the institution-specific `.env`.

Do not upload:

- `.git/`;
- `.ai/`;
- `tests/`;
- local caches, logs, sessions, uploads or temporary workbooks;
- SQL dumps, installation SQL or backups;
- data or configuration from another institution.

`install.sql` is selected from the local computer in phpMyAdmin and is never copied into the hosting filesystem.

# 7. Hosting Preparation and Installation

1. Create a completely empty database in cPanel.
2. Create a dedicated database user.
3. Assign that user exclusively to the institutional database with the privileges needed by the imported schema and runtime.
4. Select PHP 8.2–8.4 and enable every required extension.
5. Upload the prepared runtime and `.env` through File Manager or FTP.
6. Point the domain or subdomain DocumentRoot to `<application-root>/public`.
7. Confirm that `storage/` and the PHP session path are private and writable.
8. Open phpMyAdmin and select the empty database.
9. Choose **Import**, select the institution-specific `install.sql` directly from the local computer and execute it.
10. Validate the import result before opening the product.
11. Copy the approved logo and favicon into `public/institution/`.
12. Open `/login` over HTTPS and authenticate as `admin`.

No installation SQL should remain stored on the hosting after import.

# 8. Phase 2 `install.sql` Contract

Phase 1 does not create `install.sql`. Phase 2 prepares one manual institution-specific artifact for a completely empty database. It is local, sensitive, unversioned and outside the product repository. Its completion requires institution-approved catalog rows and administrator Person data; repository examples or earlier conversations are not authority for those values.

Migrations `001–011` remain the schema authority. Before use, the SQL must pass automated structural parity against a disposable database built from those migrations.

The SQL shall contain:

- the final schema;
- the compatible migration ledger for `001–011`;
- `status_types`;
- `statuses`;
- institution-approved `document_types`;
- institution-approved `sexes`;
- institution-approved `relationship_types`;
- initial `grades`;
- initial `sections`;
- the initial `academic_periods` row or rows;
- the administrative Person;
- the User whose login and normalized login are both `admin` and whose status is `USER_STATUS / ACTIVE`;
- only a PHP-generated value in `users.password_hash`.

# 9. Initial Administrator and Password

The initial administrator consists of:

1. one Person satisfying the current Person invariants;
2. one User associated with that Person;
3. `login_identifier = admin`;
4. `normalized_login_identifier = admin`;
5. `USER_STATUS / ACTIVE`;
6. a valid PHP password hash.

The Person is not automatically a Representative, Student or Family member.

The operator defines the plaintext password locally. DEPLOY-001 introduces no additional password-complexity policy. Generate the hash using `password_hash($password, PASSWORD_DEFAULT)` and copy only the result into `users.password_hash`.

One optional local PowerShell procedure that avoids placing the plaintext in command history is:

```powershell
$adminSecret = Read-Host "Initial admin password" -AsSecureString
$adminPlain = [Net.NetworkCredential]::new("", $adminSecret).Password
$env:ANTARES_ADMIN_PASSWORD = $adminPlain
php -r '$p=getenv("ANTARES_ADMIN_PASSWORD"); echo password_hash($p, PASSWORD_DEFAULT), PHP_EOL;'
Remove-Item Env:ANTARES_ADMIN_PASSWORD
$adminPlain = $null
$adminSecret.Dispose()
```

This is an operator procedure, not product tooling. The plaintext must never be inserted into the database, copied into `install.sql`, committed, documented or logged. A future manual password replacement through phpMyAdmin must likewise replace `password_hash` with a newly generated PHP hash, never plaintext.

# 10. White Label Branding

Institutional public assets belong in:

```text
public/institution/
├── logo.png
└── favicon.ico
```

The real assets are deployment-owned and ignored by Git. Configure them through:

```text
APP_LOGO_PATH=/institution/logo.png
APP_FAVICON_PATH=/institution/favicon.ico
```

The existing White Label boundary validates that configured assets exist inside the canonical public directory. DEPLOY-001 adds no branding UI, database configuration, manifest or theme engine.

---

# 11. Production Errors

Production must use:

```text
APP_ENV=production
APP_DEBUG=false
```

PHP diagnostics are disabled before bootstrap. Production never exposes exception messages, stack traces or internal paths and preserves the generic HTTP 500 response. Local or development diagnostics are permitted only when `APP_DEBUG=true`.

DEPLOY-001 introduces no logging framework, correlation identifier, external logging service or observability subsystem.

---

# 12. Initial Verification and Backup

After import:

1. confirm the expected schema and migration ledger;
2. open `/login` over HTTPS;
3. authenticate as `admin`;
4. confirm the configured name, color, logo and favicon;
5. confirm no SQL dump, backup or secret is reachable below `public/`;
6. create an initial backup of the database, `.env` and institutional branding.

The operator stores backups outside the DocumentRoot.

---

# 13. Future Upgrade Rule

When a future release introduces a migration, that release must also provide ordered equivalent SQL instructions for installations without terminal access. The operator must back up the database, `.env`, branding and required files before copying the release and importing its SQL through phpMyAdmin.

DEPLOY-001 does not create a delta generator, migration compiler, update framework, automatic updater or rollback automation.

---

# 14. Scope Boundary

This baseline deliberately excludes installer wizards, provisioners, manifests, remote Composer, hosting CLI commands, split-root support, configurable application roots, release pipelines, automatic SQL generation, generic catalog provisioning, new seeders, schema changes and demonstration data.

Phase 2 owns the institutional SQL, automated parity check and fresh manual-installation rehearsal. DEPLOY-001 is complete and merged. The persistent review installation and MVP acceptance process that follows is governed separately by `19.MVP_VALIDATION_BASELINE.md` and is not part of this deployment baseline.

# 15. Phase 2 Local Validation Harness

The repository exposes the test-only command:

```text
composer test:deployment
```

It requires explicit process environment values and never loads the project `.env` for database-test authority:

- `E0041_DB_HOST`;
- `E0041_DB_PORT`;
- `E0041_DB_USERNAME`;
- explicitly defined `E0041_DB_PASSWORD`, which may be empty;
- safe disposable `E0041_DB_PREFIX`;
- `E0041_DB_ALLOW_DISPOSABLE=1`;
- `DEPLOY001_INSTALL_SQL_PATH`, pointing to the external institution-specific SQL artifact;
- `DEPLOY001_ADMIN_PASSWORD`, used only to verify the PHP hash and real authentication flow;
- `DEPLOY001_RUNTIME_ROOT`, pointing to a prepared local production runtime outside the repository.

The existing disposable-prefix and UEAnt protections remain mandatory. Legacy `E0041_ADMIN_PERSON_ID` and `E0041_ADMIN_INITIAL_PASSWORD` must be unset so the migration-built reference database contains only global system seed data.

All rehearsal-only database values, safe prefixes and random database names, filesystem paths, temporary branding and administrator password/hash are local technical inputs selected or generated by the validating engineer. They are not institutional decisions, are never requested through chat, remain outside Git and are removed after the rehearsal. The real installation operator may replace the external artifact's rehearsal hash with a locally generated hash for the institution's chosen initial password before the definitive import.

The harness creates two random disposable databases under the authorized prefix. Base A runs the current migrations and seeders and becomes the physical schema reference. Base B imports only the autonomous external `install.sql`. The comparison covers tables, columns, types, nullability, defaults, generated expressions, character sets/collations, engines, primary and unique keys, indexes, checks, foreign keys/actions, AUTO_INCREMENT semantics and the migration ledger. The expected migration list and physical inventory derive from the checked-out repository rather than from a duplicated SQL schema definition.

After parity, the harness verifies the approved system statuses, institution-required active catalogs, exactly one initial ACTIVE AcademicPeriod, the single admin Person/User with a PHP-verifiable hash, approved empty catalogs, absence of demo/domain data, a real `/login` authentication roundtrip, administrative Dashboard access, temporary White Label name/color/logo/favicon and the local-only no-pending-migration check. The prepared runtime contains no `.git`, `.ai`, tests or pre-existing `.env`; temporary environment, sessions, logs and branding assets are removed after the rehearsal.

Every database created by the harness is dropped in `finally`, followed by a zero-residual prefix check. A failed import is not repaired: the disposable database is discarded and the rehearsal must be repeated from a fresh empty database. The external SQL remains untracked, contains no database-selection commands or credentials and is never copied into the runtime or DocumentRoot.

As of 2026-09-13, the reusable loader, schema inspector, parity/rehearsal harness and focused tests are implemented and validated. The final fresh rehearsal used an external untracked `install.sql` and a clean disposable MariaDB 10.4.32 instance.
