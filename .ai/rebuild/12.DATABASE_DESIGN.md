# DATABASE DESIGN — Clean Enrollment Rebuild

## Propósito y autoridad documental
Especificación física MySQL 8 derivada de Enrollment Domain Discovery. Las entidades de dominio usan auditoría y soft delete salvo los hijos de snapshot, que son dependientes. Unicidad activa se implementa con columnas generadas STORED y UNIQUE; nunca UNIQUE(..., deleted_at).

# Tabla: status_types

## Propósito
Persistir Status en el contexto Catalogs.

## Columnas
| Columna | Tipo MySQL | Null | Default | Generada | Descripción |
|---|---|---:|---|---|---|
| id | BIGINT UNSIGNED | No | AUTO_INCREMENT | No | Campo de Status. |
| code | VARCHAR(50) | No |  | No | Campo de Status. |
| name | VARCHAR(150) | No |  | No | Campo de Status. |
| description | VARCHAR(255) | Sí | NULL | No | Campo de Status. |
| display_order | SMALLINT UNSIGNED | No | 0 | No | Campo de Status. |
| is_active | TINYINT(1) | No | 1 | No | Campo de Status. |

## Clave primaria
`id BIGINT UNSIGNED AUTO_INCREMENT`.

## Claves foráneas
Cada `*_id` funcional referencia la PK de la tabla singular correspondiente; ON UPDATE RESTRICT y ON DELETE RESTRICT. Los tres hijos de snapshot usan ON DELETE CASCADE desde enrollment_submission_snapshots.

## Restricciones UNIQUE
Cada columna generated `active_*` tiene índice UNIQUE. family_students además usa UNIQUE(family_id, student_id, started_at).

## Restricciones CHECK
Flags TINYINT(1) usan CHECK IN (0,1); latitude CHECK BETWEEN -90 AND 90; longitude CHECK BETWEEN -180 AND 180 cuando existan.

## Columnas generadas
Cada `active_*` se declara con su tipo mostrado, `GENERATED ALWAYS AS (IF(deleted_at IS NULL, CONCAT_WS(':', columnas_funcionales), NULL)) STORED`; family_students usa `IF(ended_at IS NULL AND deleted_at IS NULL, student_id, NULL)`; las asignaciones incluyen family_id y miembro.

## Índices
PK(id), UNIQUE anteriores e índice no único por cada FK.

## Reglas de eliminación
Soft delete para entidades; recursos asignados usan RESTRICT. Los hijos de snapshot se sustituyen al reenvío dentro de la transacción.

## Reglas de integridad
No se usan FKs polimórficas. Contactos y pickups familiares no tienen person_id.

## Validaciones transaccionales
La aplicación valida Family común para Student, recurso y Representative; valida autorización de quien acepta o envía; snapshot y lifecycle son atómicos.

## Observaciones
La relación activa depende de ended_at, deleted_at y columna generated cuando exista.
