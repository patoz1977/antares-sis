# DATABASE DESIGN

**Versión:** Rebuild 1.0
**Estado:** Borrador de reconstrucción documental
**Motor:** MySQL 8 / InnoDB
**Charset / Collation:** utf8mb4 / utf8mb4_unicode_ci

## 1. Propósito
Diseño físico implementable del dominio aprobado: MySQL 8, tablas, columnas, claves, constraints, índices y validación transaccional.

## 2. Relación con otros documentos
DOMAIN_MODEL y ENROLLMENT_DOMAIN_DISCOVERY gobiernan el dominio; ERD debe coincidir; CATALOGS define referencias y DECISIONS conserva ADR.

## 3. Alcance
Identity & Access, Family Management, Academic Core, Institutional Documents, Enrollment y snapshots.

## 4. Exclusiones
Pagos, operación financiera, rutas de transporte, portal de estudiantes, archivos binarios y firma digital.

## 5. Convenciones generales
MySQL 8, InnoDB, utf8mb4, snake_case, tablas plurales, PK `id BIGINT UNSIGNED AUTO_INCREMENT`, FKs explícitas, timestamps consistentes, una base por institución y sin institution_id. No ENUM; estados usan status_types/statuses. Soft delete no se usa; ended_at y status preservan historia. Generated columns STORED resuelven unicidad condicional.

## 6. Estrategia de integridad
PK, FK, UNIQUE, CHECK y generated columns protegen reglas expresables. Las reglas entre filas o Aggregates se validan transaccionalmente y nunca solo en el cliente.

## 8. status_types

### Purpose
Persistir status_types conforme al modelo aprobado.

### Aggregate ownership
Según DOMAIN_MODEL.

### Columns
| Column | MySQL type | Unsigned | Nullable | Default | Generated | Description |
|---|---|---|---|---|---|---|
| id | BIGINT | Yes | No | AUTO_INCREMENT | No | Primary key. |
| status_id | BIGINT | Yes | No | — | No | Estado cuando aplica. |
| created_at | TIMESTAMP | No | No | CURRENT_TIMESTAMP | No | Auditoría. |
| updated_at | TIMESTAMP | No | No | CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | No | Auditoría. |

### Primary key
pk_status_types (id).

### Foreign keys
FKs explícitas con ON DELETE RESTRICT y ON UPDATE RESTRICT; snapshot children usan CASCADE desde su raíz.

### Unique constraints
UNIQUE de códigos, identidad, relaciones activas y student_id + academic_period_id para enrollments.

### Check constraints
CHECK de booleanos, fechas y dependencias médicas cuando aplique.

### Generated columns
Claves activas STORED con CASE WHEN ended_at IS NULL THEN clave ELSE NULL END y UNIQUE asociado cuando la relación conserva historia.

### Indexes
PK, UNIQUE, FKs y consultas por estado, período, Family y Student; sin índices duplicados.

### Delete rules
RESTRICT para identidad e historia; CASCADE únicamente para hijos internos del snapshot.

### Integrity rules
No referencias polimórficas; asignaciones y recursos deben pertenecer a la misma Family.

### Transactional validation
Validar acceso, Family común, relaciones activas, documentos y lifecycle; Submission modifica solo Enrollment y sus hijos.

### Lifecycle and history
ended_at y status preservan historia sin eliminar hechos institucionales.

### Notes
MySQL 8 / InnoDB / utf8mb4.

## 9. Reglas de Enrollment
enrollments contiene Student, Family, AcademicPeriod, Grade, Section, BillingInformation, MedicalInformation, TransportInformation, is_authorized_to_leave_alone y lifecycle. billing_address VARCHAR(255) NOT NULL es texto libre anual, no referencia FamilyAddress, geografía ni Geolocation. MedicalInformation usa flags y detalles condicionales; CHECK exige detalle cuando una bandera es true. No se incluyen dosis, frecuencia, póliza, ruta, proveedor, conductor ni observaciones de transporte.

## 10. Generated columns obligatorias
family_representatives usa claves activas para Family+Representative y principal por Family; family_students usa active_student_id; asignaciones, contactos y pickups usan claves activas STORED y UNIQUE asociado.

## 11. Validaciones transaccionales
Family mantiene representante activo; Student tiene una Family activa; recursos no se eliminan asignados; Submission valida Draft, acceso, membresía, recursos, documentos y crea o reemplaza snapshot; Reopening, Completion y Cancellation respetan sus transiciones.

## 12. Orden de creación y dependencias
Catálogos, geografía, identidad, roles, Family, recursos, Academic Core, documentos, Enrollment, acceptances y snapshot.

## 13. Decisiones físicas pendientes
Ninguna indispensable.
