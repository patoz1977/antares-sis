# Post-import Academic Initialization Baseline

## Purpose

This document defines the permanent functional, application, delivery and operational baseline for initializing annual AcademicPlacement after an approved institutional bulk import has created Students and Families without Enrollment.

It is a separate administrative capability. It does not change the responsibility or contract of E015.

---

# 1. Confirmed Incident and Ownership

The first institutional E015 execution correctly imported 172 Families, 310 Representatives and 231 Students. The E013 Student Enrollment List subsequently showed blank Grade and Section because those values are owned by AcademicPlacement inside the annual Enrollment, while E015 deliberately excludes Enrollment and AcademicPlacement.

The reporting result was therefore consistent with the approved model: an ACTIVE Student without Enrollment for the selected AcademicPeriod is represented as reporting-only `NOT STARTED`, with no Grade or Section.

This correction does not reinterpret E015 and does not move Grade or Section into Student.

---

# 2. Authorized Outcome

For each eligible manifest row, the operation resolves:

`institutional_code → Student → active Family → AcademicPeriod code → Grade code → Section code → Enrollment`

The only permitted writes are:

- create an Enrollment in `DRAFT` with the requested AcademicPlacement when none exists; or
- set AcademicPlacement on an existing `DRAFT` that has no placement.

The operation never creates BillingInformation, MedicalInformation, TransportInformation, leave-alone information, Institutional Acknowledgements or lifecycle transitions. It does not modify Person, User, Representative, Student, Family or membership data.

The real installation expects 231 unique Students, the `2026-2027` AcademicPeriod, the 14 approved Grade codes and Section `A`. Those values are operational expectations, not hard-coded product rules. The product accepts an explicit AcademicPeriod code and resolves every physical identity server-side.

---

# 3. Manifest Contract

The manifest is a UTF-8 CSV with exactly these headers and no additional columns:

```text
institutional_code,grade_code,section_code
```

It contains no physical IDs and no unnecessary personal data. Limits are 1 MiB and 1,000 data rows. Every row must contain three non-empty values of at most 100 characters. Grade and Section codes use only uppercase letters, digits, hyphen and underscore. Formula-leading and control-character values are rejected.

Duplicate `institutional_code` values are rejected. Preflight also rejects the complete batch if distinct supplied codes resolve to the same Student identity.

The institutional manifest is operational data and remains outside Git.

---

# 4. Complete Preflight

Preflight is read-only and validates the complete batch before Apply becomes available. It resolves and validates:

- one ACTIVE Student per institutional code;
- one authoritative active Family context for that Student;
- one ACTIVE AcademicPeriod by code;
- ACTIVE Grade and Section references by code;
- current Enrollment state for Student + AcademicPeriod;
- manifest structure, values, bounds and identity uniqueness.

Preflight classifies every valid row as follows:

| Current state | Classification | Apply behavior |
|---|---|---|
| No Enrollment | `CREATE_DRAFT` | Create one DRAFT with the requested placement. |
| DRAFT without placement | `SET_PLACEMENT` | Set the requested placement. |
| DRAFT with the exact placement | `ALREADY_CORRECT` | No write. |
| DRAFT with different placement | `CONFLICT` | Block the complete batch. |
| SUBMITTED, COMPLETED or CANCELLED | `CONFLICT` | Block the complete batch. |
| Missing, inactive, ambiguous or corrupt reference | issue | Block the complete batch. |

Any conflict or issue prevents all writes.

---

# 5. Atomicity, Idempotency and Concurrency

Apply requires a successful preview produced for the same authenticated administrator, exact file SHA-256 and authoritative state digest. The grant is opaque, actor-bound, expires after 15 minutes and is consumed once.

Apply reruns complete preflight and then uses one Application-owned transaction for the whole batch. It stabilizes the ACTIVE AcademicPeriod context, locks Students in deterministic institutional-code order, revalidates the active Family, locks any existing Enrollment and compares the complete locked state with the preview before the first write.

Creation reuses `EnrollmentDraftInitializer`. Placement mutation uses the existing Enrollment Aggregate and persistence verification. The physical unique Student + AcademicPeriod constraint remains the final race guard.

If any authoritative state changed, any row conflicts or any persistence operation fails, the entire transaction rolls back. Reapplying an unchanged successful manifest produces only `ALREADY_CORRECT` results and no duplicate Enrollment or placement mutation.

---

# 6. Administrative Delivery and Security

The maintained server-rendered administrative flow is:

1. `GET /admin/academic-initialization`;
2. CSRF-protected `POST /admin/academic-initialization/preview`;
3. review the complete classification and issues;
4. exact CSV reupload with the opaque preview token;
5. CSRF-protected `POST /admin/academic-initialization/apply`;
6. PRG to `GET /admin/academic-initialization/result`.

Every route uses AuthenticationMiddleware and the existing exact temporary administrator gate. Mutations are POST-only. Files are bounded, stored under a random name outside `public`, never retained in session and removed in `finally`. Output is escaped, cache is disabled for result surfaces and unexpected failures return safe Spanish feedback without SQL, paths, credentials or row payloads.

Navigation visibility is not authority. No Representative route or new role model is introduced.

---

# 7. Architecture and Physical Model

Delivery contains no SQL or business rule. Application owns preflight, classification, state integrity and the batch transaction. Domain retains all Enrollment and AcademicPlacement invariants. Infrastructure provides only CSV reading, temporary-file storage and prepared PDO code lookups.

No schema change or migration is required. Existing `enrollments.grade_id`, `enrollments.section_id`, Student + AcademicPeriod uniqueness, repositories and Aggregate behavior are reused.

E013 semantics remain unchanged. After a successful initialization, its existing Student Enrollment List naturally reads the DRAFT placement and no longer derives `NOT STARTED` for that Student. Students not included in a partial test remain unchanged.

---

# 8. Production Procedure

Codex must not run this operation against production. The owner/operator procedure is:

1. create and verify a complete database backup;
2. deploy the reviewed release;
3. prepare the real CSV outside Git from the approved institutional source;
4. open the administrative initialization screen;
5. enter the target AcademicPeriod code and execute Preflight;
6. verify the expected row count, unique Students, Grade distribution and Section values;
7. investigate every issue or conflict; do not Apply unless the complete preflight is clean;
8. reselect the exact same CSV and execute Apply once;
9. verify the final created/set/no-op counts;
10. review E013 Student Enrollment List for the target period;
11. create and verify a post-initialization database backup.

Direct table editing through phpMyAdmin is not the primary or approved initialization mechanism.

---

# 9. Explicit Exclusions and Preserved Product Input

This capability does not add Enrollment to E015, generic Family or Student discovery, search by name/document/FamilyCode, new administrative lists, historical placement, Submission, Completion or automatic acknowledgements.

The previously observed lack of usable administrative Family/Student discovery remains future product input. It is not solved or redesigned here.

---

# 10. Validation State

Local validation covers manifest security, reference resolution, all Enrollment classifications, zero-write conflict behavior, all-or-nothing Apply, deterministic locking, stale-preview rejection, rollback, idempotency, Delivery authorization/CSRF/digest/replay/cleanup/XSS and E013 reporting integration.

The complete local suite passes with 841 tests and zero failures plus all three HTTP/session scenarios. No fresh MariaDB execution is claimed because the six disposable-harness environment variables were not available in the implementation session. The schema is unchanged; fresh physical evidence must be recorded separately if required before production deployment.
