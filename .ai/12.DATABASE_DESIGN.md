# DATABASE DESIGN

## Fuente y convenciones
Diseño físico derivado de `11.DOMAIN_MODEL.md` y `15.ENROLLMENT_DOMAIN_DISCOVERY.md`. PostgreSQL/MySQL equivalentes: `BIGINT` ids, `VARCHAR`, `TEXT`, `BOOLEAN`, `DATE`, `TIMESTAMP`, `DECIMAL`; todas las tablas tienen `id` y auditoría (`created_at`, `updated_at`, `deleted_at` cuando aplica). Una base por institución; no `institution_id`.

## Catálogos
`document_types`, `sexes`, `marital_statuses`, `education_levels`, `relationship_types`, `provinces`, `cantons`, `parishes`, `grades`, `sections`, `academic_periods`, más `status_types`/`statuses` si la implementación vigente los conserva. PK `id`; códigos/nombres únicos por catálogo. FK canton→province y parish→canton; no se inventan valores.

## Identity & Academic Core
`persons(id, document_type_id FK, document_number, first_name, middle_name, first_surname, second_surname, birth_date, sex_id FK, marital_status_id FK NULL, education_level_id FK NULL, email NULL, mobile_phone NULL, landline_phone NULL, status_id FK)`. Unicidad `(document_type_id,document_number)` cuando el número está definido. `users(id, person_id FK UNIQUE, username_or_email UNIQUE, password_credential, status_id FK, last_access_at NULL, locked_at NULL)`. `representatives(id, person_id FK UNIQUE, occupation NULL, company NULL, position NULL, work_phone NULL, work_email NULL, status_id FK)`. `students(id, person_id FK UNIQUE, institutional_code UNIQUE, admission_date, status_id FK)`.

## Family Management
`families(id, display_name, status_id FK)`. `family_representatives(id, family_id FK, representative_id FK, relationship_type_id FK, is_primary, status_id FK, UNIQUE(family_id,representative_id))`; índice único parcial/funcional garantiza un primary activo por familia. `family_students(id, family_id FK, student_id FK, started_at, ended_at NULL, status_id FK)`; índice único parcial de `student_id` para una relación activa.

`family_addresses(id, family_id FK, label, province_id FK, canton_id FK, parish_id FK, main_street, street_number NULL, secondary_street NULL, sector NULL, reference NULL, latitude NULL, longitude NULL, status_id FK)`. FKs geográficas y CHECK de coordenadas. Para evitar FK polimórfica: `representative_address_assignments(id, family_address_id FK, representative_id FK, status_id FK, UNIQUE(family_address_id,representative_id))` y `student_address_assignments(id, family_address_id FK, student_id FK, status_id FK, UNIQUE(family_address_id,student_id))`; índices únicos activos por `(family_id, representative_id)` y `student_id` se implementan con columnas derivadas/constraints o triggers transaccionales. Servicio de dominio verifica que miembro y dirección pertenezcan a la misma Family. No se borra una dirección asignada; se desactiva.

`family_emergency_contacts(id, family_id FK, names, relationship_type_id FK, mobile_phone, phone NULL, email NULL, observations NULL, status_id FK)`. `emergency_contact_assignments(id, family_emergency_contact_id FK, student_id FK, priority NULL, status_id FK, UNIQUE(contact_id,student_id), UNIQUE(student_id,priority) cuando priority no es NULL)`. `family_authorized_pickups(id, family_id FK, names, relationship_type_id FK, mobile_phone, phone NULL, document_number, observations NULL, status_id FK)`. `authorized_pickup_assignments(id, family_authorized_pickup_id FK, student_id FK, status_id FK, UNIQUE(pickup_id,student_id))`. Asignaciones no cruzan Family y bloquean eliminación de recursos.

## Enrollment
`enrollments(id, student_id FK, family_id FK, academic_period_id FK, grade_id FK, section_id FK NULL, billing_information JSON/columnas normalizadas, medical_information JSON/columnas normalizadas, requires_institutional_transport BOOLEAN, is_authorized_to_leave_alone BOOLEAN, status_id FK, started_at, submitted_at NULL, completed_at NULL, cancelled_at NULL, UNIQUE(student_id,academic_period_id))`. Si la base no usa JSON, Billing/Medical se descomponen en columnas atómicas; ambas opciones preservan el Value Object. FKs student/family y constraint de periodo.

`institutional_documents`, `institutional_document_versions(institutional_document_id FK, version, file_reference, published_at, status_id FK, UNIQUE(document_id,version))`, `document_requirements(institutional_document_version_id FK, academic_period_id FK, is_required)`, `document_acceptances(enrollment_id FK, institutional_document_version_id FK, accepted_at, accepted_by_representative_id FK, UNIQUE(enrollment_id,institutional_document_version_id))`.

Snapshot: `enrollment_submission_snapshots(id, enrollment_id FK UNIQUE, submitted_at, submitted_by_representative_id FK, representative_data JSON/columnas, student_data JSON/columnas, family_data JSON/columnas)`, con tablas hijas opcionales `submitted_address_snapshots`, `submitted_emergency_contact_snapshots`, `submitted_authorized_pickup_snapshots` referenciadas por snapshot. No duplica billing/medical/transport/placement/acceptances. Reenvío actualiza/reemplaza el snapshot dentro de la misma transacción.

## Integridad y estados
FK con RESTRICT para recursos asignados y documentos aceptados; CASCADE solo para hijos puramente dependientes. Estados permitidos para Enrollment: Draft, Submitted, Completed, Cancelled. Índices en todas las FK, `(family_id,status_id)`, `(student_id,status_id)`, `(academic_period_id,status_id)` y consultas de revisión. Desactivación conserva historia; eliminación física no aplica a registros con referencia histórica.

## Multiinstitución y seguridad
La separación por base de datos implementa el aislamiento institucional. La autorización se valida en servidor antes de cada lectura/escritura. Este documento no define migraciones ni rutas.
