# 3. Migration 012 Physical Contract

Migration `012_create_user_capabilities` adds exactly:

```text
user_capabilities
├── id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
├── user_id BIGINT UNSIGNED NOT NULL
├── capability_code VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL
```

Constraints:

- `uq_user_capabilities_user_code (user_id, capability_code)`;
- `fk_user_capabilities_user` to `users(id)` with `ON DELETE RESTRICT ON UPDATE RESTRICT`;
- InnoDB, table default `utf8mb4_unicode_ci`;

- ledger row `012_create_user_capabilities` in the next batch;
- no change to Person, User, credentials, statuses, lockout, Family, Enrollment or institutional data.

The migration's legacy `admin` lookup is a one-time compatibility backfill. Runtime report authorization remains UserId plus persisted capability and never username.

## 5.2 DDL draft

Run only after Stage 2 approves the exact artifact and checksums:

```sql
SET time_zone = '+00:00';

CREATE TABLE `user_capabilities` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `user_id` BIGINT UNSIGNED NOT NULL,
    `capability_code` VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    `granted_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uq_user_capabilities_user_code` (`user_id`, `capability_code`),
    CONSTRAINT `fk_user_capabilities_user` FOREIGN KEY (`user_id`)
        REFERENCES `users` (`id`) ON DELETE RESTRICT ON UPDATE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

MariaDB DDL causes implicit commits. `CREATE TABLE` is not made reversible by surrounding it with `START TRANSACTION`; after it succeeds, the table persists even if later backfill or ledger work fails. The application must remain in maintenance, and the verified full backup is the authoritative recovery mechanism.

## 5.3 Backfill and ledger draft

The reviewed artifact must perform the backfill and ledger registration in one transaction after DDL. This draft deliberately inserts the ledger row only when exactly one exact Admin exists and exactly one corresponding capability row exists:

```sql
SET time_zone = '+00:00';
START TRANSACTION;

SELECT u.id
FROM users u
WHERE BINARY u.login_identifier = BINARY 'admin'
   OR BINARY u.normalized_login_identifier = BINARY 'admin'
ORDER BY u.id
FOR UPDATE;

INSERT INTO user_capabilities (user_id, capability_code)
SELECT u.id, 'REPORTS_VIEW_ALL'
FROM users u
WHERE BINARY u.login_identifier = BINARY 'admin'
  AND BINARY u.normalized_login_identifier = BINARY 'admin'
  AND (
      SELECT COUNT(*)
      FROM users candidate
      WHERE BINARY candidate.login_identifier = BINARY 'admin'
         OR BINARY candidate.normalized_login_identifier = BINARY 'admin'
  ) = 1;

SET @migration_batch = (
    SELECT COALESCE(MAX(existing.batch), 0) + 1
    FROM migrations existing
);

INSERT INTO migrations (migration, batch, executed_at)
SELECT '012_create_user_capabilities',
       @migration_batch,
       UTC_TIMESTAMP()
WHERE (
    SELECT COUNT(*)
    FROM user_capabilities uc
    INNER JOIN users u ON u.id = uc.user_id
    WHERE BINARY u.login_identifier = BINARY 'admin'
      AND BINARY u.normalized_login_identifier = BINARY 'admin'
      AND BINARY uc.capability_code = BINARY 'REPORTS_VIEW_ALL'
) = 1;

COMMIT;
```

On the first valid execution, both INSERT statements must affect exactly one row. The final Stage 2 artifact must make affected-row expectations explicit in its operator checklist. If any statement errors or an affected-row expectation is not met, treat the database as partially migrated even if a later query appears correct; keep maintenance active and follow section 7.

## 7.4 Recovery cases

- **Before SQL:** remove/abandon the staged release; current code and database remain unchanged.
- **DDL/DML/ledger partial or preservation mismatch:** keep maintenance active and restore the complete database backup. Do not activate new code and do not rely on `down()`.
- **Schema 012 verified, code activation fails:** immediately switch back to the complete `b3a6bea` runtime. Old code with schema 012 is the bounded service-recovery state. Then decide under maintenance whether to keep the verified additive schema temporarily or restore the database backup for exact pre-upgrade state.
- **Post-activation functional/security failure:** switch back old code. If no post-upgrade writes were accepted, restore the database backup for integral rollback. If writes were accepted, stop and perform an incident-specific recovery analysis; never overwrite newer data automatically.
- **Integral rollback:** restore old runtime, database backup, `.env`, branding and required storage as one coordinated set, then repeat the old-version smoke test before reopening traffic.

Backups remain outside `public/`, encrypted or access-controlled according to institutional policy, and retained until explicit post-deployment acceptance and retention expiry.

## 15.2 Demonstrated cause

The original artifact captured affected rows in a later statement:

```sql
INSERT INTO user_capabilities ...;
SET @grant_rows = ROW_COUNT();
```

MariaDB defines `ROW_COUNT()` as the effect of the immediately preceding statement. It is therefore not a durable property of the earlier `INSERT`. phpMyAdmin's SQL-file import parses and executes small files statement by statement. Its execution path reads affected rows through the client API and also performs profiling/warning/result handling between imported statements. A result-set or diagnostic statement becomes the immediately preceding server statement, so the later `ROW_COUNT()` no longer describes the `INSERT`.

The original artifact then deliberately converted any affected-row mismatch into a two-row scalar subquery, which MariaDB correctly rejected as `#1242 - Subquery returns more than 1 row`. Because `CREATE TABLE` had already caused an implicit commit, the error rolled back or prevented the capability/ledger DML but could not remove the newly created table. This explains the exact second rehearsal state.

Controlled reproduction on MariaDB `11.4.13-MariaDB` proved the distinction:

- the original SQL passes when executed directly with no client statement between `INSERT` and `ROW_COUNT()`;
- the same SQL fails exactly at `@assert_exact_grant_insert` with `#1242` when phpMyAdmin-equivalent warning/profiling statements are interleaved; and
- a real phpMyAdmin `5.2.3` multipart SQL import reproduced the same `#1242` and final counts `table = 1`, `ledger 012 = 0`, `capabilities = 0`.

MariaDB 11.4 syntax or the approved table structure is therefore not the demonstrated defect. The defect is the original artifact's client-sensitive use of affected-row session diagnostics across separate imported statements.

## 15.3 Minimal correction

The corrected artifact preserves the exact physical and authorization contract in sections 3 and 5. It changes only procedural guards:

1. remove every dependency on `ROW_COUNT()`;
2. compute the complete 001–011/table/Admin preflight from persisted database state and retain only its boolean result in a named session variable;
3. use prepared `SIGNAL SQLSTATE '45000'` guards so invalid, repeated or partial states stop before DDL under the default phpMyAdmin behavior;
4. execute the exact approved `CREATE TABLE` only when the preflight result is valid;
5. insert the one exact Admin `REPORTS_VIEW_ALL` assignment and ledger row inside one transaction, with each step gated by current table state rather than client affected-row metadata;

7. select `COMMIT` only for that exact final state, otherwise execute `ROLLBACK` and emit a controlled failure.

phpMyAdmin diagnostic statements do not overwrite named user variables. If an import session were nevertheless lost, the guards use `COALESCE(..., 0)` and cannot authorize capability or ledger DML.
